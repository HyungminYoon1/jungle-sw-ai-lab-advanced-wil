## 저장 결과를 확인하는 방법이 달라졌다

11월 7일에는 상태 변경 POST가 `500`이면 요청이 전달되지 않았거나 저장이 실패했다고 보고, 변경 전후 상태를 비교하겠다고 답했다. 그런데 같은 상태에도 여러 경로로 도달할 수 있다. DB가 Commit을 거부한 경우에는 변경과 새 이력이 함께 취소된다. Commit 뒤 응답 전달이 끊기면 이력은 이미 남아 있다. 두 상황을 가르려면 현재 상태와 함께 원래 UUID의 저장 결과를 확인해야 한다는 점을 배웠다. [11월 7일 문답](./study-notes/2026-11-07-study-questions.md)

재확인에는 처음 보낸 UUID와 내용을 유지한다. 조회 권한이 유효하고 해당 제출이 이미 저장됐다면 `200`으로 그때의 결과를 받으며 새 이력은 0건이다. 해결 이력이 상태 버전 2로 남아 있어도, 그 뒤 명시적으로 재개했다면 현재 화면에는 `OPEN`과 버전 3을 표시한다. 반대로 해당 UUID의 이력이 없고 기대 버전이 오래됐다면 새 변경에 대한 버전 검사에서 `409 STATUS_VERSION_CONFLICT`가 된다. 11월 8일에는 버전이 3까지 올라간 중간의 해결과 재개가 예제에서 빠졌음을 직접 질문했다. 그 흐름을 보완한 뒤에는 왜 `409`가 나오는지 설명할 수 있었다. [11월 8일 문답](./study-notes/2026-11-08-study-questions.md)

저장 성공을 이미 확인한 뒤 조회만 실패한 경우도 다르다. 이때는 화면 갱신용 GET만 다시 보낸다. 브라우저 테스트는 첫 POST와 재확인 POST의 JSON 전체를 대조했고, 실행한 코드를 나중에 구분하려면 기준 Commit과 작업 트리 상태를 함께 남겨야 했다. [상태 변경과 브라우저 검증](./lab-reports/2026-11-04-ticket-status.md#화면과-실제-browser)

## 읽은 범위를 정확히 남겨야 했다

인계 사례에서 처음에는 A가 30번까지 확인했다면 B도 30번까지 확인한 것으로 표시할 수 있다고 생각했다. 설명을 듣고 보니 팀 공통 진행률과 담당자가 명시적으로 확인한 범위는 서로 다른 값이었다. 이 Lab은 후자를 선택했다. A의 기록은 배정 1에 남고, B의 배정 2에는 B가 확인을 저장할 때까지 확인 지점이 없다. 같은 배정에서 30번 확인 뒤 20번 확인이 저장돼도, 유효 범위는 기록 ID가 아니라 대상 고객 Message ID의 최댓값인 30번이다. 작은 확인 기록도 남는다. [인계와 확인 범위 문답](./study-notes/2026-11-04-study-questions.md)

담당자가 30번을 선택한 뒤 31번이 저장됐다면, 확인 POST는 30번을 기록하고 31번을 확인 필요로 남긴다. 해결 요청은 선택한 고객 글이 최신이며 해당 배정에서 명시적으로 확인됐는지, 연결한 공식 답변이 같은 Ticket에 속하는지 함께 검사한다. 조회가 끝났거나 공식 답변을 작성했다는 사실만으로 새 고객 글을 확인했다고 판단할 수는 없다. [확인 지점 학습 자료](./study-docs/confirmation-checkpoint-and-assignment.md), [상태 변경과 해결 근거](./study-docs/status-change-transaction-flow.md)

## 화면의 결과와 DB의 근거를 대조했다

권한 회수 뒤 같은 세션의 재확인 POST에서 `404`를 관찰했다. 접근 차단은 이 HTTP 결과로 확인했다. 기존 확인 기록의 보존은 별도 SQL로 행의 ID, 작성자, 배정 버전과 대상 등 전후 값을 대조해 확인했다. 행 수만 비교하면 최초 문의를 가리키던 AI Job의 `input_message_id`가 후속 글로 바뀌는 문제를 놓칠 수 있다. [권한 회수 브라우저 검증](./lab-reports/2026-11-04-confirmation-authority-browser.md), [11월 7일 보존 문답](./study-notes/2026-11-07-study-questions.md#보존과-접근-권한을-검증하는-방법)

같은 Ticket에 고객 후속 글과 담당자 답변이 겹치는 경우, 두 번째 요청은 자기 Message를 쓰기 전에 Ticket 행 잠금을 기다렸다. 두 저장 순서에서 대기 지점과 Commit 뒤 대화 페이지를 확인했다. 테스트가 통과했다는 사실과 사용이 끝난 테스트 자원이 닫혔다는 사실도 구분했다. 후자는 실제로 사용한 Spring Context와 연결 Pool의 상태 및 해당 Pool의 관리 Thread를 따로 확인했다. [혼합 메시지 검증과 직접 재현 기록](./lab-reports/2026-11-04-final-review-publication.md), [테스트 자원 정리](./lab-reports/2026-11-04-test-jvm-cleanup.md)
