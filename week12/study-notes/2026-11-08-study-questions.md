## 브라우저가 원래 제출을 유지하는지 확인

화면 JavaScript를 수정한 뒤 재확인 버튼을 검사하는 문제에서, 사용자는 최초 UUID를 기록하고 버튼을 눌렀을 때 전송되는 UUID와 비교한다고 답했다. 실행 결과에 코드 기준을 남기는 방법은 모르겠다고 했다.

이 비교를 수행하는 기존 검사는 Lab의 `TicketStatusBrowserExperiment`다. 최초 POST와 재확인 POST의 JSON 본문 전체를 비교한다. 실행 전 `git rev-parse HEAD`로 기준 Commit을, `git status --short`로 변경 유무와 파일을 확인한다. 수정한 파일이 있다면 해당 Diff도 보관해야 같은 코드를 다시 구성할 수 있다. 예제의 대상 파일은 `git diff HEAD -- src/main/resources/static/ticket-status-ui.mjs`로 확인할 수 있다. 테스트 이름, 명령과 실제 종료 코드도 같은 기록에 남긴다. ## Ticket 식별, UUID와 상태 버전

사용자는 상태 버전 검사를 앞세울 때 다른 고객의 Ticket을 잘못 대상으로 삼을 수 있다고 설명했다. 그 예는 URL의 Ticket ID와 요청을 보낸 계정의 접근 권한으로 처리하는 문제다. 서버는 Ticket과 접근 권한을 확인하고, 그 Ticket ID/요청 계정 ID/UUID에 해당하는 상태 이력을 조회한다. 상태 버전은 선택된 Ticket에서 변경이 일어날 때 증가한다.

같은 Ticket에서 최초 해결 요청은 상태 버전 1을 예상해 해결 버전 2로 저장됐다. 이어 재개돼 현재 상태는 OPEN, 버전은 3이다. 원래 요청을 재전송했을 때 먼저 버전을 비교하면 1과 3의 차이로 409 `STATUS_VERSION_CONFLICT`가 발생한다. 현재 구현은 권한을 검사한 뒤 같은 UUID와 내용으로 저장된 이력을 찾아 200과 함께 해결 이력 및 현재 상태를 반환한다. 새 제출에는 현재 상태 버전 검사를 적용한다. [상태 변경의 저장과 권한 경계](../lab-reports/2026-11-04-ticket-status.md#저장과-권한-경계)

적용 문답에서는 현재 버전 3이고 작성 권한이 유효한 같은 Ticket에서, 두 요청에 기대 버전 1을 담았다. 사용자는 기존 UUID K에는 이미 등록됐다는 메시지를 반환하며 추가 등록을 거부한다고 답했다. 새 UUID L에는 의도한 새 요청인지 확인해, 의도했다면 새 메시지로 추가하자고 답했다.

- K는 동일한 원래 요청으로 이력을 찾았으므로 재확인에 성공한다. HTTP 200과 과거 해결 이력 및 현재 OPEN/버전 3을 반환하며 추가 이력은 0건이다.
- L은 새 상태 변경 제출이다. 기대 버전 1과 현재 버전 3을 대조해 409 `STATUS_VERSION_CONFLICT`를 반환한다. 새 변경을 의도했다면 최신 상태에서 가능한 동작을 골라 새 제출을 작성한다. 유효한 새 상태 변경이 저장하는 것은 상태 변경 이력이다.

보충 문답에서 사용자는 K의 이력이 없는데 현재 버전이 3으로 바뀐 경위를 물었다. 기존 질문에는 중간의 상태 변경이 빠져 있었다. K가 저장되지 않고 별도 상태 변경도 없으면 상태 버전은 1이다. 일반 후속 글 작성은 고객 Message를 저장하며, 상태 버전은 명시적인 상태 변경이 저장될 때 증가한다.

예시는 `IN_PROGRESS/1`에서 K가 저장에 실패한 뒤, 요건을 충족한 별도의 해결 요청이 `RESOLVED/2`로 저장되고 고객의 명시적 재개 요청이 `OPEN/3`으로 저장된 상황으로 구체화했다. 이때 K의 이력은 없고 K가 담은 기대 버전은 1이다. 사용자는 기존 이력이 없어 새 상태 변경으로 처리하고, 기대 버전 1과 현재 버전 3이 달라 409 `STATUS_VERSION_CONFLICT`를 반환한다고 정확히 답했다.
