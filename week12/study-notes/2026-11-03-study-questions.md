## 1 학습 재개와 정책 선택

작성자는 학회 참석으로 지난주 학습/구현을 이어가지 못했다고 설명하고 11/3~9 모두 학습하기로 했다. 기존 10/27 기록을 보존하면서 12주차 계획을 반영했다. 실제 사용 시간은 아직 기록하지 않았으며 계획 배분을 사용 실적으로 계산하지 않는다.

사용자 답변으로 F03의 원문 보존/새 문의 안내, F05의 Commit 직후 공개/고객·담당자 표시, F12의 내 문의 목록 포함을 합의했다. 이어서 F13의 Ticket 단위 작성과 공개 Message 기준 활동 시각도 합의했다. 이 기록은 업무 정책의 선택이며 신규 코드 실행 결과가 아니다.

## 2 첫 번째 문답: 80 확인 뒤 늦게 Commit된 71 확인

질문은 같은 배정에서 80번 고객 Message까지 확인한 기록이 Commit된 후, 다른 UUID의 71번 확인 요청이 늦게 Commit되는 상황이었다.

사용자는 80번이라고 답했고, DB가 진실의 근원이며 이미 가장 최근에 Commit된 내용이 80번이기 때문이라고 설명했다. 결과값은 맞지만 Commit 순서에 대한 이유는 보완이 필요하다.

| 순서 | DB에 저장한 확인 요청 | 같은 Ticket/배정의 유효 확인 범위 |
|---|---:|---:|
| 먼저 Commit | 80번까지 확인 | 80 |
| 나중 Commit | 71번까지 확인 | MAX(80, 71) = 80 |

마지막으로 Commit된 요청은 71이다. 두 기록은 보존하되 범위가 후퇴하지 않도록 through_message_id의 최대값을 사용한다. DB의 최신 Row를 그대로 선택하는 것과 DB 기록에 합의한 계산 규칙을 적용하는 것은 다르다. 같은 이름의 담당자가 다시 배정돼도 다른 배정 버전의 기록을 섞지 않는다.

이 설명을 보완했으며 사용자가 수정한 이유를 독립적으로 다시 설명한 단계는 아직 아니다.

## 3 두 번째 문답: 종류가 다른 동일 제출 UUID

같은 Ticket/작성자/UUID로 공식 답변이 이미 저장된 뒤 같은 본문의 고객 후속 글을 요청하면 200으로 기존 답변을 반환해도 되는지 물었다.

사용자는 200 성공의 구체적인 의미를 모르겠다고 답했다. 고객 후속 글은 추가 문의일 가능성이 있고 문제는 해결되지 않았다고 볼 수 있으므로 고객 또는 담당자가 명시적으로 Ticket을 종료해야 한다는 의견을 제시했다.

질문의 대상은 메시지 제출과 재확인이고, 사용자의 설명은 문의 해결 상태에 관한 것이었다. 상태를 명시적으로 처리해야 한다는 방향과 별개로 동일 제출의 판단을 다시 설명했다.

| 이 후속 API의 상황 | HTTP | 새 Message |
|---|---:|---:|
| 새 후속 글을 Commit | 201 | 1건 |
| 같은 고객 후속 글을 같은 UUID/종류/본문으로 재확인 | 200 | 0건 |
| 기존 공식 답변의 UUID를 다른 종류인 고객 후속 글에 사용 | 409 FOLLOWUP_REQUEST_CONFLICT | 0건 |

종류가 다르면 같은 제출로 인정하지 않는다. 409에서도 기존 공식 답변은 유지한다. 이 200은 저장된 같은 제출의 결과를 돌려주는 성공이며 문의 해결을 뜻하지 않는다. [HTTP 일반 의미와 우리 API 계약의 구분](../customer-followup-contract-draft.md#http-응답과-문의-해결-상태)은 기술 계약에 보완했다.

## 4 해결 상태에 관한 의견과 남은 선택

F04/P2에 따라 후속 글/공식 답변 저장과 Ticket 상태 변경은 분리한다. 추가 글이 감사 인사인지 오류 경과인지 본문으로 추측해 자동 해결/재개하지 않는다. RESOLVED에서도 고객 후속 글은 저장할 수 있고 담당자가 확인할 수 있게 표시한다.

사용자는 명시적 종료의 필요성을 제시했지만 고객과 담당자 중 누가 해결을 확정하는지, 재개 권한/전이와 조건은 아직 정하지 않았다. T02~T04를 합의로 바꾸거나 CLOSED 상태를 새로 추가하지 않는다.

## 5 재확인 질문과 실제 답변

1. 같은 고객 후속 글이 Commit된 뒤 같은 Ticket/작성자/UUID/종류/본문을 다시 제출하면 HTTP와 추가 Row 수는 무엇인가? 그 응답으로 해결 여부도 알 수 있는가?
2. RESOLVED Ticket에 '같은 오류가 계속됩니다'라는 새 후속 글이 저장되면, 메시지 저장 자체가 Ticket을 자동으로 OPEN으로 바꾸는가?

첫 질문에 사용자는 '200이고 추가 Row는 0건입니다. 문의 해결 여부와는 별개입니다'라고 답했다. 같은 고객 후속 제출의 재확인과 문의 해결 상태를 구분한 답변으로 확인했다.

두 번째 질문에는 메시지 저장과 문의 재개는 별개이므로 명시적으로 상태를 변경해야 한다고 답했다. 기존 F04/P2를 적용한 답변으로 맞다. 이 문답으로 고객/담당자의 해결 권한을 새로 확정한 것은 아니다.

이 시점에는 두 재확인 문항의 답변을 확인했다. 80/71에서 최대 대상 ID를 선택하는 이유와 다른 종류의 UUID 충돌 설명은 추가 점검으로 남겼다. 이후 종류 충돌에 대한 직접 답변은 7절에 기록했다.

## 6 실행과 검증 경계

문답 시점에는 Codex가 기존 계약과 HTTP 공식 자료를 확인하고 기술 초안/정책 문서의 설명을 보완했다. 그 시점에는 새 업무 코드, Migration, 실제 DB 실행이나 Browser Test를 진행하지 않았다. 이후 구현/실행 결과는 별도 근거를 연결하고 기존 Lab 6eed98c의 검증 결과나 이번 문답과 섞지 않는다.

이후 V11 고객 후속 저장과 공식 답변 재확인의 종류 비교를 구현하고 로컬 검증했다. Lab Commit은 645b3df이며 [실행 보고서](../lab-reports/2026-11-03-customer-followup-storage.md)에 새 HTTP 26개/마이그레이션 1개와 전체 Java 1,095개/패키징 후 2개, JavaScript 333개/Lint 결과를 구분했다. 이는 Codex의 구현/실행 근거이고 사용자의 독립 구현이나 직접 실행 근거는 아니다.

두 저장소의 원격 공개/배포나 실제 AI 실행을 이번 결과로 주장하지 않는다. 이후 내 문의 목록과 고객 작성 화면도 [후속 보고서](../lab-reports/2026-11-03-my-tickets-and-followup-ui.md)처럼 로컬 검증했다. 명시적 확인은 그 뒤다. 실제 사용 시간과 남은 기술 예산은 아직 확인하지 않았다.

## 7 구현 후 문답: 고객 소유권과 종류 충돌

직원 서비스 권한이 회수돼도 자기 문의의 고객 소유권을 유지하는 이유를 물었다. 사용자는 직원 권한과 고객으로서의 문의 소유권은 별개이기 때문이라고 답했다. 전체 계정의 로그인 중지와 특정 서비스 직원 권한 회수를 구분한 답변으로 맞다.

이미 CUSTOMER_FOLLOWUP으로 저장된 같은 UUID를 공식 답변 API에 보내고 배정 버전을 생략한 상황에서는 200을 반환하면 안 된다고 답했다. 다만 고객 후속 문의를 새 메시지/질의로 처리하고 공식 답변이 아직 없으면 400대 응답으로 거부해야 한다는 이유를 제시했다.

거부한다는 방향은 맞지만 충돌의 원인은 기존 공식 답변의 유무가 아니다. 요청 경로는 공식 답변 작성이고 DB의 같은 Ticket/작성자/UUID는 고객 후속 글에 이미 사용됐다. 이 제출을 새로운 글로 바꾸거나 다른 경로로 재해석해 저장하지 않는다. REPLY_REQUEST_CONFLICT/409와 추가 Row 0건으로 처리하고 기존 고객 글을 유지한다.

실제 Service의 replay()는 배정 버전 비교 전에 OFFICIAL_REPLY 종류부터 검사한다. 따라서 올바른 배정 버전을 보내도 종류 충돌은 남는다. 반대로 기존 공식 답변이 없어도 현재 담당자가 새 UUID/유효 본문/현재 배정 버전으로 첫 답변을 작성하면 저장을 허용하고 Commit 후 201을 반환한다. 정정 대상은 일반 첫 답변의 필수 조건이 아니다.

재확인에서 사용자는 올바른 배정 버전을 보내도 같은 UUID가 이미 고객 후속 글에 사용돼 메시지 종류가 충돌하므로 200을 반환하면 안 된다고 설명했다. 충돌 원인을 직접 설명한 답변으로 확인했다. 구체적인 409/추가 Row 0건은 Codex가 다시 명시했다.

유효한 새 UUID/본문/현재 배정 버전으로 첫 공식 답변을 작성하는 경우에는 허용할 수 있고 Commit 후 201/추가 Row 1건이라고 답했다. 기존 공식 답변의 존재가 첫 답변의 조건이 아니라는 점을 구분했다. 이 문답에서 업무 코드나 기존 Test 결과를 바꾸지는 않았다.

## 8 목록과 화면 구현 후 문답

첫 페이지를 읽은 뒤 아직 읽지 않은 문의에 새 답변이 달려 맨 위로 이동한 상황을 물었다. 사용자는 기존 Cursor를 계속 읽으면 놓칠 수 있다고 답했고, 조회 내용에 번호를 붙여 업데이트할 때 최신 번호를 할당하고 동적으로 조회하는 방안을 제시했다.

놓칠 수 있다는 판단은 맞다. 다만 별도 활동 순번을 붙여도 기존 Cursor보다 위로 이동한 항목은 그 다음 페이지에 포함되지 않는다. Codex는 '100~91을 읽은 뒤 다른 문의가 새 활동 101이 돼도 90 이하 조회에 포함되지 않는다'는 예를 들었다. 문의 ID를 바꾸는 구현은 하지 않았고 현재 목록은 첫 페이지부터 명시적으로 새로 조회해 새 활동을 확인한다. 이 설명을 사용자가 독립적으로 다시 설명한 단계는 아니다.

두 번째 질문에 사용자는 유효 지점은 80이며 마지막 Commit은 유효기간이 지났고 Commit된 것 중 가장 큰 번호의 확인을 믿어야 한다고 답했다. 80이라는 값은 맞지만 만료시간이 기준은 아니다. Codex는 같은 Ticket/배정 안에서 MAX(through_message_id)를 사용하고 작은 확인도 유효한 이력으로 남긴다고 보완했다.

확인 기록 ID 11→고객 메시지 80, 기록 ID 12→고객 메시지 71을 제시해 어떤 필드의 최대값인지 다시 물었다. 사용자는 잘 모르겠으며 올바른 방향을 설명해달라고 요청했다. 기록의 저장 순서와 확인한 대화 범위를 나누고, 71번 요청이 늦게 도착해도 이미 확인한 72~80번을 취소하지 않는다는 예로 설명했다. 작은 기록의 삭제/만료 처리는 하지 않는다.

A가 버전 1에서 80번까지 확인한 뒤 B에게 인계되어 버전 2가 되면 A의 기록을 현재 확인 지점으로 써도 되는지에는 '그럴 것 같습니다'라고 답했다. 현재 합의한 F11은 담당자별 명시적 확인이므로 버전 2의 확인 지점은 NULL이다. A의 기록은 버전 1 이력으로 보존하고 B의 확인으로 복사하지 않는다. 인계 완료와 B의 명시적 확인 기록을 구분해 설명했다.

이 시점에는 두 구분의 설명을 보완했고 독립적인 재설명 검증은 아직이었다. [확인 지점 학습 자료](../study-docs/confirmation-checkpoint-and-assignment.md)에 두 번호, MAX, 새 배정과 새 글의 예를 정리했다. 대화 조회가 자동 확인을 의미하지 않는 계약도 유지한다. 이후 V12 API/저장 검증은 학습 답변과 별도 근거로 기록한다.

새 30/20 사례에서 사용자는 현재 지점은 30이며, 20번 확인 기록은 실제 처리 결과를 유지하고 감사에 대비하도록 로그에 남겨야 한다고 답했다. 최대 범위와 이력 보존을 적용한 답변으로 확인했다. Codex는 이번 이력이 별도 DB 확인 테이블의 Row로 보존되며 실행 로그에만 적는 방식은 아니라고 구체화했다. 배정 버전 2에 관한 새 질문은 이번 전달 시점까지 답변을 확인하지 못해 다음 회차의 보충으로 남긴다.

V12 저장/API는 Lab 80e5de9/6b3ba1d에서 로컬 검증/Commit했다. [확인 API 실행 보고서](../lab-reports/2026-11-03-customer-message-confirmations.md)에 42개 HTTP/1개 Migration과 전체 Java 1,165+2, 남은 종료 경고와 직원 화면 범위를 기록했다. 학습자의 독립 구현이나 모든 개념의 이해 완료로 바꾸지 않는다.
