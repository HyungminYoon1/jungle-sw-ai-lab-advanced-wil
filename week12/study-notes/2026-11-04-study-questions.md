# 11/4 학습 기록: 인계와 명시적 확인 범위

> 회차: 2026-11-04
> 범위: 직원 업무 표시와 확인 버튼. [주간 계획](../weekly-plan.md)의 11/4 과업
> 구현/실행은 Codex가 진행했으며 학습자의 이해와 구분한다.

## 질문과 실제 답변

| 질문 | 사용자 답변 | 확인할 점 |
|---|---|---|
| A가 배정 1에서 30번까지 확인한 뒤 B/배정 2로 인계. B는 아직 확인 버튼을 누르지 않은 상태의 표시 | 'B도 30번까지 확인' | 현재 F11 계약과는 다름. 다만 승계 여부는 설계 선택이므로 보편적인 오답으로 다루지 않고 값의 의미부터 설명해야 함 |
| 30번을 선택한 뒤 저장 직전에 새 고객 글 31번 도착. 30번 확인 저장으로 31번도 포함할 수 있는지 | '잘 모르겠습니다.' | 명시한 대상 30만 저장. 31번은 확인 필요로 남김 |

## 보완한 설명

이 기록은 문의에 대한 누구의 확인이든 합쳐 놓은 공통 진행률이 아니다. 현재 담당자가 명시적으로 확인한 범위다. A의 '30번까지 확인했다'를 B에게 옮기면 B가 아직 남기지 않은 확인을 서버가 대신 기록하는 셈이다. 인계는 책임 담당자를 바꾸고 확인은 해당 담당자의 선언을 남기는 서로 다른 작업이다.

따라서 A/배정 1의 기록은 남기고 B/배정 2의 유효 확인 지점은 NULL로 둔다. 이는 과거 이력이나 고객 글을 삭제했다는 뜻도, B가 실제로 읽지 않았다는 증명도 아니다. B의 명시적 기록이 없다는 뜻이다.

30번을 선택한 뒤 도착한 31번도 마찬가지다. 담당자가 읽었는지 확인하지 않은 새 글까지 자동 포함하지 않는다. 선택한 throughMessageId와 그때의 expectedAssignmentVersion을 함께 보관하고 서버는 그 범위만 검사/저장한다. HTTP 201/Commit 성공도 명시한 기록이 저장됐다는 뜻이며, 그 사이 도착한 모든 글을 확인했다는 뜻은 아니다.

## 재확인과 다음 학습

설명 후 두 변형을 묶어서 제시했다.

1. A가 50번까지 확인한 뒤 B에게 인계했을 때 A의 과거 이력과 B의 현재 표시를 어떻게 나눌지
2. 12번을 선택한 뒤 아직 읽지 않은 새 글 13번이 왔을 때 저장할 범위

첫 질문에 사용자는 '우선 올바른 개념을 설명해주세요.'라고 요청하며, 보편적인 정답이 아니라 설계 차이라면 대안의 차이와 선택 이유부터 설명해야 한다고 지적했다. 둘째 질문에는 '잘 모르겠습니다.'라고 답했다. Codex가 현재 F11과 보편적인 원리를 먼저 나누지 않고 정답처럼 질문한 점을 바로잡고 추가 문답은 잠시 멈췄다.

공식 Twilio/Matrix 자료에서 참여자/사용자별 읽기 위치를 확인했다. 이를 모든 Helpdesk의 인계 규칙으로 확대하지 않고, 팀 공통/사람별/배정별 세 설계 대안을 비교했다. 현재의 한 명 책임 담당자/명시적 인계 목적에는 배정별 확인을 유지하는 안을 추천한다. 팀 공통 50을 유지하는 설계도 가능하지만 그 값을 B 개인의 확인이라고 부르지는 않아야 한다. 이전 담당자 지점을 현재 화면과 함께 보여주는 것은 아직 구현하지 않은 보완안이다.

12/13 사례는 버튼이 선택한 범위를 확인하는 명령인지, 서버의 최신 수신 범위를 일괄 처리하는 명령인지부터 설명한다. 현재 버튼은 12번의 명시적 확인이므로 13번은 새 확인 필요로 남긴다. 13번을 자동 포함하면 새 고객 글의 확인 필요가 사라질 수 있다는 구체적인 영향으로 설명했다.

이 시점에는 설명과 비교 자료를 보완한 단계다. 두 구분을 이해했다고 판정하지 않으며 추가 설명/확인은 이후 실제 답변을 받아 갱신한다. 합의한 F11 정책이나 코드의 배정별 범위를 사용자 학습 답변만으로 변경하지 않는다.

[학습 자료](../study-docs/confirmation-checkpoint-and-assignment.md)에는 두 ID/MAX와 인계 예, 실제 화면에서의 선택/Commit 절차를 두었다. [11/4 검증 보고서](../lab-reports/2026-11-04-staff-confirmation-ui.md)의 Test/Row/화면은 코드 동작의 근거이며 위 이해 점검을 대신하지 않는다.

## 저장/조회 실패 학습으로 진행

사용자는 설계 비교 설명 뒤 '좋습니다. 이해했습니다. 다음 단계 학습을 진행해주세요'라고 말했다. 설명을 이해했다는 본인 표현으로 기록한다. 독립적인 새 사례 풀이를 확인한 결과로 바꾸지는 않는다.

다음에는 확인 저장의 POST와 현재 상태 조회 GET을 나누었다. 유효한 201을 받은 뒤 GET만 실패하면 조회만 재시도하고, POST 응답 자체가 없으면 원래 UUID/대상/배정 버전으로 저장 결과를 재확인한다고 설명했다. 이 둘을 구분하는 질문을 묶어서 제시했다.

사용자는 첫 질문에 'GET만 다시 보냅니다. 확인 저장은 이미 성공했기 때문입니다', 둘째에는 '아니요. 원래 UUID·배정 버전·대상으로 저장 결과를 재확인합니다'라고 답했다. 두 실패 경계를 적용한 선택으로 확인했다.

기존 Node Test Double에 더해 실제 Browser에서 서버의 Commit 완료 응답을 중계 지점에서 차단하는 재현을 진행했다. [실제 Browser/DB 검증](../lab-reports/2026-11-04-confirmation-recovery-browser.md)은 서버 POST 201/200/201과 최종 확인 Row 2건, 원래 제출의 유지와 GET만 재시도하는 화면을 확인했다. 사용자 답변은 별도로 기록한다. 이 설명/실행을 근거로 현재 F11 정책이나 원문/AI 보존 계약을 바꾸지는 않는다.

## 인계와 권한 회수 후의 재확인

현재 서비스 조회 권한을 먼저 검사하고, 기존 UUID의 저장 결과 재확인과 새 확인 쓰기를 구분하는 Service 순서를 설명했다. 인계는 새 쓰기의 담당자를 바꾸지만 활성 직원의 기존 결과 조회 권한까지 없애지는 않는다. 서비스 권한 회수는 기존 결과를 새로 조회하는 것도 막되 이미 Commit된 이력을 삭제하지 않는다.

사용자는 인계 뒤 A가 활성 서비스 직원으로 남은 경우 '기존 결과만 반환하고 B의 확인 기록은 만들지 않습니다'라고 답했다. A 권한 회수 Commit 뒤 새 요청을 시작한 경우에는 '조회를 거부하되 기존 확인 기록은 보존합니다'라고 답했다. 현재 계약을 구분해 적용한 선택으로 확인했다.

[실제 Browser/DB 검증](../lab-reports/2026-11-04-confirmation-authority-browser.md)에서는 기존 Session의 과거 재확인 200, 새 쓰기 403과 회수 후 재확인 404, 남은 A의 기록 한 건을 대조했다. 권한 회수는 검증한 격리 DB의 테스트 장치에서만 실행했다. 이 결과를 사용자의 독립 구현이나 모든 정책/잠금 경합의 이해 완료로 기록하지 않는다.

다음에는 A가 다시 담당자가 된 배정 3에서 같은 대상까지 새로 확인하는 상황을 설명했다. 과거 UUID/배정 1의 제출 재확인과 현재 배정 3의 새 확인은 다른 명령이다. 원래 UUID의 버전만 바꾸는 재사용과, 버전 충돌 뒤 자동 최신화/재전송을 피해야 하는 기존 계약을 기준으로 두 문항을 제시했다.

사용자는 첫 질문에 '배정 3에서 범위를 다시 선택하고 새 UUID로 확인을 제출합니다', 둘째에는 '현재 배정을 조회하고 사용자가 확인 범위를 다시 선택하게 합니다'라고 답했다. 새 배정의 확인과 충돌 뒤 재선택을 현재 계약에 맞게 구분했다. 이 답변을 독립 구현이나 모든 실패 경계의 이해 완료로 확대하지 않는다.

[재선택 UI 검증](../lab-reports/2026-11-04-confirmation-reselection-ui.md)에서는 알려진 배정 버전 충돌에만 명시적 재선택을 연결했다. 실제 A→B→A 뒤 오래된 제출의 409, GET만 하는 초기화와 빈 선택, 새 UUID/배정 3의 201을 Browser/PostgreSQL로 대조했다. HTTP 409만 있거나 오류 Body를 읽지 못하면 결과 미확인 제출을 그대로 보관한다.

## 다음 확인: 같은 제출의 결과와 현재 상태

응답을 잃은 뒤 같은 UUID로 재확인해도 반드시 200인 것은 아니다. 서버에 기존 기록이 없고 현재 쓰기 조건이 모두 유효하면 새로 저장해 201이 될 수 있다. 또한 현재 확인 지점의 GET은 여러 제출에서 계산한 상태이므로 특정 UUID의 저장 증거와 다르다. [학습 자료 10절](../study-docs/confirmation-checkpoint-and-assignment.md#10-저장-성공-뒤-조회-실패와-저장-여부-미확인)의 설명을 바탕으로 이 두 구분을 문답으로 확인했다.

사용자는 첫 요청이 서버에 도착하지 않은 K를 재확인해 처음 저장한 경우 '201이고 추가 확인 Row는 1건입니다.'라고 답했다. 현재 GET의 30번으로 K의 저장을 확정할 수 있는지에는 '아니요. 다른 UUID로 같은 30번까지 확인한 기록일 수 있기 때문입니다.'라고 답했다. 두 답변은 현재 계약에 맞다. 재확인의 가능한 첫 저장과 상태 집계/특정 제출의 증거를 구분한 답변으로 기록한다.

## 공식 답변의 오래된 초안으로 적용

다음에는 `draftVersion`과 `pending`을 구분했다. 전자는 답변을 시작한 배정이고 후자는 이미 저장됐을 수도 있는 제출이다. 미제출의 확인된 버전 차이나 정확한 배정 충돌에는 사용자의 명시적 초안 폐기/GET/새 작성을 제공하고, 결과 미확인 제출은 먼저 원래 정보로 재확인하도록 했다. [학습 자료 13절](../study-docs/confirmation-checkpoint-and-assignment.md#13-공식-답변-초안과-결과-미확인-제출)과 [실제 검증](../lab-reports/2026-11-04-reply-draft-review.md)에 코드와 관찰을 나눠 남겼다.

실제 Browser의 최초 실패에서 저장 후 정정 후보 목록까지 비워 다음 정정을 선택할 수 없는 문제를 찾았다. 재현하는 Node 검사를 추가하고 현재 선택만 비우도록 수정한 뒤 통과했다. Codex가 구현/실행한 결과이며 사용자의 직접 문제 발견이나 수정으로 기록하지 않는다.

배정 3에서 저장/응답 유실 후 배정 5의 재확인 200이 만드는 추가 Row와 저장 버전, 그리고 명시적 초안 폐기 뒤 GET 503에서 새 POST를 허용할지를 두 문항으로 제시했다.

사용자는 첫 질문에 '추가 Row는 0건이고 저장 배정 버전은 3입니다.'라고 답했다. 둘째에는 '아니요. 현재 배정을 다시 조회해 담당자·배정 버전·작성 권한을 확인해야 합니다.'라고 답했다. 과거 저장 결과의 재확인이 당시 기록을 바꾸지 않는다는 점과, 초안 초기화가 새 작성 권한을 보장하지 않는다는 점을 현재 계약에 맞게 구분했다.

## 새 고객 글과 상태를 읽은 시점

다음 계획의 교차 실행을 검토하니 새 글/확인, 인계/확인과 권한 회수의 두 Commit 순서는 이미 서버의 실제 PostgreSQL 테스트와 이전 보고서에 있었다. 이를 미구현으로 보아 새 업무 로직을 추가하지 않고, 확인 대상을 선택한 뒤 고객 글이 도착하는 Browser 순서 한 가지를 강화했다.

[새 검증](../lab-reports/2026-11-04-confirmation-cross-flow.md)은 선택한 1번의 확인 201과 별개로 2번을 확인 필요로 남기는 화면/DB를 대조했다. 대화를 다시 읽어 2번을 표시해도 자동 선택/확인하지 않았다. 기존 서버의 Lock 대기 검증과 이번 파일 Gate의 순차 실행은 서로 다른 근거다.

이후 '70번을 선택한 뒤 71번이 먼저 Commit된 경우의 유효 확인 지점/확인 필요'와 '확인 응답의 false 뒤 새 글이 Commit돼 다음 GET이 true가 되는 것이 모순인지'를 두 문항으로 제시했다. [학습 자료 14절](../study-docs/confirmation-checkpoint-and-assignment.md#14-확인-저장-성공과-새-글의-확인-필요는-함께-성립한다)의 두 시점 설명을 적용하는 질문이다.

첫 질문에 사용자는 '잘 모르겠습니다. 70번 확인 200이 뜨고, 71번은 확인이 필요하다고 떠야 하지 않을까요?'라고 답했다. 70번까지만 확인하고 71번은 확인 필요로 남긴다는 방향은 맞다. 이 사례의 effectiveThroughMessageId는 70, needsConfirmation은 true다. 다만 질문은 새 확인이 201로 저장된 경우다. 이미 있는 고객 메시지 70번을 대상으로 하더라도 이번 UUID의 확인 기록은 처음 만드는 것이므로 201/추가 확인 Row 1건이다. 같은 제출이 이미 저장된 뒤 원래 내용으로 재확인한 경우의 200/0건과 구분해 설명했다. 이 답변을 두 필드와 HTTP 상태를 모두 정확히 설명한 것으로 기록하지 않는다.

둘째 질문에는 '아니요. Browser가 받은 201에 false가 뜬 이유는 needsConfirmation=false 를 읽은 것이고, GET의 true는 이후 71번 글 commit이 성공했음을 확인받은 것이니 모순이 없습니다.'라고 답했다. 두 응답의 기준 시점을 구분한 답변이다. GET이 새 글을 Commit하는 것이 아니라 이미 Commit된 새 글을 읽어 true를 반환한다는 점도 보충했다. 앞의 성공 응답이 그 뒤에도 새 글이 없을 것을 보장하지는 않는다.

## 테스트 자원 수명으로 진행

기존 미해결 항목이던 Surefire 종료 지연을 점검했다. 대표 3개 클래스의 자원 정리 검사가 수정 전에 실패하고 AFTER_CLASS 정리 뒤 통과하는 것을 확인한 다음, 같은 기본 통합 패턴 21개에 적용했다. 전체 Java 1,173건과 패키지 검증 2건이 통과했고 이번 실행의 종료 제한 경고/새 Dump는 0건이었다. [실행 보고서](../lab-reports/2026-11-04-test-jvm-cleanup.md)에 범위와 한계를 분리했다.

[학습 자료](../study-docs/test-jvm-resource-lifecycle.md)에는 업무 검사, Context/연결 Pool 정리와 JVM 종료를 구분해 설명했다. Codex가 수정/실행한 결과이며 사용자가 자원 수명까지 이해했다고 판정하지 않는다. 운영 앱의 종료 정책이나 저장된 업무 Row를 바꾼 작업도 아니다.

이후 고객 메시지 90번을 대상으로 유효한 새 UUID의 확인이 처음 Commit된 경우를 다시 질문했다. 사용자는 '201이고 추가되는 확인 Row는 1건입니다.'라고 답했다. 이미 있는 고객 메시지와 새로 만드는 확인 기록을 구분해 이번 사례의 상태/Row 수를 정확히 적용했다.

업무 테스트 60건이 통과해도 클래스 종료 뒤 Context/연결 Pool이 열려 있는 경우에는 '업무 계약 검증은 통과했지만 자원 정리는 완료되지 않았습니다.'라고 답했다. 업무 검증과 자원 정리를 분리한 판단이다. 이 두 답변을 모든 HTTP/자원 수명 경계의 이해나 사용자의 독립 구현 완료로 확대하지 않는다. 이번 문답 반영을 위해 테스트를 다시 실행한 것은 아니다.

## 상태의 의미와 변경 권한 합의

후속 대화와 확인 기능 다음의 구현 우선 과업은 상태 변경/재개 API다. 검토 시작 시점에는 메시지/답변/확인만으로 상태를 자동 변경하지 않는 원칙은 합의했고, 누가 어떤 조건으로 해결/재개할지는 미합의였다. [T01~T08 검토안](../../week11/customer-followup-policy-review.md#4-상태-변경-api-전에-정할-정책)을 기준으로 T01/T02부터 선택 이유를 설명하고 묶어서 검토했다.

- T01 권장안은 OPEN/IN_PROGRESS/RESOLVED를 유지하고 배정 유무와 처리 상태를 구분하는 것이다. 고객 답변 대기 같은 추가 상태는 진입/종료 조건과 표시를 정한 뒤 도입한다.
- T02 권장안은 일반 처리 시작/해결을 현재 담당자가 수행하고 지원관리자도 먼저 인계받는 것이다. 책임자와 상태 변경자를 맞추며, 고객의 명시적 재개와 관리자 긴급 예외는 별도로 검토한다.

사용자는 T01에 '기존 세 상태 유지 (권장)', T02에 '현재 담당자만 변경 (권장)'을 선택했다. 두 항목을 11/4 합의로 반영했다. 배정과 상태를 구분하고 책임자와 일반 처리 결정자를 맞추는 선택이며, 담당하기/인계만으로 상태를 바꾸지 않는다. 지원관리자도 먼저 현재 담당자가 되어 일반 처리 시작/해결을 수행한다.

두 답변은 서비스 운영 정책의 선택이다. 이해도 퀴즈의 정답이나 상태 API 구현 완료로 기록하지 않는다. 이 단계에서는 해결 근거/고객 확인, 재개, 버전/이력과 새 글의 경합 등 T03~T08이 남아 있었다. 최종 검증 안내, 주간 기록/회고와 출시 조건 역시 유지한다.

## 해결 후 재개와 해결 근거 합의

T03 검토에서는 등록자 본인 또는 현재 담당자가 별도의 재개 동작을 명시적으로 요청하면 RESOLVED를 OPEN으로 바꾸는 안을 권했다. 고객의 일반 글/AI 판단으로 자동 재개하지 않는다. 처리 재개가 곧 작업 시작을 뜻하지 않으므로 IN_PROGRESS로 바로 바꾸지 않고 기존 담당자/배정 버전은 유지하는 안이다. 담당자가 해결 처리를 바로잡는 경우도 후보에 명시했다.

T04 권장안은 관련 공식 답변, 해결 결과/사유와 담당자가 명시적으로 확인한 고객 범위를 남기고 담당자가 해결 처리하는 것이다. 고객의 추가 동의 응답을 필수로 기다리는 대신 고객에게 명시적 재개를 허용하는 안과, 고객 확인 후 담당자가 해결 처리하는 대안을 비교한다. 공식 답변/확인 Row가 있다는 사실만으로 문제 해결을 자동 판정하지 않는다. 새 글과 해결 요청의 경합 및 저장 조건은 T06과 후속 기술 계약에서 따로 구체화한다.

사용자는 T03에 '등록자와 현재 담당자의 명시적 재개 (권장)', T04에 '담당자 해결과 명시적 재개 (권장)'를 선택했다. 두 항목을 11/4 합의로 반영했다. 지원관리자는 먼저 담당자로 배정받고 일반 메시지로 자동 재개하지 않는다. 고객의 추가 동의 응답은 필수 조건으로 두지 않는다. 상태 API/재개 전이는 아직 구현하지 않았으며 T05~T08의 구체화와 기존 검증 정리/회고는 남아 있다.

## 다음 검토: 상태 변경 버전과 새 고객 글

T05는 배정 버전과 별개인 상태 버전을 두고 현재 상태/상태 버전/변경 이력을 하나의 Transaction으로 저장하는 안이다. 같은 담당자와 같은 상태 문자열로 돌아와도 중간의 해결/재개를 구분해야 한다. 예를 들어 IN_PROGRESS(3) → RESOLVED(4) → OPEN(5) → IN_PROGRESS(6)이라면 버전 3의 오래된 화면은 현재 버전 6과 다르다. 이력 저장 실패 시 새 상태도 Rollback하고 이미 Commit된 문의/답변은 유지한다. 이미 저장된 같은 UUID/요청 내용의 재확인은 추가 변경 없이 기존 결과를 반환하는 안이다. 기록이 없으면 유효한 새 저장이 가능한지는 별도로 검사한다.

T06은 해결 판단 뒤 새 고객 글이 먼저 Commit되면 오래된 해결 요청을 거부하고 다시 확인하게 하는 안이다. 고객 글 저장은 상태를 바꾸지 않으므로 상태 버전 비교만으로는 이를 찾을 수 없다. 해결 요청에 고정한 고객 범위를 최신 글/명시적 확인과 함께 검사하며 다른 창의 확인으로 옛 요청 범위를 자동 확대하지 않는다. 해결이 먼저 Commit됐다면 뒤의 새 글은 보존/확인 필요 표시를 유지하고 T03의 별도 재개를 허용하는 안으로 제시했다.

사용자는 T05에 '저장 흐름을 더 설명해주세요', T06에 '새 글 확인 후 다시 해결 (권장)'를 선택했다. T06을 합의로 반영하고 T05는 아직 미합의로 유지했다. 설명 요청을 기술 계약 승인이나 이해 완료로 기록하지 않는다.

[저장 순서 학습 자료](../study-docs/status-change-transaction-flow.md)에 이미 Commit된 문의 42/배정 버전 2/상태 버전 3의 가상 예시를 두었다. 현재 상태를 RESOLVED/4로 UPDATE하고 변경 이력을 INSERT한 뒤 함께 Commit한다는 흐름, 확인된 Rollback이면 IN_PROGRESS/3과 이력 0건이 되는 경우를 설명한다. 기존 문의/공식 답변 보존과 응답 유실 재확인도 구분한다. 이 수치는 새 구현/실험 결과가 아니다.

기존 Lab TicketAssignmentService 전체를 읽고 @Transactional이 있는 public claim/transfer에서 현재 배정 변경과 이력 추가를 수행하는 구조를 참고했다. 새 상태 Service를 구현하거나 테스트한 것은 아니다. 두 버전과 한 Transaction의 의미를 이해하는 문답부터 진행하며 T07/T08은 그 뒤에 검토한다.

설명 뒤 이력 INSERT 실패/확인된 Rollback의 최종 상태/버전/이력 수와, 같은 담당자에서 해결/재개 두 번을 Commit했을 때 배정 버전 5/상태 버전 8이 어떻게 되는지를 묶어서 질문했다.

사용자는 첫 질문에 'IN_PROGRESS, 상태 버전 3, 새 이력은 0건입니다.', 둘째에 '최종 배정 버전은 5, 최종 상태 버전은 10입니다.'라고 답했다. 두 답변 모두 권장안의 저장 경계와 별도 버전을 정확히 적용했다. 이 사례 풀이를 T05 정책 동의나 모든 실패 경계의 이해로 확대하지 않는다.

## 마지막 상태 정책 묶음: T05/T07/T08

T05는 설명한 별도 상태 버전/현재 상태와 이력의 한 Transaction/이미 저장된 같은 제출의 재확인을 저장 계약으로 확정할지 별도로 확인한다. T07은 첫 상태 API를 일반 처리 시작/해결/명시적 재개로 두고 취소/중복/Spam을 해결과 혼합하지 않으며 무응답 자동 해결/자동 병합/자동 삭제를 제외하는 안이다. 취소나 중복 처리도 첫 버전에 필요하다면 종료 사유/권한을 추가로 설계해야 한다.

T08은 문의 처리 상태, AI Job과 담당자 검토 상태를 구분하고 조회 200/AI 성공만으로 해결 표시를 하지 않는 안이다. 고객에게 내부 Provider 오류/인계 사유를 그대로 공개하거나 아직 정하지 않은 응대 시간을 약속하지 않는 원칙도 함께 검토한다. 알림 전달 상태는 실제 알림을 구현할 때 따로 다룬다. 이 단계에서는 세 항목의 선택을 기다렸다.

사용자는 T05에 '설명한 저장 계약에 동의 (권장)', T07에 '일반 상태 처리부터 구현 (권장)', T08에 '구분 표시와 공개 원칙에 동의 (권장)'를 선택했다. 이해 점검과 별도로 받은 정책 선택이며 T01~T08을 모두 합의로 반영했다. 고객 재개/직원 상태 변경의 입력과 공개 범위를 나누고, 배정/상태의 두 버전과 이력의 Commit 경계를 기술 계약으로 구체화한다.

다음 구현은 기존 계층/인증/CSRF/원문/AI 보존 경계 안에서 V13, Domain, 저장 Port/Adapter, Service와 HTTP를 작은 단위로 진행한다. Lab docs/ticket-status.md에 입력/권한/오류/재확인 및 기술 결정과 후속 검토를 기록한다. 운영 리소스나 실제 외부 AI를 변경하는 승인은 아니며 실행 결과와 실제 학습 이해는 별도 기록한다.

## 상태 저장과 화면 구현 뒤 확인

Codex는 합의한 V13/Service/API와 상태 화면을 작은 단위로 구현했다. 저장/Domain 15건과 HTTP 45건, Node 전체 418건/Lint 및 새 실제 Browser와 기존 Browser 두 건을 검증했다. [실행 보고서](../lab-reports/2026-11-04-ticket-status.md)에 전체 회귀의 최종 결과를 별도로 기록한다. 이 테스트는 사용자가 작성/실행한 것으로 기록하지 않는다.

첫 질문은 UUID의 해결 이력이 상태 버전 2로 저장된 뒤 재개돼 현재 OPEN/3인 상태에서, 같은 제출 재확인의 추가 이력 수와 현재 화면 상태를 묻는 것이었다. 사용자는 '추가 이력 Row 수는 2건(RESOLVED->OPEN, 상태 버전 2 -> 3), 화면의 현재 문의 상태는 OPEN 일 것 같습니다.'라고 답했다. 현재 OPEN 판단은 맞다. 다만 해결/재개 이력은 이미 Commit됐으므로 이번 재확인이 추가하는 이력은 0건이다. 기존 이력 수와 이번 요청의 추가 Row 수를 나누어 보충했다.

둘째 질문은 70번까지 고른 해결 요청 뒤 71번 고객 글과 다른 창의 71번 확인이 먼저 저장됐을 때, 서버가 요청 대상을 71번으로 자동 변경해도 되는지를 묻는 것이었다. 사용자는 '오래된 해결 요청의 대상은 명시적 승인이 있지 않는 이상 함부로 저장하면 안 될 것 같고, 저장하더라도 71번이 아니라 72번이나 그 이후의 사용되지 않은 번호로 저장하는 것이 맞을 것 같습니다.'라고 답했다. 자동 저장을 경계한 방향은 맞지만 기존 고객 글 참조와 새 상태 이력의 ID를 혼동했다.

해결 요청의 throughCustomerMessageId는 이미 있는 고객 글의 번호이며 새 Message 번호를 배정하는 값이 아니라고 설명했다. 오래된 요청은 거부하고 담당자가 71번을 읽고 새 해결을 결정하면 기존 71번을 참조하는 새 UUID의 요청을 보낸다. 상태 이력의 ID는 DB가 따로 만든다. [저장 흐름 자료 10절](../study-docs/status-change-transaction-flow.md#10-고객-글-번호와-상태-이력-번호를-구분하기)에 네 식별자의 역할을 나눠 두었다.

보충 뒤 '기존 K의 해결과 재개가 이미 저장된 경우 재확인의 추가 이력 수'와 '80/81번 고객 글이 있고 82번이 없을 때 새 해결의 참조'를 두 문항으로 다시 제시했다.

사용자는 첫 질문에 '추가 상태 이력 Row는 0건입니다.', 둘째에 'throughCustomerMessageId에는 이미 저장된 81번을 넣고, 새 상태 변경 이력의 ID는 DB가 별도로 생성합니다.'라고 답했다. 이번 두 사례에서 기존 제출 재확인의 추가 Row 수와 기존 고객 글 참조/새 이력 ID를 정확히 구분했다. 앞선 혼동/보충 과정을 지우지 않고 이해 변화로 기록하며, 독립 구현이나 전체 상태 기능의 이해 완료로 확대하지 않는다.

다음은 실제 TicketStatusService의 현재 조회 권한 검사, 기존 제출 재확인과 새 변경의 버전 검사 순서다. [저장 흐름 자료 11절](../study-docs/status-change-transaction-flow.md#11-현재-조회-권한과-새-변경-조건은-다르다)에 연결했다. 상태 문자열이 같아져도 오래된 새 요청은 거부하는 경우와, 현재 canResolve가 false여도 저장 여부 미확인인 과거 제출을 재확인하는 경우를 다음 문답으로 둔다. 이번 기록 보완으로 코드를 수정하거나 테스트를 다시 실행한 것은 아니다.

사용자는 상태 문자열이 같아도 '상태 버전이 1과 4로 다르므로 충돌로 거부해야 합니다'라고 답했다. 이미 저장된 K의 재확인에는 '조회 권한이 유지되고 이미 저장된 제출이므로 원래 UUID와 내용으로 재확인해 추가 이력 없이 기존 결과를 반환해야 합니다'라고 답했다. 새 요청의 상태 버전 검사와 기존 제출 재확인, 새 해결 가능 여부와 과거 결과 조회를 이번 두 사례에서 정확히 구분했다.

## Service 반환과 Commit의 순서로 진행

다음은 [저장 흐름 자료 12절](../study-docs/status-change-transaction-flow.md#12-service-본문의-return과-controller가-결과를-받는-시점)을 기준으로 Service 본문의 return과 Spring 트랜잭션 처리가 끝나 Controller가 결과를 받는 시점을 구분한다. TicketStatusController의 실제 호출/응답 코드, TicketStatusService의 공개 @Transactional 메서드와 기존 지연 Commit 실패 테스트의 해당 부분을 확인했다. Spring 공식 문서의 프록시/트랜잭션 설명도 대조했다. 코드 변경이나 새 테스트 실행은 없으며, 현재 1,221+2 등의 수치는 앞선 실행 보고서의 근거다.

질문은 두 가지다. 첫째는 Service 본문이 반환한 뒤 Commit이 실패한 경우 Controller의 Service 호출이 정상 완료됐는지다. 둘째는 Commit 성공 후 응답 처리에서 500이 발생한 별도 가상 상황에서 새 UUID로 자동 제출해도 되는지다. 기존 검증에서 확인한 Rollback과 가상 상황/Browser에서 저장 여부를 모르는 경우를 구분한다.

사용자는 첫 질문에 '아니요. Commit이 실패했으므로 호출이 정상 완료된 것이 아니며 201을 반환하면 안 됩니다.', 둘째에 '아니요. 원래 UUID와 요청 내용을 유지해 재확인하고 실제 DB 저장 여부를 확인해야 합니다.'라고 답했다. 이번 두 사례에서 Service 본문의 반환/Commit 성공과 Browser의 오류/DB 저장 여부를 정확히 구분했다. 실제 테스트의 새 실행이나 모든 장애 경계의 이해 완료로 확대하지 않는다.

## Ticket 잠금과 서로 다른 변경 검사로 진행

[저장 흐름 자료 13절](../study-docs/status-change-transaction-flow.md#13-ticket-잠금과-버전은-무엇을-각각-보호하는가)에 같은 Ticket의 상태 처리/고객 글 저장 순서, 상태 버전/배정 버전/고객 글 참조의 역할을 연결했다. JdbcTicketStatusRepository 전체와 Service의 잠금 뒤 새 조회, 고객 후속 글의 부모 Ticket 잠금 연결부, 기존 두 Commit 순서 테스트의 해당 부분을 확인했다. PostgreSQL 17 공식 문서의 Row Lock/Read Committed 설명도 대조했다. 기존 구현/검증을 설명하는 작업이며 코드를 변경하거나 PostgreSQL/Browser 테스트를 다시 실행하지 않았다.

다음 두 문항은 상태 버전이 그대로인 동안 새 고객 글이 먼저 Commit된 경우의 해결 조건과, 해결이 먼저 Commit된 뒤 도착한 새 고객 글의 처리다. 답변을 확인한 뒤 상태 기능의 통합 개념 점검을 마무리하고 주간 계획의 실행 안내/검증 근거 대조와 마감 기록으로 진행한다. 아직 이 두 경합 사례의 이해 완료로 판정하지 않는다.
