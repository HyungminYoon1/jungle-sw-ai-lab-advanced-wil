# 11/4 학습 기록: 인계와 명시적 확인 범위

> 회차: 2026-11-04
> 범위: 직원 업무 표시와 확인 버튼. [주간 계획](../weekly-plan.md)의 11/4 과업
> 구현/실행은 Codex가 진행했으며 학습자의 이해와 구분한다.

## 질문과 실제 답변

| 질문 | 사용자 답변 | 확인할 점 |
|---|---|---|
| A가 배정 1에서 30번까지 확인한 뒤 B/배정 2로 인계. B는 아직 확인 버튼을 누르지 않은 상태의 표시 | 'B도 30번까지 확인' | 현재 F11 계약과는 다름. 다만 승계 여부는 설계 선택이므로 보편적인 오답으로 다루지 않고 값의 의미부터 설명해야 함 |
| 30번을 선택한 뒤 저장 직전에 새 고객 글 31번 도착. 30번 확인 저장으로 31번도 포함할 수 있는지 | '잘 모르겠습니다.' | 명시한 대상 30만 저장. 31번은 확인 필요로 남김 |

## 보완한 설명

이 기록은 문의에 대한 누구의 확인이든 합쳐 놓은 공통 진행률이 아니다. 현재 담당자가 명시적으로 확인한 범위다. A의 '30번까지 확인했다'를 B에게 옮기면 B가 아직 남기지 않은 확인을 서버가 대신 기록하는 셈이다. 인계는 책임 담당자를 바꾸고 확인은 해당 담당자의 선언을 남기는 서로 다른 작업이다.

따라서 A/배정 1의 기록은 남기고 B/배정 2의 유효 확인 지점은 NULL로 둔다. 이는 과거 이력이나 고객 글을 삭제했다는 뜻도, B가 실제로 읽지 않았다는 증명도 아니다. B의 명시적 기록이 없다는 뜻이다.

30번을 선택한 뒤 도착한 31번도 마찬가지다. 담당자가 읽었는지 확인하지 않은 새 글까지 자동 포함하지 않는다. 선택한 throughMessageId와 그때의 expectedAssignmentVersion을 함께 보관하고 서버는 그 범위만 검사/저장한다. HTTP 201/Commit 성공도 명시한 기록이 저장됐다는 뜻이며, 그 사이 도착한 모든 글을 확인했다는 뜻은 아니다.

## 재확인과 다음 학습

설명 후 두 변형을 묶어서 제시했다.

1. A가 50번까지 확인한 뒤 B에게 인계했을 때 A의 과거 이력과 B의 현재 표시를 어떻게 나눌지
2. 12번을 선택한 뒤 아직 읽지 않은 새 글 13번이 왔을 때 저장할 범위

첫 질문에 사용자는 '우선 올바른 개념을 설명해주세요.'라고 요청하며, 보편적인 정답이 아니라 설계 차이라면 대안의 차이와 선택 이유부터 설명해야 한다고 지적했다. 둘째 질문에는 '잘 모르겠습니다.'라고 답했다. Codex가 현재 F11과 보편적인 원리를 먼저 나누지 않고 정답처럼 질문한 점을 바로잡고 추가 문답은 잠시 멈췄다.

공식 Twilio/Matrix 자료에서 참여자/사용자별 읽기 위치를 확인했다. 이를 모든 Helpdesk의 인계 규칙으로 확대하지 않고, 팀 공통/사람별/배정별 세 설계 대안을 비교했다. 현재의 한 명 책임 담당자/명시적 인계 목적에는 배정별 확인을 유지하는 안을 추천한다. 팀 공통 50을 유지하는 설계도 가능하지만 그 값을 B 개인의 확인이라고 부르지는 않아야 한다. 이전 담당자 지점을 현재 화면과 함께 보여주는 것은 아직 구현하지 않은 보완안이다.

12/13 사례는 버튼이 선택한 범위를 확인하는 명령인지, 서버의 최신 수신 범위를 일괄 처리하는 명령인지부터 설명한다. 현재 버튼은 12번의 명시적 확인이므로 13번은 새 확인 필요로 남긴다. 13번을 자동 포함하면 새 고객 글의 확인 필요가 사라질 수 있다는 구체적인 영향으로 설명했다.

이 시점에는 설명과 비교 자료를 보완한 단계다. 두 구분을 이해했다고 판정하지 않으며 추가 설명/확인은 이후 실제 답변을 받아 갱신한다. 합의한 F11 정책이나 코드의 배정별 범위를 사용자 학습 답변만으로 변경하지 않는다.

[학습 자료](../study-docs/confirmation-checkpoint-and-assignment.md)에는 두 ID/MAX와 인계 예, 실제 화면에서의 선택/Commit 절차를 두었다. [11/4 검증 보고서](../lab-reports/2026-11-04-staff-confirmation-ui.md)의 Test/Row/화면은 코드 동작의 근거이며 위 이해 점검을 대신하지 않는다.

## 저장/조회 실패 학습으로 진행

사용자는 설계 비교 설명 뒤 '좋습니다. 이해했습니다. 다음 단계 학습을 진행해주세요'라고 말했다. 설명을 이해했다는 본인 표현으로 기록한다. 독립적인 새 사례 풀이를 확인한 결과로 바꾸지는 않는다.

다음에는 확인 저장의 POST와 현재 상태 조회 GET을 나누었다. 유효한 201을 받은 뒤 GET만 실패하면 조회만 재시도하고, POST 응답 자체가 없으면 원래 UUID/대상/배정 버전으로 저장 결과를 재확인한다고 설명했다. 이 둘을 구분하는 질문을 묶어서 제시했다.

사용자는 첫 질문에 'GET만 다시 보냅니다. 확인 저장은 이미 성공했기 때문입니다', 둘째에는 '아니요. 원래 UUID·배정 버전·대상으로 저장 결과를 재확인합니다'라고 답했다. 두 실패 경계를 적용한 선택으로 확인했다.

기존 Node Test Double에 더해 실제 Browser에서 서버의 Commit 완료 응답을 중계 지점에서 차단하는 재현을 진행했다. [실제 Browser/DB 검증](../lab-reports/2026-11-04-confirmation-recovery-browser.md)은 서버 POST 201/200/201과 최종 확인 Row 2건, 원래 제출의 유지와 GET만 재시도하는 화면을 확인했다. 사용자 답변은 별도로 기록한다. 이 설명/실행을 근거로 현재 F11 정책이나 원문/AI 보존 계약을 바꾸지는 않는다.

## 인계와 권한 회수 후의 재확인

현재 서비스 조회 권한을 먼저 검사하고, 기존 UUID의 저장 결과 재확인과 새 확인 쓰기를 구분하는 Service 순서를 설명했다. 인계는 새 쓰기의 담당자를 바꾸지만 활성 직원의 기존 결과 조회 권한까지 없애지는 않는다. 서비스 권한 회수는 기존 결과를 새로 조회하는 것도 막되 이미 Commit된 이력을 삭제하지 않는다.

사용자는 인계 뒤 A가 활성 서비스 직원으로 남은 경우 '기존 결과만 반환하고 B의 확인 기록은 만들지 않습니다'라고 답했다. A 권한 회수 Commit 뒤 새 요청을 시작한 경우에는 '조회를 거부하되 기존 확인 기록은 보존합니다'라고 답했다. 현재 계약을 구분해 적용한 선택으로 확인했다.

[실제 Browser/DB 검증](../lab-reports/2026-11-04-confirmation-authority-browser.md)에서는 기존 Session의 과거 재확인 200, 새 쓰기 403과 회수 후 재확인 404, 남은 A의 기록 한 건을 대조했다. 권한 회수는 검증한 격리 DB의 테스트 장치에서만 실행했다. 이 결과를 사용자의 독립 구현이나 모든 정책/잠금 경합의 이해 완료로 기록하지 않는다.

다음에는 A가 다시 담당자가 된 배정 3에서 같은 대상까지 새로 확인하는 상황을 설명했다. 과거 UUID/배정 1의 제출 재확인과 현재 배정 3의 새 확인은 다른 명령이다. 원래 UUID의 버전만 바꾸는 재사용과, 버전 충돌 뒤 자동 최신화/재전송을 피해야 하는 기존 계약을 기준으로 두 문항을 제시했다.

사용자는 첫 질문에 '배정 3에서 범위를 다시 선택하고 새 UUID로 확인을 제출합니다', 둘째에는 '현재 배정을 조회하고 사용자가 확인 범위를 다시 선택하게 합니다'라고 답했다. 새 배정의 확인과 충돌 뒤 재선택을 현재 계약에 맞게 구분했다. 이 답변을 독립 구현이나 모든 실패 경계의 이해 완료로 확대하지 않는다.

[재선택 UI 검증](../lab-reports/2026-11-04-confirmation-reselection-ui.md)에서는 알려진 배정 버전 충돌에만 명시적 재선택을 연결했다. 실제 A→B→A 뒤 오래된 제출의 409, GET만 하는 초기화와 빈 선택, 새 UUID/배정 3의 201을 Browser/PostgreSQL로 대조했다. HTTP 409만 있거나 오류 Body를 읽지 못하면 결과 미확인 제출을 그대로 보관한다.

## 다음 확인: 같은 제출의 결과와 현재 상태

응답을 잃은 뒤 같은 UUID로 재확인해도 반드시 200인 것은 아니다. 서버에 기존 기록이 없고 현재 쓰기 조건이 모두 유효하면 새로 저장해 201이 될 수 있다. 또한 현재 확인 지점의 GET은 여러 제출에서 계산한 상태이므로 특정 UUID의 저장 증거와 다르다. [학습 자료 10절](../study-docs/confirmation-checkpoint-and-assignment.md#10-저장-성공-뒤-조회-실패와-저장-여부-미확인)의 설명을 바탕으로 이 두 구분을 문답으로 확인했다.

사용자는 첫 요청이 서버에 도착하지 않은 K를 재확인해 처음 저장한 경우 '201이고 추가 확인 Row는 1건입니다.'라고 답했다. 현재 GET의 30번으로 K의 저장을 확정할 수 있는지에는 '아니요. 다른 UUID로 같은 30번까지 확인한 기록일 수 있기 때문입니다.'라고 답했다. 두 답변은 현재 계약에 맞다. 재확인의 가능한 첫 저장과 상태 집계/특정 제출의 증거를 구분한 답변으로 기록한다.

## 공식 답변의 오래된 초안으로 적용

다음에는 `draftVersion`과 `pending`을 구분했다. 전자는 답변을 시작한 배정이고 후자는 이미 저장됐을 수도 있는 제출이다. 미제출의 확인된 버전 차이나 정확한 배정 충돌에는 사용자의 명시적 초안 폐기/GET/새 작성을 제공하고, 결과 미확인 제출은 먼저 원래 정보로 재확인하도록 했다. [학습 자료 13절](../study-docs/confirmation-checkpoint-and-assignment.md#13-공식-답변-초안과-결과-미확인-제출)과 [실제 검증](../lab-reports/2026-11-04-reply-draft-review.md)에 코드와 관찰을 나눠 남겼다.

실제 Browser의 최초 실패에서 저장 후 정정 후보 목록까지 비워 다음 정정을 선택할 수 없는 문제를 찾았다. 재현하는 Node 검사를 추가하고 현재 선택만 비우도록 수정한 뒤 통과했다. Codex가 구현/실행한 결과이며 사용자의 직접 문제 발견이나 수정으로 기록하지 않는다.

배정 3에서 저장/응답 유실 후 배정 5의 재확인 200이 만드는 추가 Row와 저장 버전, 그리고 명시적 초안 폐기 뒤 GET 503에서 새 POST를 허용할지를 두 문항으로 제시했다.

사용자는 첫 질문에 '추가 Row는 0건이고 저장 배정 버전은 3입니다.'라고 답했다. 둘째에는 '아니요. 현재 배정을 다시 조회해 담당자·배정 버전·작성 권한을 확인해야 합니다.'라고 답했다. 과거 저장 결과의 재확인이 당시 기록을 바꾸지 않는다는 점과, 초안 초기화가 새 작성 권한을 보장하지 않는다는 점을 현재 계약에 맞게 구분했다.

## 새 고객 글과 상태를 읽은 시점

다음 계획의 교차 실행을 검토하니 새 글/확인, 인계/확인과 권한 회수의 두 Commit 순서는 이미 서버의 실제 PostgreSQL 테스트와 이전 보고서에 있었다. 이를 미구현으로 보아 새 업무 로직을 추가하지 않고, 확인 대상을 선택한 뒤 고객 글이 도착하는 Browser 순서 한 가지를 강화했다.

[새 검증](../lab-reports/2026-11-04-confirmation-cross-flow.md)은 선택한 1번의 확인 201과 별개로 2번을 확인 필요로 남기는 화면/DB를 대조했다. 대화를 다시 읽어 2번을 표시해도 자동 선택/확인하지 않았다. 기존 서버의 Lock 대기 검증과 이번 파일 Gate의 순차 실행은 서로 다른 근거다.

이후 '70번을 선택한 뒤 71번이 먼저 Commit된 경우의 유효 확인 지점/확인 필요'와 '확인 응답의 false 뒤 새 글이 Commit돼 다음 GET이 true가 되는 것이 모순인지'를 두 문항으로 제시했다. [학습 자료 14절](../study-docs/confirmation-checkpoint-and-assignment.md#14-확인-저장-성공과-새-글의-확인-필요는-함께-성립한다)의 두 시점 설명을 적용하는 질문이다. 이 기록 시점에는 답변 대기다.
