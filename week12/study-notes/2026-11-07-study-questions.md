# 11/7 검증 결과에서 저장 여부 읽기

Lab 코드 기준은 `fe9336d`다. 권한, 동시 저장, Rollback, 응답 유실, 기존 데이터 보존을 실제 테스트의 검사 조건과 보관된 실행 결과에 연결했다. 사용자는 같은 Ticket의 저장 순서와 Commit 실패 및 응답 유실의 차이를 이해했다고 답했다. 보존과 접근 권한의 마지막 문답까지 마쳐 11/7 학습 범위를 완료했다.

## 같은 Ticket의 저장 요청이 겹치는 경우

고객 후속 글 A의 요청이 먼저 도착해도 Commit까지 끝나기 전에 담당자 답변 B의 요청을 처리하기 시작할 수 있다. 두 요청은 같은 Ticket에 서로 다른 Message 행을 추가한다.

1. A가 Ticket 행의 잠금을 얻고 고객 글을 INSERT한다.
2. A가 아직 Commit하기 전이면 B는 같은 Ticket의 `SELECT ... FOR UPDATE`에서 기다린다.
3. A가 Commit해 잠금을 풀면 B가 잠금을 얻는다.
4. B는 현재 담당자와 배정 버전 등 작성 요건을 검사하고, 유효하면 자신의 첫 INSERT와 Commit을 진행한다.

이 예에서 B의 대기는 첫 INSERT 전에 발생한다. 테스트는 B의 PostgreSQL 연결이 A의 잠금에 막혀 있는지, 대기 중인 SQL이 Ticket의 `FOR UPDATE`인지, B의 INSERT 호출이 아직 0회인지 확인한다. 작성 중 인계처럼 계약 검사 결과에 영향을 주는 변경이 있으면 잠금을 얻은 뒤 최신 상태에 따라 판단한다.

## 같은 확인 POST에서 실패 지점이 달라지면

첫 번째 사례는 INSERT 뒤 Commit에서 PostgreSQL이 쓰기를 거부한다. 테스트는 500과 저장 전후 DB 대조를 함께 사용해 새 확인이 추가되지 않았음을 확인한다.

두 번째 사례는 Commit 뒤 201의 전달만 끊긴다. 화면에서는 저장 결과를 알 수 없다. 원래 제출의 재확인 응답과 DB의 제출 UUID를 연결하면 이미 저장된 한 건을 확인할 수 있다. 현재 확인 지점을 반환하는 GET은 조회 시점의 집계를 보여준다.

## 첫 이해 점검

1. 테스트에서 두 번째 요청이 첫 번째 요청에 막힌 것은 확인했지만, 대기 중인 SQL은 이미 `INSERT`였다. 이 관찰로 두 번째 요청이 INSERT 전에 Ticket 잠금을 기다렸다고 결론 내릴 수 있나? 어느 지점의 SQL을 관찰해야 할까?
2. 상태 변경 POST가 500을 반환했다. 새 상태와 이력이 함께 Rollback됐다는 결론을 검증하려면 어떤 DB 값을 요청 전후에 비교해야 할까? 기존 문의와 AI 제안도 보존됐다는 주장은 어떤 비교로 뒷받침할 수 있을까?

사용자는 먼저 도착한 요청이 끝나기 전에 다른 요청이 어떻게 저장을 시도하는지, 두 번째 요청을 재시도해야 하는지 질문했다. 상태 변경 전후의 상태를 비교하자고 답했고, 500을 받았을 때의 저장 단계도 물었다. 두 요청의 실행 시간이 겹치는 예로 첫 Commit까지 두 번째 요청이 `FOR UPDATE`에서 대기하는 흐름을 설명했다. 상태 버전과 제출 UUID에 해당하는 이력, 이미 저장된 업무 데이터까지 비교하는 방법을 짚었다. 사용자는 설명 뒤 같은 Ticket의 저장 순서와 두 실패의 차이를 이해했다고 확인했다.

## 보존과 접근 권한을 검증하는 방법

해결 요청이 성공하면 `tickets`의 현재 상태와 상태 버전이 바뀌고 `ticket_status_events`에 새 이력이 남는다. 정상 흐름의 `preserved()`는 이 두 테이블을 제외한 DB 행을 비교한다. 상태와 버전, 이력 건수는 별도 검사를 사용한다. 이력 INSERT 직후 실패시키는 보존 테스트는 합성 AI 제안을 미리 저장하고 `snapshot()`으로 두 테이블까지 포함한 전후 행을 비교한다. Job의 최초 문의 참조나 제안 내용이 달라지면 행 수가 같아도 이 비교는 실패한다. [상태 변경 검증](../lab-reports/2026-11-04-ticket-status.md)

권한 회수 Browser 실험은 같은 Session에서 CSRF 조회 200과 같은 제출의 재확인 404를 관찰했다. 회수 전의 재확인은 200이었다. 테스트는 별도 SQL로 회수 전후의 확인 이력 전체 행도 비교했다. HTTP 결과로 요청 시점의 접근 제어를, DB 결과로 기존 저장 기록의 보존을 확인했다. [권한 실험](../lab-reports/2026-11-04-confirmation-authority-browser.md)

1. 해결 요청은 201이고 상태 버전과 새 이력도 정상이다. 기존 문의 본문과 AI 제안 건수는 그대로인데, Job의 `input_message_id`가 최초 문의 80번에서 후속 글 81번으로 바뀌었다. 보존 테스트를 통과시켜도 될까? 어떤 값을 대조해야 이 문제를 찾을 수 있을까?
2. 같은 Session에서 A의 재확인이 권한 회수 전에는 200이었다. 회수 뒤 CSRF 조회는 200, 재확인은 404다. DB에서는 확인 이력 건수가 전후 모두 1건이라는 사실만 확인했다. 접근 차단과 기존 기록 보존을 각각 어떻게 판정할까? 보존을 판정하려면 무엇을 더 비교해야 할까?

사용자는 1번에서 참조 대상 변경을 매핑 문제로 판단했다. `input_message_id`의 직접 참조 대상은 Message이며, 두 Message가 같은 Ticket에 속해도 최초 문의의 참조를 바꾼 것이므로 보존 검사에서 거부해야 한다고 보충했다.

2번에서는 접근 차단은 성공이고, A가 조회만 시도했으므로 기록 보존에도 문제가 없을 것이라고 답했다. 앞선 설명의 '재확인'은 원래 UUID와 내용을 같은 POST로 다시 보내는 흐름이었다고 명확히 했다. 같은 통제 조건의 HTTP 결과는 서비스 접근 차단을 뒷받침하고, 보존 여부는 기존 확인 행의 ID/UUID/작성자/배정 버전/대상 등 값의 전후 대조로 확인한다. 실제 Browser 실험은 해당 확인 테이블의 전체 행을 SQL로 비교했다. 건수만 같은 결과에서 행 값의 동일성까지 추론한 부분을 설명하고 마지막 질문으로 확인했다.

마지막 확인 질문은 같은 제출의 재확인이 404로 거부되고 별도 SQL 대조에서 기존 확인 행 전체가 이전과 같을 때, 접근 차단과 기록 보존을 각각 어떤 근거로 판정하는지다. 사용자는 '별도 SQL로 기존 확인 행 전체가 전후 동일하다는 것을 확인한 것이 직접 근거'라고 답했다. 기록 보존의 직접 근거를 정확히 구분했다.
