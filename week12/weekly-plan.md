## 계획 배경

공식 답변, 대화 조회와 담당자 배정/인계는 기존 V10 구현과 검증 기록이 있다. 11/3에는 F03/F05/F12/F13과 공개 대화 활동 시각을 합의하고 기술 계약을 작성했다. 이어서 V11 고객 대화/목록/작성과 V12 명시적 확인 저장/API를 로컬 구현/검증했다. 11/4에는 직원 업무 표시와 직접 고른 Message까지 확인하는 버튼을 실제 Browser/PostgreSQL로 연결했다. 학습 이해와 원격 CI/운영 배포는 이 로컬 결과와 구분한다.

11/3 작성자는 지난주 학회 참석으로 학습과 구현을 진행하지 못했다고 설명하고, 11/9까지 휴무일 없이 학습하기로 했다. 10/27까지의 정책 합의는 보존하며 이어서 진행하지 못한 과업을 이번 일정에 반영한다. 기존 12주차의 최종 회고와 다음 단계 정리도 함께 수행한다.

## 시간 배분과 학습 방식

취업 활동과 면접 일정을 우선하며 기술 과업은 이번 7일 전체에 합쳐 6시간 이내를 기준으로 둔다. 정책 검토, 개념 설명, 코드 검토, 구현/실행과 문서 정리를 함께 계산한다. 실제 사용 시간은 회차별로 기록하고 계획 시간을 실적처럼 적지 않는다.

배분은 작업량 추정과 별개인 시간 상한 내의 목표다. 정책 미합의나 구현/검증 지연이 생기면 다음 작업으로 순서대로 넘긴다. 11/8~9의 검증 정리와 회고 시간을 확보하고 미완료 기능은 부분 완료 또는 후속으로 남긴다. 이미 선택한 필수 검증을 생략하거나 F11을 표시만 하는 기능으로 축소해 완료 처리하지 않는다.

매 회차에는 짧은 복습과 핵심 질문 2~3개, 필요한 설계 선택, 작은 구현과 Test, 결과 해석 순으로 진행한다. Codex는 기존 계층과 합의 범위 안에서 기술 계약과 반복 작업을 구체화한다. 사용자는 소유권, 공개 범위, 상태 변경, 데이터 보존과 실패 처리의 의미를 검토한다.

## 핵심 검증 사례

1. 고객은 자기 문의에만 후속 글을 작성한다. 다른 고객과 비등록자 직원의 작성, 작성자/서비스/상태 등 허용하지 않은 필드는 거부한다.
2. 새 제출은 Commit 후 201, 동일 제출 재확인은 200/추가 Row 0, 같은 키의 다른 종류나 내용은 409로 구분한다. 고객 후속 글과 공식 답변의 제출을 혼동하지 않는다.
3. 같은 Ticket의 고객 글과 직원 답변을 함께 실행해 저장/조회 순서를 확인한다. 새 저장과 관련 이력의 확인된 Rollback은 기존 문의, 답변, 배정과 AI Row를 취소하지 않는다.
4. POST 결과 미확인은 원래 제출을 유지해 확인하고, 저장 성공 뒤 GET 실패는 GET을 재시도한다. 다른 Ticket이나 이전 조회의 늦은 응답은 화면에 반영하지 않는다.
5. 후속 글로 새 AI Job/예약/호출을 만들지 않고 최초 문의 입력과 제안을 유지한다. 요약/분류/우선순위가 최초 문의 기준임을 표시한다. 독립적으로 진행 중인 기존 Job의 처리는 별개다.
6. 확인은 현재 담당자와 배정 버전, 같은 Ticket의 고객 Message ID를 검사한다. GET은 확인을 기록하지 않고, 이미 확인한 지점은 같은 배정 안에서 후퇴하지 않는다.
7. 71번 확인 뒤 도착한 72번은 확인 필요로 남는다. 인계와 A→B→A 재배정에서 과거 확인을 새 배정의 확인으로 복사하지 않는다. RESOLVED의 새 글도 발견할 수 있어야 한다.
8. 내 문의 목록도 서버에서 본인 범위를 제한하고 문의 번호/제목/상태/최근 활동을 표시한다. 마지막 공개 Message의 작성 시각을 사용하며 인계/확인만으로 활동을 갱신하지 않는다. 가변 정렬/페이지 조회는 누락 없는 처리 원장으로 해석하지 않는다.

전체 Case와 기존 P1~P8/O1~O6 회귀는 [후속 정책 검토의 검증 사례](../week11/customer-followup-policy-review.md#후속-메시지-구현의-최소-검증-사례)와 연결한다. Test 개수만으로 학습이나 기능 완료를 판정하지 않는다.

## 기록과 변경 전달

- 계획과 정책 선택은 이 계획 및 기존 정책 검토에 누적한다. 정책 한 항목마다 새 Commit을 만들지 않는다.
- 구현은 저장 API, 고객 화면, 확인 기능과 통합 검증처럼 검토 가능한 단위로 나누고 관련 Test와 함께 Commit한다.
- Study Note는 실제 문답, Lab Report는 실행 조건/관찰, 주간 기록은 이해 변화와 미완료 사항을 중심으로 작성한다. 아직 없는 산출물의 링크는 만들지 않는다.
- 최종 변경은 Diff와 공개 내용을 검토하고 승인된 전달 범위에서 Push/정확한 Commit의 CI를 확인한다. 로컬 통과와 원격 CI를 분리한다.
- 10~12주차 블로그는 통합 한 편의 초안을 작성한다. 실제 발행/포럼 제출은 작성과 구분해 기록한다.
