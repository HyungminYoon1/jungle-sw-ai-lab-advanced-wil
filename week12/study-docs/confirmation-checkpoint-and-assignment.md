# 확인 기록 번호와 '어디까지 확인했는지' 구분하기

> 작성일: 2026-11-03
> 범위: F11 담당자의 명시적 확인. [기술 계약](../customer-followup-contract-draft.md) 5~6절의 설명
> 구현: Lab 80e5de9/6b3ba1d, V12 확인 기록/API. 직원 목록 표시와 확인 버튼은 다음 단위

## 1 이 기능이 기록하는 것

현재 담당자가 '이 고객 메시지까지 확인했습니다'라고 명시적으로 남기는 기록이다. 대화를 GET하거나 화면을 열기만 해서는 기록하지 않는다. 담당자가 실제로 무엇을 읽고 이해했는지 서버가 알아내는 기능도 아니다.

Ticket 상태, 공식 답변과 고객 메시지는 그대로 둔다. 확인을 기록했다고 문의가 해결되는 것은 아니다.

## 2 서로 다른 두 번호

| 확인 기록의 ID: id | 확인 대상 고객 메시지 ID: through_message_id | 뜻 |
|---:|---:|---|
| 11 | 80 | 이 담당자가 고객 메시지 80번까지 확인했다고 기록 |
| 12 | 71 | 이 담당자가 고객 메시지 71번까지 확인했다고 나중에 기록 |

id는 저장된 확인 기록을 구별하는 번호다. 12가 11보다 크다는 사실은 기록을 구분할 뿐, 확인한 대화의 범위가 더 넓다는 뜻은 아니다.

through_message_id는 '어디까지 확인했는지'를 나타낸다. 80번까지 확인한 뒤 71번까지 확인했다는 요청이 늦게 들어와도 이미 확인한 72~80번이 취소되지 않는다. 따라서 같은 Ticket/배정에서 이 필드의 최대값인 80을 현재 확인 지점으로 삼는다.

두 확인 기록은 모두 남긴다. 71번은 잘못된 요청이나 만료된 기록이 아니라 더 작은 범위를 가리킨 기록이다. 현재 계약에는 확인 기록의 만료시간이나 TTL이 없다.

실제 조회 원리를 단순화하면 다음과 같다. 두 조건은 생략할 수 없다.

```sql
SELECT MAX(through_message_id)
FROM ticket_customer_message_confirmations
WHERE ticket_id = :ticketId
  AND assignment_version = :currentAssignmentVersion;
```

MAX(id), 마지막 recorded_at이나 마지막 Commit을 고르는 방식은 이 규칙을 표현하지 못한다. 실제 JDBC 조회는 현재 Ticket의 배정 버전과 확인 범위를 한 SQL에서 읽어 서로 다른 시점의 배정을 섞지 않는다.

## 3 담당자가 바뀌면 범위도 분리한다

| 시점 | 현재 담당자/배정 버전 | 현재 배정의 확인 지점 |
|---|---|---|
| A가 80번까지 확인 | A / 버전 1 | 80 |
| B에게 인계, B는 아직 명시적 확인 안 함 | B / 버전 2 | NULL |
| B가 80번까지 명시적으로 확인 | B / 버전 2 | 80 |

인계는 담당 책임을 바꾸는 작업이다. 그것만으로 B의 확인을 대신 기록하지 않는다. A의 기록은 버전 1의 이력으로 보존하고 B의 버전 2에 복사하지 않는다. A가 다시 담당자가 되어 버전 3이 되더라도 새 배정의 확인 기록이 필요하다.

B가 이미 글을 읽었을 가능성과 서버에 B의 명시적 확인 기록이 있다는 사실은 구분한다. B가 버튼을 누르기 전에는 '현재 배정의 확인 기록 없음'이라고 표시한다. 이 NULL은 대화가 없거나 과거 확인 기록을 삭제했다는 뜻이 아니다.

## 4 확인 뒤 새 글이 오면

현재 배정에서 80번까지 확인한 뒤 새 고객 메시지 81번이 저장되면 다음과 같다.

| 값 | 결과 |
|---|---|
| effectiveThroughMessageId | 80 |
| latestCustomerMessageId | 81 |
| needsConfirmation | true |

80번 확인 요청을 같은 UUID로 다시 보내도 81번을 자동으로 확인하지 않는다. 기존 제출은 그대로 재확인하고 최신 고객 메시지/확인 필요 여부를 별도로 반환한다. 이전 담당자의 제출을 재확인하는 경우도 당시 기록과 현재 배정의 상태를 나누어 본다.

## 5 코드와 검증 위치

- Lab `CustomerMessageConfirmationService`: 현재 직원 자격/담당자/배정 버전/명시한 고객 Message를 검사한다. 같은 UUID 재확인과 새 쓰기를 구분한다.
- Lab `JdbcCustomerMessageConfirmationRepository.current`: 같은 Ticket/현재 배정의 MAX(through_message_id)와 최신 고객 메시지를 한 SQL에서 읽는다.
- Lab `V12__add_customer_message_confirmations.sql`: 확인 기록과 같은 Ticket의 배정/메시지 참조를 추가한다. 이전 업무 Row를 바꾸거나 과거 확인을 자동 생성하지 않는다.
- Lab `CustomerMessageConfirmationHttpIntegrationTest`: 작은 대상의 늦은 기록, A→B→A, 확인/새 글/인계/권한 회수의 잠금 순서와 Commit 실패를 실제 PostgreSQL에서 검증한다.

외울 기준은 '기록 ID는 이력 식별, 대상 Message ID는 확인 범위, 배정 버전은 그 범위의 소속'이다. 현재는 Codex가 설명과 구현을 진행한 근거이며 학습자가 이를 독립적으로 설명/구현했다는 판정은 별도로 남긴다.
