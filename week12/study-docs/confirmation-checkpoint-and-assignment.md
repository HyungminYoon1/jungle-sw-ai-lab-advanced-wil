# 확인 기록 번호와 '어디까지 확인했는지' 구분하기

> 작성일: 2026-11-03
> 범위: F11 담당자의 명시적 확인. [기술 계약](../customer-followup-contract-draft.md) 5~6절의 설명
> 구현: Lab 80e5de9/6b3ba1d의 V12 확인 기록/API, 11/4의 7e17319/77a117b에서 직원 목록 표시와 확인 버튼을 로컬 검증

## 1 이 기능이 기록하는 것

현재 담당자가 '이 고객 메시지까지 확인했습니다'라고 명시적으로 남기는 기록이다. 대화를 GET하거나 화면을 열기만 해서는 기록하지 않는다. 담당자가 실제로 무엇을 읽고 이해했는지 서버가 알아내는 기능도 아니다.

Ticket 상태, 공식 답변과 고객 메시지는 그대로 둔다. 확인을 기록했다고 문의가 해결되는 것은 아니다.

## 2 서로 다른 두 번호

| 확인 기록의 ID: id | 확인 대상 고객 메시지 ID: through_message_id | 뜻 |
|---:|---:|---|
| 11 | 80 | 이 담당자가 고객 메시지 80번까지 확인했다고 기록 |
| 12 | 71 | 이 담당자가 고객 메시지 71번까지 확인했다고 나중에 기록 |

id는 저장된 확인 기록을 구별하는 번호다. 12가 11보다 크다는 사실은 기록을 구분할 뿐, 확인한 대화의 범위가 더 넓다는 뜻은 아니다.

through_message_id는 '어디까지 확인했는지'를 나타낸다. 80번까지 확인한 뒤 71번까지 확인했다는 요청이 늦게 들어와도 이미 확인한 72~80번이 취소되지 않는다. 따라서 같은 Ticket/배정에서 이 필드의 최대값인 80을 현재 확인 지점으로 삼는다.

두 확인 기록은 모두 남긴다. 71번은 잘못된 요청이나 만료된 기록이 아니라 더 작은 범위를 가리킨 기록이다. 현재 계약에는 확인 기록의 만료시간이나 TTL이 없다.

실제 조회 원리를 단순화하면 다음과 같다. 두 조건은 생략할 수 없다.

```sql
SELECT MAX(through_message_id)
FROM ticket_customer_message_confirmations
WHERE ticket_id = :ticketId
  AND assignment_version = :currentAssignmentVersion;
```

MAX(id), 마지막 recorded_at이나 마지막 Commit을 고르는 방식은 이 규칙을 표현하지 못한다. 실제 JDBC 조회는 현재 Ticket의 배정 버전과 확인 범위를 한 SQL에서 읽어 서로 다른 시점의 배정을 섞지 않는다.

## 3 현재 정책: 담당자가 바뀌면 배정별 범위도 분리한다

| 시점 | 현재 담당자/배정 버전 | 현재 배정의 확인 지점 |
|---|---|---|
| A가 80번까지 확인 | A / 버전 1 | 80 |
| B에게 인계, B는 아직 명시적 확인 안 함 | B / 버전 2 | NULL |
| B가 80번까지 명시적으로 확인 | B / 버전 2 | 80 |

인계는 담당 책임을 바꾸는 작업이다. 그것만으로 B의 확인을 대신 기록하지 않는다. A의 기록은 버전 1의 이력으로 보존하고 B의 버전 2에 복사하지 않는다. A가 다시 담당자가 되어 버전 3이 되더라도 새 배정의 확인 기록이 필요하다.

B가 이미 글을 읽었을 가능성과 서버에 B의 명시적 확인 기록이 있다는 사실은 구분한다. B가 버튼을 누르기 전에는 '현재 배정의 확인 기록 없음'이라고 표시한다. 이 NULL은 대화가 없거나 과거 확인 기록을 삭제했다는 뜻이 아니다.

## 4 확인 뒤 새 글이 오면

현재 배정에서 80번까지 확인한 뒤 새 고객 메시지 81번이 저장되면 다음과 같다.

| 값 | 결과 |
|---|---|
| effectiveThroughMessageId | 80 |
| latestCustomerMessageId | 81 |
| needsConfirmation | true |

80번 확인 요청을 같은 UUID로 다시 보내도 81번을 자동으로 확인하지 않는다. 기존 제출은 그대로 재확인하고 최신 고객 메시지/확인 필요 여부를 별도로 반환한다. 이전 담당자의 제출을 재확인하는 경우도 당시 기록과 현재 배정의 상태를 나누어 본다.

## 5 코드와 검증 위치

- Lab `CustomerMessageConfirmationService`: 현재 직원 자격/담당자/배정 버전/명시한 고객 Message를 검사한다. 같은 UUID 재확인과 새 쓰기를 구분한다.
- Lab `JdbcCustomerMessageConfirmationRepository.current`: 같은 Ticket/현재 배정의 MAX(through_message_id)와 최신 고객 메시지를 한 SQL에서 읽는다.
- Lab `V12__add_customer_message_confirmations.sql`: 확인 기록과 같은 Ticket의 배정/메시지 참조를 추가한다. 이전 업무 Row를 바꾸거나 과거 확인을 자동 생성하지 않는다.
- Lab `CustomerMessageConfirmationHttpIntegrationTest`: 작은 대상의 늦은 기록, A→B→A, 확인/새 글/인계/권한 회수의 잠금 순서와 Commit 실패를 실제 PostgreSQL에서 검증한다.

외울 기준은 '기록 ID는 이력 식별, 대상 Message ID는 확인 범위, 배정 버전은 그 범위의 소속'이다. 현재는 Codex가 설명과 구현을 진행한 근거이며 학습자가 이를 독립적으로 설명/구현했다는 판정은 별도로 남긴다.

## 6 직원 화면을 따라가기 (11/4)

업무 목록에는 최신 고객 Message ID/시각과 현재 배정의 확인 지점이 나온다. RESOLVED인 문의도 새 글이 있으면 확인 필요로 표시할 수 있다. 목록을 새로고침하거나 대화를 연 것만으로는 확인 이력을 만들지 않는다.

대화 화면의 직원 확인 영역에서 고객 Message를 직접 선택한다. 예를 들어 배정 버전 2에서 30번을 골랐다면 Client는 다음 두 값을 함께 보관한다.

```javascript
target = {throughMessageId: 30, expectedAssignmentVersion: 2};
```

버튼을 누르면 이 선택과 제출 UUID를 POST한다. 그 사이 31번이 도착해도 30번을 31번으로 바꾸지 않는다. Commit이 완료되면 서버는 저장한 확인 이력과 현재 상태를 나누어 반환한다. 화면은 저장 이력을 표시하고 GET으로 현재 배정 상태를 다시 읽는다. 31번은 확인 필요로 남는다.

응답을 잃었을 때는 원래 UUID/대상/버전을 유지해 같은 제출을 재확인한다. 반대로 저장 성공은 확인했으나 다음 GET만 실패했다면 POST를 다시 보내지 않고 상태 조회를 재시도한다. pagehide에서는 이 메모리 정보가 지워지며 영속 초안 복구 기능은 아니다.

코드는 Lab의 `customer-confirmation-ui.mjs`가 선택/제출/늦은 응답을, `customer-confirmation-page.mjs`가 직원 확인 영역과 선택지를 담당한다. 서버는 기존 CustomerMessageConfirmationService의 짧은 Transaction에서 다시 인가/배정/대상을 검사하고 Commit을 끝낸 뒤 Controller가 201을 반환한다. Browser의 선택이나 활성 버튼만으로 저장 권한이 생기지는 않는다.

오늘의 실제 실행 결과는 [직원 업무 목록과 확인 화면 검증](../lab-reports/2026-11-04-staff-confirmation-ui.md)에서 확인한다. 이 설명과 학습자의 직접 답변은 구분한다.

## 7 왜 인계만으로 B도 확인했다고 하지 않는가

확인 버튼의 뜻은 '이 문의는 어디까지 처리됐다'가 아니라 '현재 담당자가 이 고객 글까지 확인했다고 기록한다'이다. A가 30번까지 확인한 사실과 B가 30번까지 확인한 사실은 서로 다르다. 인계만으로 후자를 만들 수 없다.

| 항목 | A에서 B로 인계한 뒤 |
|---|---|
| 고객이 쓴 30번 메시지 | 그대로 남음 |
| A가 30번까지 확인한 기록 | A의 이전 배정 이력으로 남음 |
| 현재 담당자 | B로 변경 |
| B의 현재 확인 지점 | B가 명시적으로 기록하기 전에는 없음 |

또 담당자가 화면에서 30번까지를 골랐다면 나중에 도착한 31번을 읽었다고 대신 기록해서는 안 된다. 같은 UUID로 30번의 저장 결과를 다시 확인해도 범위는 30이다. 31번은 별도로 읽고 명시적으로 선택할 대상이다. 두 경우 모두 '하지 않은 확인을 서버가 대신 만들어서는 안 된다'는 기준으로 생각하면 된다.

## 8 설계 선택: 팀 공통, 사람별, 배정별

인계 후 확인 지점이 반드시 초기화돼야 한다는 보편적인 DB/Spring 규칙은 없다. 먼저 이 값이 무엇을 뜻하는지 정하고 그에 맞는 키와 화면 문구를 선택한다. 아래 세 안은 비교를 위한 설계 대안이며 외부 제품이 이 세 방식을 모두 제공한다는 뜻은 아니다.

| 설계 | 기록의 뜻 | A가 50번까지 확인한 뒤 B에게 인계 | 장점과 한계 |
|---|---|---|---|
| Ticket의 팀 공통 지점 | 우리 팀에서 50번까지 확인한 이력이 있음 | 공통 50을 유지. 'B가 읽었다'고 표시하지 않음 | 인계가 잦아도 중복 확인 부담이 적음. 새 담당자의 확인 여부는 알 수 없음 |
| 사람별 지점 | 특정 사람이 어디까지 확인했는지 | A=50 유지, B는 자신의 기존 기록 또는 없음 | 개인별 읽음/안 읽음 표시와 잘 맞음. A가 다시 담당자가 되면 과거 A의 지점을 쓸 수 있어 새 배정의 명시적 확인과는 다름 |
| 현재 배정별 지점 | 이 책임 배정을 맡은 담당자가 명시적으로 확인한 범위 | A/배정 1의 50 보존. B/배정 2는 별도 확인 전까지 없음 | 인계 이후 책임 구간을 분명히 기록. A가 돌아와도 새 배정에서 확인해야 하는 추가 동작이 생김 |

읽기 위치를 사람/참여자별로 두는 실제 패턴도 있다. [Twilio Read Horizon](https://www.twilio.com/docs/conversations-classic/read-horizon-overview)은 특정 참여자의 마지막 읽은 메시지 위치를 다루며, Application에서 언제 갱신할지 정하도록 한다. [Matrix의 읽기 표식](https://spec.matrix.org/latest/client-server-api/#read-and-unread-markers)도 사용자별 방 Account Data에 위치를 둔다. 이것은 사람별 표식의 근거이고, Helpdesk가 인계할 때 배정마다 초기화하라고 요구하는 근거는 아니다.

현재 F11은 세 번째 설계다. 한 명의 책임 담당자와 명시적 인계를 두기로 한 이 앱에서는 이 선택을 유지하는 것을 권장한다. 새 책임자가 문의 내용을 확인했다고 남긴 기록과 이전 담당자의 기록을 구분할 수 있기 때문이다. 이는 우리 업무 목적을 바탕으로 한 추천이며 프레임워크 제약이나 모든 Helpdesk의 표준은 아니다.

반면 목적이 '팀에서 누군가 확인했으니 반복 확인을 줄이자'라면 첫 번째가 더 단순할 수 있다. 화면에는 '팀에서 50번까지 확인'이라고 적고 B 개인의 확인으로 해석하지 않아야 한다. 실제 운영에서 인계 빈도/업무 부담을 보고 다시 검토할 수 있다.

이전 담당자의 확인 이력과 현재 배정 상태를 함께 보여주면 두 정보를 모두 활용할 수 있다. 현재 구현은 과거 이력을 DB에 보존하고 현재 배정 상태를 조회한다. 새 담당자의 화면에 이전 배정의 확인 지점까지 함께 보여주는 조회/화면은 후속 보완안이며 이번에 구현했다고 하지 않는다.

## 9 12번 선택 뒤 도착한 13번은 어떻게 할까

이 질문도 먼저 버튼의 뜻을 정해야 한다. '선택한 12번까지 확인했다'와 '저장 시점까지 도착한 글을 일괄 처리한다'는 서로 다른 명령이다. 현재 버튼은 전자이며 다음 순서로 움직인다.

1. 담당자가 12번까지의 글을 보고 12번을 선택한다.
2. 다른 요청에서 고객 글 13번이 저장된다. 담당자 화면에는 아직 보이지 않을 수도 있다.
3. 확인 요청은 선택했던 12번을 보낸다. 서버는 12번을 기록한다.
4. 최신 고객 글은 13번이므로 현재 확인 지점 12와 비교해 확인 필요로 남긴다.

서버가 저장 직전에 최신 ID인 13을 찾아 대신 기록하면 담당자가 요청하지 않은 범위까지 '확인했다'로 표시한다. 13번에 새 오류나 중요한 경과가 있어도 목록에서 확인 필요가 사라질 수 있다. 그래서 명시적 확인을 기록하는 이 앱에는 선택한 범위를 유지하는 안을 권장한다.

다른 서비스는 대화를 화면에 표시할 때 읽음 위치를 자동 갱신할 수 있다. 그것도 가능한 설계지만, 화면에 표시한 범위와 서버에 도착만 한 범위는 구분해야 한다. Twilio도 화면을 열 때 전체 읽음 처리를 호출하는 방식과 특정 Message Index를 지정하는 방식을 설명한다. 이를 우리 앱의 수동 확인 버튼과 동일한 정책으로 해석하지 않는다.

HTTP 201은 이 요청이 만든 확인 기록의 저장 성공이다. 12번을 요청했다면 12번의 저장 성공이며 13번을 확인했다는 뜻이 추가되지 않는다. 사람별/배정별/팀 공통 중 어느 설계를 쓰든 기록의 이름과 실제 저장 범위를 일치시켜야 한다.

## 10 저장 성공 뒤 조회 실패와 저장 여부 미확인

확인 POST는 기록을 저장하는 요청이고, 뒤따르는 현재 상태 GET은 화면에 보여줄 상태를 읽는 요청이다. 두 요청은 별개이므로 어느 응답을 받았는지부터 구분한다.

| Browser가 확인한 사실 | 남은 불확실성 | 다음 동작 |
|---|---|---|
| POST의 유효한 201과 저장 기록을 정상 수신. 뒤의 GET만 실패 | 최신 현재 상태를 아직 읽지 못함 | POST를 반복하지 않고 GET만 다시 시도 |
| POST를 보냈으나 연결이 끊겨 응답을 받지 못함 | 서버가 Commit했을 수도, 저장하지 못했을 수도 있음 | 원래 UUID/배정 버전/대상을 그대로 유지해 같은 제출 재확인 |

첫 경우에는 저장 성공이라는 근거가 있다. 화면을 갱신하지 못했다는 이유로 확인을 새로 저장할 필요가 없다. 실제 Client는 저장을 확인하면 pending을 지우고 현재 상태를 GET한다. GET 실패는 saved-refresh-failed로 구분한다.

두 번째 경우에는 '응답 없음'을 'Rollback 완료'로 해석하지 않는다. 같은 제출을 재확인하면 서버는 먼저 현재 조회 권한을 검사하고 UUID에 대응하는 기존 기록을 찾는다. 동일 기록이 이미 있으면 200/추가 Row 0으로 반환한다. 아직 없고 현재 쓰기 조건도 유효하면 처음 저장해 201이 될 수 있다. 새 쓰기 권한/버전이 사라졌다면 저장을 거부할 수 있으므로 재확인이 항상 200이라는 뜻은 아니다.

현재 확인 지점이 30이라는 GET 결과만으로 특정 UUID의 제출이 저장됐다고 확정하지도 않는다. 다른 제출이 같은 30을 기록했을 수 있다. 명령의 저장 결과와 현재 상태를 나누어 확인하는 이유다.

실제 Browser 실패 실험은 이미 승인한 로컬 합성 범위에서 진행한다. 서버의 실제 응답을 받은 테스트 중계 지점에서 전달을 막는 조건을 명시하고, 임의의 성공 JSON만 반환하는 Test Double과 구분한다. 이 재현이 모든 단절/Commit 장애를 증명하는 것은 아니다.

## 11 인계와 서비스 권한 회수 후 재확인

같은 UUID로 저장 결과를 재확인한다고 현재 인가를 생략하지 않는다. 현재 F11/O5/O6에서는 서비스의 활성 직원은 자신의 과거 제출 결과를 읽을 수 있고, 새 확인은 현재 담당자만 만들 수 있다.

실제 Service 내부의 핵심 순서를 단순화하면 다음과 같다. HTTP 입력/Session/CSRF 검사가 이 코드 앞에도 있으며 생략되는 것은 아니다.

```java
access.staff(ticket, actor);                   // 현재 서비스 조회 권한
var existing = repository.submission(...);     // 같은 Ticket/작성자/UUID
if (existing.isPresent()) return replay(...);  // 같은 버전/대상의 과거 결과
// 새 기록은 현재 담당자, 배정 버전과 대상 메시지를 검사한 뒤 저장
```

| 상태 | 같은 과거 제출 재확인 | 기존 확인 기록 |
|---|---|---|
| A가 저장 후 B에게 인계, A는 활성 서비스 직원 | 허용/200. A의 과거 결과이며 B의 새 확인은 만들지 않음 | A의 이전 배정에 보존 |
| A의 서비스 권한 회수 Commit 후 새 요청 시작 | 거부. 현재 직원 자격이 없으면 UUID만으로 공개하지 않음 | 이미 Commit된 이력은 보존 |

권한 회수는 특정 서비스에서 직원으로 할 수 있는 일을 막는 것이며 로그인 계정 자체의 삭제와 다르다. 이 실험은 Session이 유효해도 서비스 조회/재확인이 거부되는 것을 확인한다. 전체 로그인 계정 중지나 고객 소유권 회수는 별도 계약이다.

이미 권한을 검사하고 공유 잠금을 얻은 Transaction은 권한 회수 Commit 전에 끝날 수 있다. '회수 Commit 뒤 새로 시작한 요청'과 이미 진행 중이던 요청을 섞지 않는다. 과거에 전달한 화면/데이터를 되돌리는 기능도 아니다.

[인계/권한 회수 Browser 검증](../lab-reports/2026-11-04-confirmation-authority-browser.md)은 실제 201/200/403/404, 남은 A의 Row 한 건과 B의 새 배정/확인 없음을 대조했다. 코드 동작의 검증과 학습자의 답변은 별도 근거다.

## 12 배정 충돌 뒤에는 어떻게 다시 선택할까

A가 배정 1에서 30번을 선택한 뒤 B에게 인계됐다가 다시 A/배정 3이 됐다고 하자. 사람이 같아도 선택의 배정 버전은 1이다. 현재 상태를 조회해 버전 3을 읽었다고 기존 선택의 버전을 바꾸면 사용자가 새 배정에서 하지 않은 확인을 대신 제출하게 된다.

현재 화면은 확인 POST의 HTTP 409와 `code: "ASSIGNMENT_VERSION_CONFLICT"`를 함께 확인한 경우에만 '현재 배정 다시 조회하고 확인 범위 새로 선택' 버튼을 보여준다. 같은 Ticket/인증 사용자/UUID의 저장 결과를 배정 버전 검사보다 먼저 찾는 현재 Service 순서가 이 복구의 근거다. 이 오류는 새 배정의 확인을 자동으로 생성하라는 지시가 아니다.

1. 충돌 직후에는 원래 선택/제출을 보관하고 추가 제출을 막는다. 일반 새로고침으로 현재 배정 3을 읽어도 배정 1의 선택을 자동 변경하지 않는다.
2. 사용자가 재선택 버튼을 누르면 거부된 선택을 비우고 현재 상태를 GET한다. 이 버튼은 POST나 새 UUID 발급을 하지 않는다.
3. GET이 성공해 현재 확인 권한을 확인해도 대상은 빈 상태다. 사용자가 고객 메시지를 직접 다시 선택해야 한다.
4. 그 선택을 제출할 때 새 UUID와 현재 배정 버전을 사용한다. 이때도 서버가 현재 담당자/배정/대상을 다시 검사하고 Commit 후 201을 반환한다.

| 응답/상황 | 화면이 유지할 것 | 허용할 복구 |
|---|---|---|
| 409와 정확한 배정 버전 충돌 코드 | 원래 제출을 자동 변경하지 않음 | 사용자의 명시적 초기화 → GET → 새 선택 |
| 409지만 다른 코드/코드 누락/Body 해석 실패 | 원래 UUID/배정 버전/대상 | 위 재선택 버튼을 열지 않음 |
| 연결 단절이나 5xx 등 저장 결과 미확인 | 원래 UUID/배정 버전/대상 | 같은 제출의 명시적 재확인 |
| 재선택 버튼 뒤 GET 실패 또는 권한 없음 | 비워진 선택, 쓰기 비활성 | 현재 상태 조회부터 복구 |

모든 409를 '저장되지 않음'으로 해석하는 일반 규칙이 아니다. 이 Endpoint의 오류 계약에 맞춘 화면 동작이며 오류 Body에서 새 배정 버전을 가져와 자동 재전송하지 않는다. 다른 답변 Form의 초안도 이 버튼이 함께 초기화해 주는 것은 아니다.

Lab `customer-confirmation-ui.mjs`의 `reselect()`는 선택을 비운 뒤 읽기만 하고, `customer-confirmation-page.mjs`가 버튼/빈 선택/비활성 상태를 표시한다. [재선택 검증 보고서](../lab-reports/2026-11-04-confirmation-reselection-ui.md)는 실제 오래된 버전의 409와 새 선택의 201, DB 확인 한 건을 대조했다. 기존 확인 이력이나 문의 원문을 삭제하는 기능은 없다.

## 13 공식 답변 초안과 결과 미확인 제출

확인 버튼과 공식 답변 작성은 별도 기능이지만 배정이 바뀌었을 때 같은 구분이 필요하다. 답변 초안의 배정 버전을 고정하는 것은 '현재 담당자가 다시 A가 됐다'는 이유만으로 오래된 초안을 새 배정의 답변으로 보내지 않기 위한 장치다.

| 상황 | 보관할 정보 | 다음 동작 |
|---|---|---|
| 배정 1에서 작성 중. 아직 POST 전이며 새 GET은 배정 3 | 원래 본문/정정 대상/초안 버전 | 자동 버전 교체나 POST를 막음. 사용자가 명시적으로 초안을 버린 뒤 현재 배정 GET과 빈 Form에서 다시 작성 |
| 원래 제출이 409/ASSIGNMENT_VERSION_CONFLICT로 거부됨 | 사용자가 결정할 때까지 원래 초안/제출 | 명시적 초안 초기화 뒤 GET. 새 본문을 제출할 때 새 UUID 사용 |
| POST 응답을 잃음. 새 GET은 배정 3 | 원래 UUID/본문/정정 대상/제출 버전 | 초안 초기화로 넘어가지 않고 같은 제출을 먼저 재확인 |

마지막 경우에는 서버에 이미 저장됐을 가능성이 있다. 배정이 바뀌었다고 새 UUID로 같은 답변을 보내면 중복 답변이 생길 수 있다. 단순 대화 GET에서 같은 문장을 발견해도 UUID의 결과를 확인한 것은 아니다. 서버의 같은 제출 재확인은 현재 조회 권한을 확인한 뒤 저장된 결과를 찾으며, 과거 배정의 답변을 현재 배정의 답변으로 고치지 않는다.

현재 Client의 `reviewReply()`는 다음 조건으로 명시적 초기화를 제한한다. 일부 초기화 대입은 설명을 위해 줄였다.

```javascript
if (posting || !isId(selected) || !needsReplyReview()
        || pending !== null && !replyVersionRejected) return false;
// 허용된 오래된 초안/거부된 제출만 비우고 새 쓰기 권한은 일단 끈다.
render({kind: "reply-draft-reset"});
return read(ticketId); // 조회만 수행. 새 답변 POST/UUID 생성은 하지 않는다.
```

Page는 초기화 이벤트에서 본문과 정정 선택을 비운다. 일반 대화 새로고침은 이 이벤트가 아니므로 원래 초안을 비우지 않는다. 결과 미확인 제출의 본문/정정 선택은 수정하지 못하게 하고 같은 제출을 재확인하게 한다. 정정 대상이 다시 읽은 첫 페이지에 없더라도 선택을 지워 다른 답변으로 바꾸지 않는다. 실제 대상의 종류와 같은 Ticket 여부는 서버가 다시 검사한다.

이것은 메모리의 초안을 새로 시작하는 화면 동작이다. DB에 저장된 원문/답변을 지우거나 Rollback하는 동작이 아니다. 현재 조회가 실패하면 새 답변을 허용하지 않으며 페이지 이탈 시 메모리 정보가 사라지는 기존 한계도 유지한다. 위 설명은 합의한 배정/제출 계약에 따른 UI 설계이고 모든 Helpdesk가 같은 초기화 버튼을 제공해야 한다는 표준은 아니다.

[답변 초안 복구 검증](../lab-reports/2026-11-04-reply-draft-review.md)은 실제 409/201/201/200과 새 답변 두 건을 대조했다. 현재 배정 5에서 재확인한 답변도 저장 당시 배정 3을 유지했다. Node의 화면/통신 대역과 실제 Browser/PostgreSQL 근거를 나누어 읽는다.

## 14 확인 저장 성공과 새 글의 확인 필요는 함께 성립한다

확인 POST의 성공은 선택한 범위가 저장됐다는 뜻이다. 그 사이 도착한 모든 고객 글까지 확인했다는 뜻은 아니다. 11/4의 강화한 Browser 실험은 다음 순서를 고정했다.

| 순서 | 실제 동작 | 결과 |
|---|---|---|
| 1 | 배정 3에서 고객 메시지 1번을 직접 선택 | 선택한 대상은 1번 |
| 2 | 같은 고객의 추가 글 2번을 Commit | 아직 화면에서 선택하지 않은 새 글 |
| 3 | 원래 선택을 POST하고 Commit | 201, 확인 지점 1, 최신 고객 글 2, 확인 필요 true |
| 4 | 대화를 다시 GET | 2번도 보이지만 선택은 빈 상태. 새 확인을 대신 제출하지 않음 |

확인 지점 1과 최신 고객 글 2가 다른 것은 저장 실패가 아니다. 사용자가 명시한 범위를 지켰기 때문에 새 글의 확인 필요가 남는다. [실제 화면/DB 검증](../lab-reports/2026-11-04-confirmation-cross-flow.md)에 원문/Job 보존과 관찰 범위를 기록했다.

순서가 반대일 수도 있다. 확인 Transaction이 당시 최신 글 1번까지 확인해 needsConfirmation=false를 읽고 Commit한 뒤 새 글 2번이 Commit되면, 다음 GET은 true다. 앞의 false는 처음 자료를 읽었던 시점의 상태이며 뒤의 true는 새 글을 반영한 다른 시점의 상태다. POST 응답이 Browser에 도착하기 전에 새 글이 저장될 수도 있다. 따라서 두 값을 다르게 받았다는 사실만으로 앞선 저장을 실패나 잘못된 응답으로 판정하지 않는다.

GET도 조회한 시점의 결과다. 그 뒤 발생한 변경까지 계속 반영하는 실시간 구독은 아니다. 현재 화면은 저장된 이력을 따로 표시하고 상태를 다시 GET하며, 새로운 고객 글의 선택과 확인은 사용자에게 남긴다. 서버의 실제 잠금/두 Commit 순서 검증과 Browser에서 통제한 순차 실행의 차이도 위 보고서에서 나눈다.

### 이미 있는 메시지를 확인해도 새 기록이면 201

고객 메시지와 담당자의 확인 기록은 서로 다른 Row다. 고객 메시지 70번이 이미 있다는 이유로 첫 확인도 200이 되는 것은 아니다. 이 POST가 만드는 것은 '이번 담당자가 이번 배정에서 70번까지 확인했다'는 확인 기록이다.

| 제출의 저장 여부 | HTTP 상태 | 이번 요청으로 추가된 확인 Row |
|---|---|---:|
| 이번 UUID의 확인이 없고, 입력/권한/배정 검사와 Commit이 성공 | 201 | 1 |
| 같은 UUID/배정 버전/대상의 확인이 이미 저장돼 있고 재확인 권한도 유효 | 200 | 0 |

새 글 71번이 먼저 Commit됐더라도 70번의 새 확인 자체는 201로 성공할 수 있다. 이때 유효 확인 지점은 70, needsConfirmation은 true다. 저장 성공 여부와 아직 확인하지 않은 새 글의 존재는 별개의 정보다. 현재 상태 GET은 저장을 하지 않으므로 그 조회의 200과도 구분한다.

## 15. 배정과 확인 지점이 같은 시점의 값이어야 하는 이유

유효 확인 지점의 집계 범위는 Ticket ID와 현재 배정 버전이다. 인계 뒤에도 A가 해당 서비스를 조회할 수 있다면 A의 화면에 B가 담당하는 배정의 확인 지점이 표시된다. canConfirm은 고객 글이 있고 조회한 직원이 현재 담당자일 때 true다.

JdbcCustomerMessageConfirmationRepository.current는 Ticket의 담당자/배정 버전과 유효 확인 지점을 한 SELECT로 읽는다. 아래는 유효 확인 지점을 계산하는 부분이다.

```sql
(SELECT MAX(c.through_message_id) FROM ticket_customer_message_confirmations c
    WHERE c.ticket_id=t.id AND c.assignment_version=t.assignment_version) AS effective_through
```

확인 이력의 Ticket과 배정 버전을 이 SELECT에서 읽는 Ticket 행과 맞춘다. 최신 고객 Message도 같은 SELECT에서 읽는다. PostgreSQL의 Read Committed에서 일반 SELECT는 그 문장이 시작될 때의 스냅샷으로 계산한다. 따라서 담당자, 배정 버전과 그 배정의 확인 지점을 같은 시점으로 연결할 수 있다. [PostgreSQL 17의 Read Committed 설명](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)

기존 CustomerMessageConfirmationHttpIntegrationTest에는 다음 순서의 사례가 있다.

1. A가 배정 버전 1에서 확인 기록을 저장한다.
2. A의 조회 서비스 호출이 Repository의 현재 상태 SQL을 실행하기 직전에 대기한다.
3. A에서 B로 인계하고 배정 버전 2를 Commit한다.
4. 실제 SQL을 실행한다. 그 결과가 배정 버전 2, 유효 확인 지점 NULL, A의 canConfirm false인지 검사한다.

이 사례에서 B의 배정에는 확인 이력이 아직 없다. A의 배정 1 기록은 이력으로 남는다. 조회 서비스의 시작과 실제 SELECT의 스냅샷 획득 사이에 인계가 완료되면, 그 SELECT에는 Commit된 새 배정과 새 배정의 확인 범위가 함께 보인다. 이 순서는 [기존 통합 테스트](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/test/java/lab/helpdesk/ticket/web/CustomerMessageConfirmationHttpIntegrationTest.java#L345)의 근거다.

조회한 시점의 needsConfirmation은 그때의 최신 고객 글과 유효 확인 지점을 비교한 값이다. 해당 SELECT가 시작된 뒤 새 확인이 Commit되면 다음 SELECT에서 반영된다. 이 개념의 적용 문항과 실제 답변은 [11/5 학습 기록](../study-notes/2026-11-05-study-questions.md)에 남긴다.

## 16. 두 저장이 실제로 겹쳤다는 근거

고객 글이 먼저 Commit되는 통합 테스트는 실제 INSERT 뒤 바깥 트랜잭션을 잠시 열어 둔다. `inserted.countDown()`은 INSERT 단계에 도달했다는 테스트 신호다. 이어 `await(release)`에서 기다리는 동안 담당자의 확인 작업을 시작한다. 테스트가 대기를 풀면 바깥 콜백이 반환되고 그 트랜잭션이 Commit된다. [새 글이 먼저 저장되는 통합 테스트](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/test/java/lab/helpdesk/ticket/web/CustomerMessageConfirmationHttpIntegrationTest.java#L330)

대기를 풀기 전에 `awaitDatabaseWaiter()`가 `pg_stat_activity`를 읽는다. 조건은 같은 테스트 DB의 다른 세션 중 `wait_event_type = 'Lock'`이 있는지다. 이 값은 PostgreSQL 서버 프로세스가 잠금을 기다리고 있음을 뜻한다. 현재 함수의 판정 범위는 격리 DB 안의 잠금 대기 존재 여부이며 테스트가 구성한 두 작업의 순서와 함께 해석한다. [PostgreSQL 17 대기 이벤트](https://www.postgresql.org/docs/17/monitoring-stats.html)

| 기존 검사 | 두 요청의 순서 | 관찰한 결과 |
|---|---|---|
| PostgreSQL 통합 테스트 | 새 글 INSERT 뒤 트랜잭션 유지 → 확인 시작 → 잠금 대기 관찰 → 새 글 Commit | 확인은 선택한 메시지를 그대로 저장하고 새 글을 확인 필요로 반환 |
| 실제 Browser 순차 검사 | 1번 선택 → 새 글 2번 Commit → Browser에 파일 신호 전달 → 1번 POST | 201, 확인 지점 1, 최신 고객 글 2, 확인 필요 true와 화면 선택 상태 |

Browser 검사에서는 새 글 저장을 완료한 시점 이후에 확인 POST를 시작한다. 서버의 두 Commit 순서에 대한 관찰과 Browser의 응답/화면 관찰은 [11/4 확인 교차 흐름 보고서](../lab-reports/2026-11-04-confirmation-cross-flow.md)에 있다.

## 17. 같은 Ticket 행을 잠그고 두 종류의 기록을 저장하기

두 저장은 각각 `ticket_messages`와 `ticket_customer_message_confirmations`에 기록한다. 작업 순서를 맞추는 기준은 두 요청이 공통으로 사용하는 Ticket 행이다. 두 Service가 `access.ticket(ticketId, true)`를 호출하면 Repository가 해당 ID에 `FOR UPDATE`를 적용한다. [Ticket 행을 조회하는 코드](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/main/java/lab/helpdesk/support/JdbcSupportRepository.java#L75)

예를 들어 고객 글 저장이 Ticket 10을 잠갔다면 같은 Ticket 10에 확인을 저장하는 작업은 잠금을 얻을 때까지 기다린다. 그 행 잠금은 트랜잭션이 Commit 또는 Rollback될 때 풀린다. Ticket 20의 쓰기는 자기 Ticket 행을 사용한다. 일반 조회는 해당 행 잠금과 동시에 Commit된 데이터를 읽을 수 있다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)

통합 테스트의 대기는 두 작업이 같은 Ticket에서 실제로 겹치도록 첫 트랜잭션 안에서 의도적으로 만든다. 아직 응답이 없다는 사실은 작업이 완료되지 않았다는 관찰이다. 잠금 대기 여부는 `pg_stat_activity`에서 확인한다.

Browser 사례에는 순서대로 두 저장이 있다.

| 순서 | 요청의 의미 | 저장된 값 |
|---|---|---|
| 먼저 | 고객이 후속 글을 남김 | `ticket_messages`의 고객 글 ID 2 |
| 다음 | 담당자가 현재 배정에서 고객 글 1번까지 확인했다고 제출 | 확인 이력 한 건, `through_message_id = 1` |

담당자의 POST는 `throughMessageId=1`을 전달한다. 이 값은 확인 이력의 자체 ID와 별도로 그 이력이 가리키는 고객 글의 ID다. Browser가 받은 201은 이 POST로 새 확인 이력이 생겼다는 응답이다. 응답의 현재 상태는 확인 지점 1, 최신 고객 글 2이므로 `needsConfirmation=true`다. [확인 POST Controller](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/main/java/lab/helpdesk/ticket/web/CustomerMessageConfirmationController.java#L34)

| 같은 Ticket의 Commit 순서 | 1번까지의 확인이 반환하는 상태 | 두 작업이 끝난 뒤 조회 |
|---|---|---|
| 새 고객 글 2번이 먼저 | 저장 대상 1, 최신 글 2, 확인 필요 true | 확인 지점 1, 최신 글 2, 확인 필요 true |
| 1번까지의 확인이 먼저 | 저장 대상 1, 최신 글 1, 확인 필요 false | 확인 지점 1, 최신 글 2, 확인 필요 true |

같은 배정에서 2번까지 확인한 뒤 별도의 1번 확인도 저장되면 두 이력이 남는다. 나중 확인의 자체 ID가 더 커도 유효 지점은 `MAX(through_message_id)`인 2다. [늦은 작은 확인 테스트](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/test/java/lab/helpdesk/ticket/web/CustomerMessageConfirmationHttpIntegrationTest.java#L119)

A→B→A로 담당자가 돌아오면 현재 배정은 버전 3이다. 버전 3의 이력이 비어 있으면 유효 확인 지점은 NULL이다. 조회 권한을 유지한 A가 원래 UUID와 제출 내용으로 재확인하면 이전 버전의 저장 결과와 버전 3의 현재 상태를 각각 받는다. [인계와 재배정 테스트](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/fe9336ddbc8166051b54858e870fc9abe07c810a/src/test/java/lab/helpdesk/ticket/web/CustomerMessageConfirmationHttpIntegrationTest.java#L163)
