# 문의 상태 변경과 명시적 재개

> 기준일: 2026-11-04
> 범위: 합의한 T01~T08의 로컬 합성 구현/검증. 운영 배포, 실제 AI 호출과 원격 CI 결과는 포함하지 않음

## 합의와 구현 범위

사용자는 저장 흐름 설명과 두 문항의 이해 점검 뒤 T05의 별도 상태 버전/원자적 이력 저장을 별도로 승인했다. T07의 일반 상태 처리 우선, T08의 문의/AI/검토 상태 구분과 고객 공개 원칙도 선택했다. 정책 선택을 테스트 결과나 이해도 점수로 취급하지 않는다.

Lab 91c0e25에 기술 계약, 946937c에 V13/Domain/저장, c57ff94에 Service/HTTP, a6d51ad에 화면/Node, af92b61에 실제 Browser 실험을 나눠 저장했다. 현재 담당자의 START/RESOLVE/REOPEN과 등록자 본인의 명시적 REOPEN을 구현했다. 배정 버전과 상태 버전은 별개이며 재개가 담당자나 배정 버전을 변경하지 않는다. 답변/고객 글/확인/AI 성공도 상태를 자동 변경하지 않는다.

취소/중복/Spam을 해결로 대신 기록하거나 자동 해결/병합/삭제하는 기능은 추가하지 않았다. 제한 Pilot의 개인별 계정, 보관/삭제, 악용 대응과 일반 입력 AI의 출시 조건도 유지한다.

## 저장과 권한 경계

V1~V12는 유지하고 V13에서 tickets.status_version과 ticket_status_events를 추가한다. 기존 Row의 0은 도입 기준값이다. 이전 업무 이력을 만들어 넣지 않는다. Ticket 현재 상태/버전의 UPDATE와 이력 INSERT는 같은 Transaction으로 Commit/확인된 Rollback을 한다.

새 요청은 Ticket 잠금을 얻은 뒤 새 SQL로 상태, 최신 고객 글과 현재 배정의 확인 범위를 읽는다. 직원의 활성 서비스 권한은 같은 Transaction의 기존 공유 잠금 검사로 확인한다. 이미 저장된 동일 제출은 현재 조회 권한과 원래 내용의 일치를 검사한 뒤 재확인하므로 인계/재개 후에도 과거 기록을 새 배정의 처리로 바꾸지 않는다.

해결에는 같은 Ticket의 공식 답변, 사유, 직접 선택한 최신 고객 글과 현재 배정의 명시적 확인이 필요하다. 다른 창의 최신 확인이 있어도 오래된 해결 요청의 대상은 서버가 자동 확대하지 않는다. 원문 내용의 의미상 해결 여부까지 DB 제약으로 증명하는 것은 아니다.

직원 API는 기존 Session/CSRF와 AGENT/서비스 권한을 함께 요구한다. 고객 본인 재개는 별도 경로와 공개 DTO를 쓰고 배정 정보/직원 내부 이력을 노출하지 않는다. 같은 사람이 직원 권한을 잃어도 본인 문의에 대한 고객 권한은 별개다. 같은 UUID로 두 경로를 바꿔 쓰면 요청 충돌이다.

## 화면과 실제 Browser

대화 화면에 처리 시작/해결/재개를 연결했다. 해결 근거는 실제 불러온 공식 답변과 고객 글에서 직접 선택한다. 고객 목록에서 이동하면 고객 재개 경로를 사용한다. 초안은 선택 당시 두 버전을 고정하고 결과 미확인 제출은 UUID/본문/근거를 유지한다.

첫 Browser 실험은 도구의 제한된 JavaScript 실행 환경에서 process/fetch를 사용할 수 없어 로그인 준비가 실패했다. 업무 검증 통과로 기록하지 않았다. 실험 전용 일회성 Loopback 전달과 page.request를 사용해 합성 로그인 값이 명령어/출력에 들어가지 않도록 보완했다. 운영 서버에 로그인 우회 경로를 추가한 것이 아니다. 전달 서버와 실험이 직접 시작한 프로세스는 종료한다.

실제 Browser→Spring→PostgreSQL 흐름에서는 다음을 검증한다.

1. START 201 뒤 상태 GET만 503으로 실패하게 하고 GET만으로 복구한다.
2. 해결 대상을 고른 뒤 새 고객 글/명시적 확인을 먼저 Commit한다. 기존 대상의 해결은 409 NEW_CUSTOMER_MESSAGE로 거부되고 초기화는 GET만 한다.
3. 새 대상의 해결을 실제 201로 Commit한 뒤 Browser에 전달할 응답을 차단한다.
4. 그 사이 명시적으로 재개하고 A→B→A로 인계한다. 원래 해결 제출을 재확인한 200은 상태 2/배정 1의 기존 이력을 반환하고 현재 OPEN/상태 3/배정 3은 유지한다.
5. 새 START와 별도 합성 해결 뒤 고객 Session에서 명시적으로 재개한다. 고객 요청/응답에는 내부 배정 필드가 없다.

스크린샷 검토에서 대화 제목이 이전 조회의 IN_PROGRESS/RESOLVED를 반복 표시하고 별도 현재 상태는 OPEN으로 표시되는 문제를 찾았다. 제목의 중복 상태를 제거하고 Node 재현 검사와 Browser 검사를 보완했다. Codex가 발견/수정한 결과이며 사용자의 직접 발견으로 기록하지 않는다.

합성 Browser의 POST 기대 순서는 201/409/201/200/201/201이다. 중간의 실험 Service 동작을 포함한 상태 이력 6건/최종 OPEN/상태 버전 6/배정 버전 3, 최초 두 Message의 전체 Row와 AI 관련 Snapshot/Provider 0회를 DB에서 대조한다. 순차 Gate 실험이며 잠금 경합 자체는 앞의 HTTP/PostgreSQL 검사가 근거다.
