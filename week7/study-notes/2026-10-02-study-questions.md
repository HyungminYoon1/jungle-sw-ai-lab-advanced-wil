## 키워드보다 해결을 요청한 내용을 본다

“로그인이 안 된다”는 문의를 `ACCOUNT`라고 판단했다. 처음에는 로그인이라는 키워드가 있고 다른 유형의 키워드가 없기 때문이라고 설명했지만, 단어만으로 분류하면 정상이라는 배경도 문제로 오해할 수 있다.

“로그인은 정상이고 이용료가 두 번 청구됐다”는 문의에서는 `BILLING`이라고 답했다. 로그인이라는 말이 있어도 그것을 문제 삼지 않았기 때문이다. 분류의 근거는 사용자가 실제로 해결을 요청한 내용이다.

문의 유형과 원인도 다르다. 로그인에 실패한 이유를 몰라도 로그인 문제라는 점은 알 수 있다. `UNDETERMINED`는 원인 미확인이라는 이유만으로 넣는 값이 아니다.

팀 전체가 서비스를 이용하지 못하고 당일 마감이 있다는 A03 문의는 `TECHNICAL`로 분류하는 데 동의했다. 로그인 문제인지 화면 문제인지 아직 모르더라도 기술적인 이용 문제라는 유형은 알 수 있다. `HIGH`의 근거는 보고된 영향과 긴급성이며, 우리 Server의 장애가 원인이라고 확정한 것은 아니다.

## 분류의 경계는 먼저 명확하게 정한다

같은 문제에 여러 분류를 붙여도 되는지 판단하기 어려워 대기업의 공식 가이드를 확인해 달라고 요청했다. Microsoft는 구분하기 어려운 Class를 피하고 로맨틱 코미디를 로맨스·코미디 두 유형으로 표현하는 예를 제시한다. AWS도 한 문서에 여러 분류가 동시에 해당하면 Multi-label을 사용하도록 안내한다. [Microsoft 분류 설계 가이드](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/language-service/custom-text-classification-transparency-note?view=foundry-classic), [AWS 분류 모드 선택](https://docs.aws.amazon.com/comprehend/latest/dg/create-custom-classifier-console.html)

상위·하위 분류의 중복에는 공통된 금지 규칙이 없었다. Google의 분류 V1 모델은 더 구체적인 결과만 반환하지만 V2 모델은 조건을 만족하면 상위·하위를 함께 반환한다. 한 문제에 분류 하나가 반드시 정답인 것은 아니며, 분류의 의미와 출력 정책을 먼저 정해야 한다. [Google 분류 정책](https://docs.cloud.google.com/natural-language/docs/categories)

이번 Lab에서는 `ACCOUNT`·`BILLING`·`TECHNICAL`을 동등한 문의 유형으로 정의하고 복수 분류를 허용하는 안에 동의했다. `TECHNICAL`은 계정·청구 이외의 기술적인 이용 문제이며 모든 기술 문제의 상위 범주로 사용하지 않는다. 로그인 실패에는 `ACCOUNT`, 로그인 실패와 PDF 미리보기 오류가 함께 있으면 `["ACCOUNT", "TECHNICAL"]`을 사용한다. 유형이 여러 개라는 이유로 문의를 하나만 남기거나, 같은 의미의 넓은 분류를 덧붙이지 않는다.

## 복수 문제를 하나의 분류로 숨기지 않는다

한 글에서 여러 문제를 제기했다면 어떤 유형으로 분류해야 하는지, 복수 Category가 필요한지 질문했다. 단일 대표값과 복수 목록의 차이를 설명받은 뒤, 복수 `categories` 목록을 허용하되 Ticket은 자동 분리하지 않는 방향에 동의했다.

로그인 불가와 중복 청구를 모두 해결해 달라는 문의는 `["ACCOUNT", "BILLING"]`로 표현할 수 있다. 반면 로그인 실패와 비밀번호 재설정 실패는 모두 `ACCOUNT`에 속할 수 있다. 문제는 둘이지만 목록은 `["ACCOUNT"]` 한 항목이며, 요약에는 중요한 문제를 모두 남긴다.

처음에는 분류 목록의 중복을 없애면 식별한 문제 수도 줄어들지 않을까 생각했다. 그러나 목록은 문제 수가 아니라 유형을 나타낸다. 로그인 실패만 남긴 요약에는 비밀번호 재설정 문제가 빠졌다는 점을 확인했다. 분류 목록에서 같은 유형을 한 번만 쓰는 것과 요약에서 문제를 누락하는 것은 다르다.

두 유형을 모두 알면서 하나만 선택하거나 `OTHER`·`UNDETERMINED`로 바꾸는 것은 분류 정보를 잃는 일이다. 복수 분류는 한 제안 안에 보관하며, 그 때문에 Ticket·Message·AI 작업을 여러 개 만들지는 않는다.

## 분류하지 못한 별도 문제는 그대로 남긴다

로그인 불가와 구체적으로 설명하기 어려운 별도 문제를 모두 확인해 달라는 문의에는 `["ACCOUNT", "UNDETERMINED"]`를 사용하는 규칙에 동의했다. 알려진 로그인 문제도 남기고, 다른 문제를 아직 분류하지 못했다는 정보도 보존한다. 요약에도 별도 문제의 존재와 설명 부족을 적는다.

로그인 실패의 원인만 모른다면 `["ACCOUNT"]`다. 원인 미확인은 이미 파악한 문의 유형을 지우거나 미분류 항목을 추가할 이유가 아니다.

## 높은 우선순위가 원인을 확정하는 것은 아니다

중복 출금은 적은 금액이라도 신뢰성과 멱등성 문제가 있을 수 있어 `HIGH`가 적절하다고 생각했다. 다만 이런 가능성은 조사할 가설이지 확인된 원인이 아니다. 원문에 두 번 출금됐다는 신고와 환불 요청이 있다면 금전 피해를 우선 확인할 근거는 있지만, 멱등성 미구현 때문에 출금됐다고 단정할 수는 없다.

AI가 그런 추측을 원인으로 확정해 요약한다면 사실을 왜곡한 것이다. 증상·피해·요청은 원문에 따라 정리하고, 원인은 확인한 범위만 설명해야 한다. 이번 사례의 `HIGH` 판단과 복수 문제 전체에 적용할 일반적인 Priority 규칙도 구분한다.

## 구조와 내용의 검증을 함께 바꾼다

출력 계약은 단일 문자열 `category` 대신 목록 `categories`를 사용하는 v2 초안으로 바뀌었다. 단일 문의도 목록으로 표현한다. 항목의 허용값, 빈 목록과 중복을 검사해야 하며, 이전 Field를 계속 보내는 것도 계약 위반이다.

구조에 맞는 목록이어도 한 문제를 빠뜨렸거나 정상이라는 배경을 문제로 분류했다면 내용은 틀릴 수 있다. `["ACCOUNT", "BILLING"]`과 `["BILLING", "ACCOUNT"]`는 같은 분류 집합으로 평가한다. 배열 순서를 우선순위로 해석하지 않는다.

기존 평가 12건은 유지하고 실제 복수 문제 1건을 추가한 13건 초안으로 정리했다. 두 방식에서 두 번씩 비교하면 52회 후보다. 먼저 대표 문의 한 건의 전달·생성·검증을 확인하며 전체 평가에는 나머지 기대값과 Rubric을 고정하는 작업이 필요하다.

## AI 입력과 평가용 기대값은 분리한다

`expectedCategories`와 `expectedPriority`는 별도 평가 AI를 뜻하는 값이 아니라, 원문을 보고 미리 정한 채점 기준이다. 현재 실험에서는 한 AI가 요약·분류·우선순위를 함께 생성하고, 구조는 코드로 검사하며 내용은 원문과 대조한다.

AI에게 평가할 문의의 기대값까지 보내는 것은 시험문제와 함께 정답을 주고 정답을 보지 말고 풀라는 것과 비슷하다고 설명했다. 답이 같아도 원문을 이해해 분류한 것인지 주어진 답을 따라 쓴 것인지 구분하기 어렵다. 청구 문제를 `BILLING`으로 분류한다는 일반 규칙은 알려주되, 해당 Case의 기대값은 모델 입력에서 제외하고 결과가 나온 뒤 비교한다.

## API Key는 실행하는 Process별로 구분한다

논문 작업에서 이미 `OPENAI_API_KEY`를 사용하므로 Helpdesk용 키를 같은 이름으로 분리할 수 있는지 질문했다. 별도의 PowerShell에서 Helpdesk 키를 임시 환경 변수로 설정했다. 그 창에서 실행한 Node는 Helpdesk 키를 물려받지만 다른 창이나 Windows에 저장한 논문용 키는 바뀌지 않는다.

PC를 다시 켜면 임시 설정이 사라지는지도 확인했다. PowerShell을 닫고 새 창을 열어도 임시 설정은 이어지지 않는다. 이때 기존 논문용 키가 적용될 수 있으므로 Helpdesk를 실행할 때에는 전용 창의 키부터 설정해야 한다. 키 자체가 폐기되는 것과 Process의 환경 변수가 사라지는 것은 다르다.

실험 비용 $1은 호출 한 건이 아니라 오늘 Helpdesk API 실험 전체에서 넘지 말아야 할 누적 상한이라고 명확히 했다. 공유한 두 건의 사용량으로 계산한 추정 합계는 $0.0001895다. 실제 청구액과는 다르며, 추가 실험에서도 앞선 호출 비용을 포함해야 한다. 현재 스크립트는 실행 간 누계를 저장하지 않으므로 하루 한도를 자동으로 강제한다고 볼 수 없다.

## 실제 응답과 형식 검증을 분리해서 읽는다

독립 비교 스크립트와 검증기는 Codex가 작성했다. 준비 단계에서 합성 응답 Test 15개와 기존 UI Test 12개가 통과한 기록이 있다. 나는 Helpdesk 전용 PowerShell에서 N01 비교를 실행하고 결과를 공유했다. 같은 입력과 작업 지시에서 `text.format`만 바꾼 Prompt-only와 Structured Outputs 응답을 각각 한 건씩 받았다.

두 결과 모두 HTTP 200이고 JSON·계약 검증을 통과했다. API 응답은 바깥의 생성 상태·출력·사용량 객체와 그 안의 Model 텍스트를 구분해서 읽는다. `VALID_OUTPUT`은 형식과 값 규칙을 통과했다는 뜻이지 내용까지 옳다는 뜻은 아니다. Script의 `manualContentReview`는 `NOT_SCORED`였다.

AI가 틀린 내용을 넣어도 사람이 원문을 보거나 별도 평가를 하지 않으면 알아내지 못하는 것 아니냐고 질문했다. 허용값이나 명확한 상태는 코드로 대조할 수 있지만, 자유로운 문장의 모든 누락과 왜곡을 현재 검증기가 판별하지는 못한다. 추가 AI 평가도 정답을 보장하지 않는다. 그래서 원문은 그대로 보존하고 AI 결과는 검토 전 제안으로 구분해야 한다.

## 핵심 사실의 누락이 대응을 바꾼다

Prompt-only는 “로그인 링크가 만료된 이유를 알고 싶어 합니다.”라고 요약했다. Structured Outputs는 링크 만료 뒤 새 링크로 로그인에 성공했다는 사실까지 포함했다. 첫 번째 요약만 읽으면 현재 로그인할 수 있는지는 알 수 없다.

나는 로그인 성공 사실이 담당자의 대응을 바꾸는 핵심 정보라고 답했다. 이전에 안 되던 상태에서 되는 상태로 바뀌었기 때문이다. 로그인 복구가 필요한 문의와 이미 로그인했지만 만료 이유를 묻는 문의는 다르게 대응해야 한다.

핵심 사실을 누락한 경우도 0점으로 기록하도록 Rubric 문구를 보완했다. Codex의 원문 대조에서는 첫 요약 0점, 두 번째 요약 2점으로 정리했다. 첫 요약의 문제는 거짓 사실 추가가 아니라 핵심 사실 누락이다. 이 점수는 구조 검증 코드가 자동으로 계산한 값이 아니다. 한 문의의 두 응답만으로 어느 방식이 항상 더 정확하다고 결론 내릴 수도 없다.

## 전체 영향으로 우선순위를 판단한다

통상 문의와 긴급도를 판단하지 못한 문제가 함께 있을 때 전체를 `NORMAL`로 정하면, 판단하지 못한 부분의 정보가 사라진다고 답했다. 이어 작은 문제들이 다수 중첩되거나 연쇄적으로 작용해 큰 문제가 되는 경우도 있지 않느냐고 질문했다.

개별 문제의 가장 높은 값만 선택하는 규칙으로는 이런 영향을 놓칠 수 있다. 미리보기와 다운로드가 각각 우회 수단이었다면 둘 다 실패했을 때 자료를 확인할 방법이 없어진다. 문제의 개수보다 문의 전체가 업무에 미치는 영향이 중요하다.

개별 또는 누적·결합 영향에 높은 우선순위를 줄 근거가 있으면 `HIGH`, 그런 근거를 확인하지 못했고 전체 영향 판단에 필요한 정보가 부족하면 `UNDETERMINED`, 통상적으로 대응할 근거가 있으면 `NORMAL`로 보완하는 데 동의했다. 원문에 없는 연쇄 관계나 원인을 AI가 사실로 만들어서는 안 된다. 여러 Ticket을 종합해야 드러나는 문제도 한 문의만 보는 AI가 자동으로 알 수는 없다.

## 공통 지시와 구조 제한을 분리해서 비교한다

핵심 사실을 빠뜨리지 말라는 지시를 어느 조건에 넣어야 하는지 묻자 A·B 모두라고 답했다. 한쪽의 지시만 개선하면 내용이 좋아진 이유가 지시 때문인지 Structured Outputs 때문인지 구분하기 어렵다. 원문·Model·공통 지시는 같게 두고 구조 제한만 달리한다.

첫 응답에서 `priority`가 빠지고 수정 요청 뒤에 올바른 응답이 온 사례에서는 첫 응답은 실패로 보아야 할 것 같다고 답했다. 설명을 통해 최초 응답의 검증 실패와 재요청의 복구 성공을 따로 기록하는 이유를 정리했다. 같은 조건을 다시 시험하는 독립 반복과 실패를 수정하도록 요청하는 복구도 다르다.

## 10월 2일 미실시분의 후속 준비

날짜가 10월 3일로 넘어간 연장 구간도 10월 2일 학습 회차로 정리한다. Codex가 기존 예비 비교 코드는 보존하고, 13건·두 방식·두 반복을 준비하는 Code와 Test를 추가했다. 요청에는 제목과 원문만 들어가고 기대값은 들어가지 않는지 확인하는 Test도 포함됐다. 새 준비 Test 14개와 기존 27개, 총 41개가 통과했다.

분류와 우선순위는 기대 후보와 비교할 수 있지만, 그 일치만으로 요약 내용까지 옳다고 볼 수는 없다. 원문과 반대되는 합성 요약도 형식 검증은 통과할 수 있고, 내용은 별도로 평가해야 한다. 준비 코드가 이 차이를 유지하는지는 자동 Test로 확인했으며 내 코드 이해 확인이나 실제 52회 평가를 마친 것은 아니다.

예산 계산 역시 이전 호출의 비용을 포함하고, 사용량을 모르면 0원으로 가정하지 않는다. 현재 Test는 계산 규칙을 대상으로 하며 Process 사이의 누계 보존까지 구현한 것은 아니다. 이번 준비에서 새 API 호출은 없었다.

## 문의 유형의 불확실과 제안 생성 보류는 다르다

기능은 정상이고 안내 문구를 쉽게 바꾸자는 문의는 요청 내용을 알고 있지만 기존 세 범주 밖인 경우라고 답했다. 이때는 `OTHER`를 사용한다. 무슨 문제인지 판단할 정보가 부족한 `UNDETERMINED`와 구분할 수 있다.

유효한 요약은 만들 수 있지만 분류나 긴급도를 모른다면 `SUGGEST`와 `UNDETERMINED`로 그 범위를 남긴다. 유효한 요약 자체를 만들 수 없어 제안 생성을 명시적으로 보류한 `ABSTAIN`은 Job을 `ABSTAINED`로 기록하고 Suggestion은 만들지 않는 처리안에 동의했다. 어느 경우에도 접수한 원본 Ticket·Message는 유지한다.

Suggestion이 없다는 결과만으로 원인을 알 수는 없다. 명시적으로 생성을 보류한 것과 Provider 호출·출력 검증에 실패한 것은 다르다. JSON 오류나 필수 Field 누락을 `ABSTAIN`으로 바꾸지 않고, 구체적으로 어떤 입력에서 보류를 허용할지는 더 확인한다. 이번 합의는 저장 계약이며 실제 Job 저장 구현·Test를 마쳤다는 뜻은 아니다.

## 허용값과 피해 근거로 우선순위를 판단한다

미리보기 실패·다운로드 정상·급하지 않은 문의는 `TECHNICAL`·`NORMAL`, 로그인 불가 외에 영향 정보가 없는 문의는 `ACCOUNT`·`UNDETERMINED`라고 답했다. 한편 급하지 않은 문의에 `LOW`를 쓰기도 했는데, 현재 계약에는 `NORMAL`·`HIGH`·`UNDETERMINED`만 있다. 청구지 변경 방법은 `BILLING`이며 주소가 등장했다는 이유로 `ACCOUNT`나 `OTHER`를 추가하지 않는다.

중복 출금 문의의 Priority를 `UNDETERMINED`라고 답한 부분은 다시 짚어야 한다. 정확한 금액이나 시스템 원인을 몰라도 중복 출금이라는 금전 피해는 명시돼 있다. 이번 기준에서는 그것이 `HIGH`의 근거다. 근거 부족과 확인된 피해를 구분해야 한다. Ticket을 자동으로 해결 상태로 바꾸면 안 된다는 점과, 비밀번호가 포함된 로그인 문의의 `ACCOUNT`·`UNDETERMINED`는 올바르게 답했다.

## 문의 우선순위와 보안 경고를 분리한다

문의 자체는 급하지 않아도 Injection 문구가 있다는 점은 보안 경고로 다뤄야 하지 않느냐고 질문했다. 문의 Priority는 고객 문제의 영향이고 보안 신호는 입력에 대한 관측이므로, 둘을 별도로 다루는 방향에 동의했다. 의심 문구만으로 문의를 `HIGH`로 바꾸거나 실제 침해를 확정하지 않는다.

`ticketId`처럼 Server가 이미 알고 있는 값을 왜 AI가 반환하느냐고도 질문했다. 현재 대상은 Job·Message와 DB에서 확인하고, AI는 요약·분류·우선순위 등의 제안만 반환하는 것이 맞다. 독립 Tool Calling 예제와 실제 Suggestion 출력 계약을 구분하며, AI가 Ticket ID나 실행 권한을 다시 정하게 하지 않는다.

## AI 전송용 복사본에서 민감 정보를 줄인다

주소·연락처가 있는 문의는 AI에게 보내기 전 마스킹이 필요하다고 제안했다. 요약에 필요하지 않은 민감 정보는 전송용 복사본에서 제거하거나 치환하는 방향에 동의했다. 출력에서 값을 지우는 것만으로 이미 이루어진 외부 전송을 막을 수는 없다.

접수 원문 보관과 외부 AI 전송은 다른 정책이다. 전송용 복사본을 만들더라도 원문의 열람 권한·보관 기간과 비밀값 취급은 별도로 정해야 한다. 현재 평가에는 합성 자리표시자만 쓰며, 실제 전처리·탐지 구현을 마친 것은 아니다.

## Tool 실행 전 거부와 실행 중 실패를 구분한다

가짜 함수 실행 횟수를 묻는 질문에서 정상 호출은 1회, 금지 함수는 0회, 함수 내부 실패는 1회라고 답했다. 금지된 `ticketId` 인자에는 재시도를 포함해 2회라고 답했는데, AI 생성 요청 횟수와 Tool 실행 횟수를 혼동한 부분이다. 금지 함수의 0회도 처음에는 구체적인 허용 목록보다 막연한 보안 판단으로 설명했다.

이 실험에서 허용한 함수는 `find_current_ticket` 하나이고 인자는 `{}`뿐이다. 대상 Ticket ID `7`은 Server가 정한다. 추가 인자를 받았다면 거부하고 함수는 실행하지 않는다. 정상 인자로 다시 요청하는 자동 동작도 없으므로 실행은 0회다.

반면 검증을 통과한 함수가 내부에서 Exception을 발생시키면 실행은 이미 1회 진행한 것이다. 실행 여부와 결과 성공 여부를 따로 봐야 한다. 관리자에게 사유를 보고하자는 생각은 별도 운영 정책이며, 원문 Exception이나 민감 값을 그대로 출력하는 것과는 구분해야 한다.

Codex가 독립 스크립트와 Test를 작성해 실행한 결과는 **1·0·0·1회**였다. 새 Test 13개와 기존 41개를 함께 실행해 총 54개가 통과했다. 가짜 함수의 Code 동작을 확인한 것이며, 내가 자료 없이 이 경계를 설명하는지는 다음 문답에서 확인한다. 실제 AI·DB 호출과 Ticket 변경은 없었다.

## 10월 3일로 이월한 학습

별도의 미분류 문제 병기, 세 문의 유형의 범위와 전체 Priority 기준, 안내 문구 개선의 `OTHER` 분류와 유효한 `ABSTAIN`의 기록 기준은 정했다. 목록의 실제 저장 표현, 나머지 기대값, 구체적인 `ABSTAIN` 허용 사례·조회 표현은 더 검토해야 한다. 전체 비교 전에는 보완한 계약·Rubric과 Prompt Version을 맞추고 하루 누적 예산 관리도 확인한다. 예비 호출은 이전 Version으로 수행했으므로 새 조건의 본 평가와 구분한다.

나는 복수 문제와 누적 영향을 질문하고 실제 응답의 핵심 누락을 확인했다. Schema·문서·독립 비교 코드 초안은 Codex가 작성했다. 이번 호출은 Spring Application이나 PostgreSQL 저장 흐름에 연결한 것은 아니다.

남은 학습은 다음 순서로 이어간다.

1. 가짜 Tool의 금지 인자를 왜 실행 전에 거부하는지 내 말로 설명하고, 아직 후보인 평가 기대값과 구체적인 `ABSTAIN` 사례를 확인한다.
2. Dataset·Rubric·Prompt의 Version과 누적 예산 관리 방식을 맞춘 뒤 13건·두 방식·두 반복의 본 평가를 진행한다. 이전의 $1 승인을 다음 날 새 예산으로 자동 적용하지 않는다.
3. AI 전송 전 민감 정보 처리, 보안 신호와 문의 Priority 분리, 출력·Provider 실패 경계의 미구현 Test를 진행한다.
4. 입력·조회 표현, Job 등록의 Commit 경계와 복구·호출 한도를 검토한 뒤 Message·Job·Suggestion의 Spring·PostgreSQL 수직 흐름을 구현한다.
5. 원문 보존·제안 저장·중단 복구·Security·CSRF·Browser와 회귀를 실제로 검증하고 Week 7 WIL을 정리한다.

마감 시점의 최신 자동 검증은 JavaScript Test 54개 통과다. 실제 전체 Provider 평가, 민감 정보 전처리, Spring AI 연결과 Message·Job·Suggestion Migration은 아직 완료하지 않았다. 해당 PostgreSQL·Browser Test도 미실시이며, 기존 Java 61개를 이번 회차에서 다시 실행한 것은 아니다.
