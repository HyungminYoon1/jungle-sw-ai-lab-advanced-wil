## Tool 호출 요청과 실제 실행

AI가 함수 이름을 반환하는 것과 Server가 그 함수를 실행하는 것은 다르다. Dispatcher는 이름과 인자를 검증한 뒤 허용한 구현을 선택해 실행한다. 허용하지 않은 함수나 인자를 실행 전에 거부한 경우 실행 횟수는 0이다. 허용된 함수를 실행하다 실패한 경우에는 1회로 센다.

이 과정을 JavaScript의 작은 Spike로 먼저 살펴봤지만, 실제 Server는 Java·Spring이다. 함수 호출의 기본 문법보다 대상 선택·권한·검증·실패 정책이 중요한 부분이라고 정리했다. AI가 Ticket ID를 결정하도록 하지 않고 Server가 선택한 대상을 사용한다.

### 핵심 질문

- 함수 이름을 읽은 것과 실제 실행한 것을 어떻게 구분할까?
- 검증 거부와 실행 중 실패의 실행 횟수는 왜 다를까?
- AI가 보낸 인자를 그대로 실행 대상으로 사용하면 어떤 경계가 사라질까?

## 문의 접수와 AI 처리를 분리한 이유

Ticket·최초 Message·PENDING Job은 같은 접수 Transaction에 저장한다. Job 등록이 실패하면 앞선 Ticket·Message도 Rollback해야 한다. 반대로 접수가 Commit된 뒤 AI가 실패했다면 이미 접수한 원문까지 취소하면 안 된다.

Job은 실행할 작업의 기록이다. DB에 Job이 있다는 사실만으로 AI가 호출됐다고 알 수는 없다. Worker는 재시작 후 DB의 미완료 작업을 찾아야 하며, 실행할 때 가장 최근 Message를 선택하는 대신 Job이 참조하는 원문 Message를 사용해야 한다.

### 핵심 질문

- Job 등록 실패와 접수 Commit 이후 AI 실패는 무엇을 다르게 취소해야 할까?
- Job에 Ticket ID만 두고 나중에 최신 Message를 읽으면 입력이 어떻게 달라질 수 있을까?
- 문의와 Job을 서로 다른 Transaction에서 등록하면 어느 중단 구간이 문제가 될까?

## Row Lock과 실행권은 다르다

처음에는 AI 응답을 기다리는 동안에도 Job Row Lock을 유지하고, 일정 시간이 지나면 풀어야 한다고 생각했다. 하지만 Row Lock은 DB를 변경하는 짧은 구간을 보호하는 장치이고, Commit 뒤의 실행권은 저장된 상태와 현재 Attempt로 관리한다.

PENDING을 RUNNING으로 변경하고 Commit하면 Lock은 풀리지만 RUNNING 상태는 남는다. 다른 Worker가 Lock을 얻었다고 새 AI 호출을 시작할 수는 없다. 복구·재시도 조건과 남은 한도를 확인해 새 Attempt의 실행권과 호출 예약을 함께 Commit해야 한다.

실행권을 새 Attempt로 넘겼다면 이전 Attempt의 늦은 성공이나 오류로 현재 결과를 바꾸면 안 된다. 현재 실행권을 일반 SELECT로 확인한 뒤 저장하는 사이에도 교체가 발생할 수 있으므로, 결과 저장 Transaction의 보호가 필요하다.

### 핵심 질문

- Lock이 해제돼도 다른 Worker가 같은 PENDING 조건으로 실행권을 얻지 못하는 이유는 무엇일까?
- RUNNING이라는 기록만으로 실제 AI 실행이 계속되고 있다고 판단할 수 있을까?
- 이전 Attempt의 응답이 Schema를 통과해도 현재 결과로 저장하면 안 되는 이유는 무엇일까?
- 같은 Transaction에 일반 SELECT와 저장을 넣는 것만으로 실행권 교체 경쟁이 막힐까?

## 호출 예약과 결과 저장

호출 한도는 새 생성 요청을 제한한다. 같은 Message의 새 Job으로 횟수를 초기화하면 이 한도를 우회하게 된다. 같은 작업의 재시도는 기존 Job을 사용하고 누적 횟수를 유지해야 한다.

호출 예약과 실행권의 Commit이 실패했다면 Provider를 호출하면 안 된다. 반대로 예약을 Commit한 뒤 중단됐다면 실제 외부 전송 여부가 불명확할 수 있다. DB Transaction에 외부 호출까지 넣어도 Provider의 실행을 Rollback할 수는 없으므로 이 문제를 없애지 못한다.

한도를 모두 사용했다는 사실은 새 호출을 막는 것이지 이미 받은 결과를 버리라는 뜻이 아니다. 현재 실행권과 출력 검증 조건이 맞으면 저장할 수 있다. Suggestion과 SUCCEEDED는 같은 결과 저장 Transaction이며, 실패해도 이전에 Commit한 고객 원문은 유지한다.

### 핵심 질문

- 예약 기록은 실제 Provider의 접수·실행·청구 중 무엇을 확정할까?
- 생성 한도를 소진해도 가능한 작업은 무엇일까?
- 결과 저장 실패를 해결하기 위해 AI를 다시 호출하는 것과 받은 결과를 다시 저장하는 것은 어떻게 다를까?

## 접수 저장 실습과 다음 학습

문답 뒤에는 실제 PostgreSQL에서 접수 원자성을 확인하는 실습으로 넘어갔다. Codex가 V2 Migration·접수 Service·테스트를 작성하고 실행했다. 새 Integration Test 15개와 전체 Java 76개, 기존 JavaScript 54개가 통과했다. [실험 결과](../lab-reports/2026-10-03-ticket-receipt-atomicity-lab.md)

이번 실습은 HTTP가 아닌 Service 단계다. 기존 API는 여전히 제목만 받고 Worker·AI 호출·Suggestion 저장은 연결되지 않았다. 내가 새 코드를 직접 설명하고 수정하는 확인도 남아 있다.

### INSERT 성공 기록과 Commit

성공한 INSERT 횟수가 어느 Table에 기록되는지 궁금했다. 실습의 횟수는 Test에서 사용하는 Java `AtomicInteger`이고, 실제 JDBC 저장이 성공해 반환된 뒤 증가한다. DB의 업무 기록이나 Commit 완료 횟수가 아니다.

같은 Transaction의 첫 INSERT가 성공해도 뒤의 INSERT가 실패하면 첫 Row까지 Rollback된다. 반면 Java 메모리의 Counter는 DB Rollback 대상이 아니므로 1이 남는다. `INSERT 성공 횟수 1`과 `Transaction 종료 뒤 Row 수 0`은 모순되지 않는다. 전자는 실행 도중의 성공, 후자는 최종 Database 상태를 설명한다.

### 핵심 질문

- JDBC INSERT 성공과 Transaction Commit은 무엇이 다를까?
- DB Rollback이 Java `AtomicInteger`까지 되돌리지 않는 이유는 무엇일까?
- 첫 INSERT가 실행되지 않은 경우와, 성공했다가 Rollback된 경우를 어떤 Assertion으로 구분할까?

## Java AI 출력 검증 실습

앞서 정한 출력 규칙을 Java 검증기로 옮기는 실습을 진행했다. Codex가 순수 검증기와 Unit Test를 작성·실행했고 새 64개가 통과했다. 실제 PostgreSQL·Security를 포함한 전체 Java Clean Test는 140개, 기존 JavaScript Test는 54개가 통과했다. [출력 검증 실험](../lab-reports/2026-10-03-ai-output-validation-lab.md)

검증 순서는 JSON 해석 → 정확히 네 Field인지 확인 → `decision`별 값 검사다. `SUGGEST`에서 Field를 빠트리거나 공백 요약을 보내면 거부하며, 분류·긴급도를 판단하지 못한 `UNDETERMINED`는 정상 값으로 남긴다. `ABSTAIN`은 나머지 세 Field가 명시적인 `null`인 조합을 검사한다.

이번에 검사하는 것은 형식과 값이다. 구조가 맞는 거짓 요약도 통과할 수 있다. `ABSTAIN`의 형식 검사와 원문에서 실제로 보류할 근거도 다르다. Provider의 거부는 생성 응답 경계에서 구분해야 하며 `ABSTAIN`으로 바꿔서는 안 된다.

요약 상한은 설정으로 받게 하고 Test에서는 잠정 200자를 사용했다. 상한을 넘는 문자열을 자르거나 누락 값을 임의로 채우지 않는다. 입력이 섞일 수 있는 Parser 오류도 원문 대신 고정 코드로 전달한다.

검증기는 아직 Worker·Provider·Suggestion 저장에 연결하지 않았다. 새 코드에 대한 독립 설명과 추가 경계 사례 검토는 남아 있다.

### 핵심 질문

- `UNDETERMINED`, 필드 누락, `ABSTAIN`, Provider 거부는 왜 같은 결과가 아닐까?

- 검증 결과 객체가 있다는 사실만으로 DB 저장이나 Ticket 상태 변경을 허용할 수 있을까?

## 정보 부족과 제안 보류의 구분

“문제가 생겼습니다. 확인해주세요.”는 문제 종류를 몰라도 확인을 요청했다는 사실을 요약할 수 있다. 반면 중립적인 제목 `문의`와 본문 `ㅁㄴㅇㄹ ???`에서는 문의 내용을 해석하기 어렵다. 전자는 `SUGGEST`와 `UNDETERMINED`, 후자는 `ABSTAIN` 허용 사례로 정하는 안에 동의했다.

판단 기준은 문의의 의미를 이해할 수 있는지다. 짧은 글·오타·외국어라는 이유로 바로 보류하지 않고 제목과 본문을 함께 본다. 보류의 JSON 구조가 맞는지 검사하는 것과 원문에서 보류할 근거가 있는지 평가하는 것도 다르다.

Codex가 두 비교 방식의 공통 Prompt를 `prompt-v3-abstain-draft`로 보완했다. 새 Test 두 개는 같은 지시가 전달되는지, A01에 구조상 유효한 보류 결과를 넣어도 기대 결정과 다르게 평가되는지 확인한다. 전체 JavaScript 56개가 통과했다. 실제 AI가 이 사례에서 보류한 결과를 관찰한 것은 아니며 기존 13건·52회 본 평가 계획은 유지했다.

### 핵심 질문

- 구조상 유효한 `ABSTAIN`도 A01의 기대 결정과 다를 수 있는 이유는 무엇일까?

## 개인정보는 요약이 아니라 전송 전에 확인한다

최종 요약에 연락처가 없다고 해서 외부 AI로 연락처를 보내지 않았다는 뜻은 아니다. AI가 원문을 받은 뒤 요약에서만 연락처를 생략했을 수도 있다. 나는 AI에게 보내는 Prompt에 개인정보가 없어야 한다고 답했다.

확인할 대상은 전처리 함수의 반환값에서 한 단계 더 나아간, 실제 전송 직전의 요청 Body다. 작업 지시·제목·본문 등 Model 입력을 모두 확인해야 다른 위치에 남은 값도 찾을 수 있다. 전송용 복사본을 만드는 것과 DB의 접수 원문을 변경하는 것은 다른 작업이다.

다음 실험에서는 실제 AI 모델을 사용해 전처리된 입력의 응답도 확인하기로 했다. 실제 연락처나 비밀값 대신 합성 자리표시자를 사용한다. 전송 직전의 입력 검사와 AI 응답의 요약 검사는 각각 기록하며, 원문이나 Credential을 Log로 출력하지 않는다. 이번 회차에서는 전처리 구현과 이 실제 AI 실험을 진행하지 않았다.

### 핵심 질문

- 요약에 연락처가 없어도 AI가 연락처를 받았을 수 있는 이유는 무엇일까?
- 전처리 함수의 결과와 실제 전송할 요청 Body를 모두 확인해야 하는 이유는 무엇일까?
- 실제 AI의 요약 결과와 전송 직전 입력 검사는 각각 무엇을 확인할까?
