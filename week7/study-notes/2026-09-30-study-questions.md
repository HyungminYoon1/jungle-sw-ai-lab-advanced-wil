# 2026-09-30 — 문의 원본, AI 제안과 처리 상태

> 학습 주제: 판단 보류의 표현, 문의 접수와 AI 처리의 분리, Ticket·Message 모델
> 상태: 개념 정리와 설계 합의 — 실제 Provider 호출·Migration·AI 구현·새 Test 실행은 미실시

## 핵심 질문

1. 분류나 긴급도를 판단하지 못해도 유효한 요약은 보존할 수 있는가?
2. Field 누락, `null`, 명시적인 `UNDETERMINED`는 어떻게 다른가?
3. AI가 필수 Field를 빠뜨렸다면 임의 보완과 전체 재요청 중 어떤 방식이 적절한가?
4. INSERT 성공과 Commit 완료는 어떻게 다르며, 문의 접수와 AI 호출은 왜 분리해야 하는가?
5. 접수 응답을 먼저 보내는 것과 중단 후 작업을 복구할 수 있는 것은 같은가?
6. AI 작업의 성공, 담당자의 제안 검토 완료, Ticket의 해결은 어떻게 다른가?
7. Ticket을 대화 묶음으로 두면 최초 문의와 공식 답변은 어디에 저장해야 하는가?
8. Ticket·최초 Message는 같은 Transaction으로 저장하면서 AI 처리는 분리하는 이유는 무엇인가?

## 판단하지 못한 항목을 평범한 값으로 바꾸지 않는다

나는 긴급도를 판단하기 어렵다는 이유만으로 요약까지 버리기보다는, 판단한 범위와 판단하지 못한 범위를 함께 보존하는 편이 적절하다고 생각했다. `NORMAL`을 대신 넣으면 “판단하지 못함”이 “보통 우선순위로 판단함”으로 바뀐다.

처음에는 `null`을 고려했지만, 실제 값의 부재와 판단 근거 부족은 명시적으로 구분하는 편이 낫다고 제안했다. 이 계약에서는 분류·긴급도의 판단 보류를 `UNDETERMINED`로 표현한다.

```json
{
  "decision": "SUGGEST",
  "summary": "로그인이 되지 않는다고 문의함",
  "category": "ACCOUNT",
  "priority": "UNDETERMINED"
}
```

이 결과는 요약과 분류는 있지만 긴급도 판단은 보류한 제안이다. `OTHER`도 “잘 모름”의 대체값은 아니다. 분류 근거는 있으나 정해진 다른 범주에 속하지 않을 때 사용한다. `null`의 의미는 JSON 자체가 업무적으로 정해주는 것이 아니라 계약에서 정한다.

필수 `category`가 아예 빠진 결과는 명시적인 판단 보류가 아니다. 나는 AI에 다시 요청해야 한다고 제안했다. 다만 “왜 빼먹었는가”에 대한 새 설명만으로 원인을 확정하지 않고, 원래 입력과 같은 계약으로 전체 결과를 다시 받는 안을 검토했다. 두 응답의 일부 값을 섞거나 Server가 임의로 `UNDETERMINED`를 채우지는 않는다.

추가 생성은 최대 1회라는 안이 남아 있다. 중단 복구까지 포함한 총 호출 한도와 오류별 재시도 조건은 아직 확정하지 않았다.

## 문의 접수는 AI 성공을 조건으로 삼지 않는다

사용자가 등록한 문의는 AI가 없어도 보존해야 하는 원본 데이터다. 나는 AI 호출이 실패했다는 이유로 문의까지 취소해서는 안 된다고 주장했다. 이는 이미 저장했기 때문만이 아니라, 문의 접수와 AI 제안의 업무상 역할이 다르기 때문이다.

여기서 “저장 성공”은 정확히 구분해야 한다. INSERT가 성공했어도 Transaction이 끝나지 않았다면 Rollback할 수 있다. 접수 Commit이 완료된 뒤에는 후속 AI 실패로 그 접수를 Rollback하지 않는다.

수동 제안 생성 API가 반드시 필요한 것도 아니다. 나는 문의 등록 뒤 Server가 자동으로 처리하는 흐름이 더 자연스럽다고 생각했다. 최종 방식은 접수 응답을 먼저 보내고 AI를 별도로 처리하는 B로 정했다. 이때 접수 `201`은 문의 저장 완료이지 AI 제안 생성 완료가 아니다.

## 제안 내용과 생성 작업을 구분한다

제안이 없다는 사실만으로는 아직 기다리는 중인지, AI가 실패했는지, 명시적으로 판단을 보류했는지 알 수 없다. 다음처럼 원본·작업·결과의 책임을 나누는 안을 검토했다.

| 대상 | 보관하는 내용 |
|---|---|
| Ticket·Message | 문의의 주제·처리 상태와 실제 작성한 원문 |
| AI Job | 실행 상태·시도 횟수·실패 코드·처리 시각 |
| AI Suggestion | 검증된 요약·분류·우선순위와 담당자 검토 상태 |

`PENDING`·`RUNNING`·`SUCCEEDED`·`ABSTAINED`·`FAILED`는 작업 상태의 잠정안이다. 유효한 `ABSTAIN`은 실패와 구분해 작업 기록만 남기는 안이며, 정의와 저장 방식은 다음에 검토한다.

유효한 제안을 저장한 작업은 `SUCCEEDED`여도, 제안은 `PENDING_REVIEW`, Ticket은 `OPEN`일 수 있다. 작업 성공, 내용 검토와 문의 해결은 서로 다른 결정이다.

별도 실행을 시작했다고 복구가 보장되는 것은 아니다. Server가 종료되면 미완료 작업을 찾아낼 기록과 재처리 조건이 필요하다. 같은 작업의 제안 중복 저장 방지와 외부 AI 호출의 중복 방지도 같은 문제가 아니다.

## Ticket은 대화를 묶고 Message는 실제 내용을 보관한다

처음에는 최초 문의 본문을 Ticket의 `description`에 추가하고 답변을 별도 기록으로 두는 안이었다. 나는 Ticket을 특정 주제의 대화 묶음으로 두고, 고객 메시지와 공식 답변이 각각 Ticket을 참조하는 모델을 제안했다.

```text
Ticket 7 — 로그인 링크 오류
  ├─ 고객의 최초 문의 Message
  ├─ 응대팀이 고객에게 게시한 답변 Message
  └─ 고객의 추가 문의 Message
```

Ticket과 Message는 1:N이다. 같은 문구로 여러 문의에 답하더라도 각 문의의 답변 기록은 별개다. AI Suggestion은 담당자를 위한 제안이지 고객에게 게시된 공식 답변이 아니다.

최초 문의도 Message로 저장하면 `tickets.description`에 본문을 중복 보관할 필요가 없다. 기존 Ticket에는 없는 원문을 조작해 Message를 만들지 않는다. 원문이 없다는 상태는 Message 0건으로 보존할 수 있다.

새 접수에서는 Ticket과 최초 Message를 함께 Commit한다. 첫 메시지 저장이 실패하면 문의 내용 없는 빈 Ticket만 남기지 않아야 하기 때문이다. 반면 이후 AI 실패는 이미 접수한 두 Row를 유지해야 한다.

## 합의한 범위와 다음 검토

합의한 방향은 Ticket·Message 모델, 문의 원본의 독립 보존, 최종 B 처리 방식이다. 학습은 기본 처리 Test → 별도 실행 연결 → 단일 Application·PostgreSQL의 최소 복구 순서로 진행한다. Week 7에는 최초 메시지 저장과 AI 연결까지만 구현하고, 후속 대화·공식 답변 기능은 이후 확장으로 남긴다.

다음에는 Job 등록의 Commit 경계, 작업 상태와 `ABSTAIN` 기록, 중단 판정과 재시도 한도, 입력·조회 API 표현을 먼저 검토한다. 그 뒤 Provider 한 개를 선택해 공식 Structured Output 방식·비용·민감 정보 취급을 확인하고 최소 비교 실험으로 이어간다.
