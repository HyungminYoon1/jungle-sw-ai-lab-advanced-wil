## 다형성 학습 질문

1. Polymorphism과 Inheritance는 같은 개념인가?
-> 아니다. Inheritance는 상위 Type과 하위 Type의 관계를 만들고, 하위 Class가 상위 Class의 접근 가능한 상태와 행동을 물려받는 방법이다. Polymorphism은 공통 상위 Type이나 Interface를 통해 객체를 사용하더라도 Runtime의 실제 객체에 따라 서로 다른 구현이 실행되는 성질이다. Class 상속은 Polymorphism을 구현하는 방법 중 하나지만, Interface 구현으로도 Polymorphism을 사용할 수 있다.

2. Composition은 객체 사이의 관계를 어떻게 구성하는가?
-> Composition은 객체가 필요한 행동을 상속받는 대신 다른 객체를 Field나 Constructor 인수로 전달받아 사용하고, 필요한 작업을 그 객체에 위임하는 방식이다. 일반적으로 has-a 또는 uses-a 관계를 표현한다.

3. 상속을 사용해도 괜찮은 조건은 무엇인가?
-> 상속은 다음 조건을 대체로 만족할 때 검토할 수 있다.
  1) 의미상 안정적인 is-a 관계가 성립한다.
  2) 하위 Type을 상위 Type 대신 사용해도 계약이 깨지지 않아 LSP를 만족한다.
  3) 단순한 코드 복사가 아니라 상위 Type의 의미 있는 특수화가 필요하다.
  4) 상위 Class의 계약과 확장 지점이 안정적이며, 변경이 하위 Class에 예측하지 못한 영향을 주지 않는다.
이러한 조건을 만족하더라도 Composition이 변경 범위를 더 단순하게 만드는지 함께 비교해야 한다.

4. Strategy가 Polymorphism과 Composition을 함께 사용한다는 것은 무슨 뜻인가?
-> Strategy는 변경 가능한 알고리즘이나 정책을 공통 Interface를 구현하는 여러 객체로 분리한다. 사용하는 Context는 구체 구현이 아니라 공통 Interface를 통해 Strategy를 호출하므로 Polymorphism이 적용된다. 또한 Context가 Strategy 객체를 Field나 Constructor 인수로 전달받아 작업을 위임하므로 Composition이 적용된다.

5. OCP가 기존 코드를 절대 수정하지 않는다는 뜻이 아닌 이유는 무엇인가?
-> OCP는 예상되는 기능 확장이 생겼을 때 안정된 기존 로직을 반복해서 수정하기보다 새로운 구현을 추가하여 확장할 수 있도록 설계하는 원칙이다. 기존 코드를 단 한 줄도 수정하지 않는다는 뜻은 아니다. 새로운 구현을 연결하는 조립 Code, 설정, Enum과 Test는 변경될 수 있다. 핵심은 변경을 완전히 제거하는 것이 아니라 변경이 퍼지는 범위를 통제하는 것이다.

6. 정책이 두 개뿐이고 거의 변경되지 않는다면 조건문이 더 나을 수도 있는 이유는 무엇인가?
-> 그 이유는 다음과 같은 소프트웨어 공학의 핵심 원칙들 때문입니다.
  1) YAGNI(You Aren't Gonna Need It) 원칙에 따라 아직 필요하지 않은 확장 구조를 만들지 않을 수 있다.
  2) 관련 규칙을 한곳에서 확인할 수 있어 구조가 단순하고 읽기 쉽다.
  3) Interface, 구현 Class와 조립 Code가 추가되는 추상화 비용을 피할 수 있다.
  4) 정책이 독립적으로 교체되거나 반복적으로 추가되지 않는다면 Strategy가 제공하는 확장성이 실제 이점으로 이어지지 않는다.
  => 조건문과 Strategy의 선택은 성능이 아니라 정책 수, 변경 빈도, 조건 중복, 독립적인 교체 필요성과 추상화 비용을 비교하여 결정한다.

## SOLID 다섯 원칙 요약

- SRP: 클래스는 변경되는 이유가 하나여야 한다.
- OCP: 안정된 핵심 코드는 가능한 한 유지하면서 새로운 정책을 확장할 수 있어야 한다.
- LSP: 구현체를 공통 타입으로 교체해도 약속된 동작이 깨지면 안 된다.
- ISP: 사용하지 않는 기능까지 구현하도록 강요하는 큰 인터페이스를 피한다.
- DIP: 정책을 사용하는 쪽이 구체 클래스가 아니라 추상화에 의존한다.

## Policy 비교 실제 관찰

### 1. TicketPriority에 VIP만 추가했을 때 왜 컴파일에 실패했는가?
-> `TicketPriority`에 `VIP`를 추가하면서 기존 `switch` 표현식이 모든 enum 값을 처리하지 못하게 되었기 때문이다. Java의 `switch` 표현식은 가능한 값을 모두 처리하거나 `default`를 제공해야 하므로, `VIP` 분기가 없는 상태에서는 테스트 실행 전 컴파일 단계에서 실패했다.

### 2. 조건문 방식에서 VIP를 지원하기 위해 기존 코드 중 무엇을 수정했는가?
-> Production Code에서는 `TicketPriority`에 `VIP`를 추가하고, 기존 `ConditionalResponseTimePolicy`의 `switch`에 `VIP → 1시간` 분기를 추가했다. Test Code에는 VIP 결과를 검증하는 테스트를 추가했다.

### 3. Strategy 방식에서 새로 추가한 코드는 무엇이며, 수정하지 않아도 된 기존 코드는 무엇인가?
-> `VipResponseTimePolicy` 구현체와 이를 검증하는 테스트를 추가했다. 기존 `ResponseTimePolicy`, `ResponseTimeCalculator`, `NormalResponseTimePolicy`, `UrgentResponseTimePolicy`는 수정하지 않았다.

### 4. Strategy를 사용하면 기존 코드를 전혀 수정하지 않아도 된다는 뜻인가?
-> 아니다. 기존 Strategy 주입 구조는 유지됐지만, 새로운 `VipResponseTimePolicy`를 생성하고 `ResponseTimeCalculator`에 전달하는 조립 코드는 추가되어야 한다. 실제 애플리케이션에서도 Factory, 설정 또는 DI Container 구성 같은 조립 경계가 변경될 수 있다. 이번 실습에는 Factory나 DI Container가 없으며, 테스트 코드가 직접 Strategy를 생성하고 전달했다.

### 5. 현재처럼 정책이 세 개이고 계산이 단순하다면 어느 방식이 더 적합하다고 판단하는가?
-> 현재처럼 정책이 세 개뿐이고 계산식이 단순하며 분기가 한곳에만 있다면 `switch` 방식이 더 단순하고 적합하다고 판단한다. 정책이 자주 추가되거나 정책마다 계산 과정과 의존성이 달라지고, 독립적인 교체가 필요해진다면 Strategy를 검토하는 것이 적절하다.

### 6. 어떤 변화가 반복된다면 Strategy의 추가 클래스와 추상화 비용이 정당화되는가?
-> 응답 시간 정책이 반복적으로 추가되거나, 정책별 계산 규칙과 의존성이 독립적으로 변경되거나, 같은 조건 분기가 여러 위치에 반복되거나, 실행 중 정책을 교체해야 한다면 Strategy의 추가 클래스와 추상화 비용이 정당화될 수 있다.

### 7. 이번 실험에서 OCP는 어떤 의미였는가?
-> 이번 실험에서 OCP는 변경을 완전히 없애는 것이 아니라 안정된 핵심 코드로 변경이 퍼지는 범위를 줄이는 의미였다. 조건문 방식은 VIP를 추가하면서 기존 `switch`를 수정했지만, Strategy 방식은 기존 Interface와 Calculator를 유지하면서 `VipResponseTimePolicy`를 추가할 수 있었다. 다만 새 구현을 연결하는 조립 코드와 테스트, 공통 요구사항을 나타내는 enum은 변경될 수 있다.

## 취약 개념 점검

### 1. Abstraction과 단순한 구현 숨김의 차이는 무엇인가?
-> 추상화는 복잡한 대상에서 호출자에게 필요한 핵심 개념과 계약을 뽑아 모델로 표현하는 설계 행위이다. 반면 구현 숨김은 외부가 알 필요 없는 내부 표현이나 변경 가능한 세부 사항에 접근하지 못하게 제한하는 방법이다. 예를 들어 `ResponseTimePolicy`는 목표 응답 시간을 제공한다는 핵심 계약을 추상화하고, 각 구현체는 구체적인 시간 계산 방법을 내부에 숨긴다.

### 2. LSP가 깨지는 구체적인 사례는 무엇인가?
-> LSP는 상위 타입이 요구되는 자리에 어떤 하위 타입이나 구현체를 사용하더라도 기존 계약과 프로그램의 올바른 동작이 깨지지 않아야 한다는 원칙이다. 예를 들어 `ResponseTimePolicy`의 목표 응답 시간이 null이 아니고 음수가 아니어야 한다는 계약이 있는데, 어떤 구현체가 음수 `Duration`을 반환한다면 문법적으로 Interface를 구현했더라도 호출자의 기대를 깨기 때문에 LSP를 위반한다.

다른 예시로 정사각형은 수학적으로 직사각형이지만, 프로그램 설계에서는 LSP를 위반하기 쉽다.
- 상위 클래스: 직사각형(Rectangle) -> 가로와 세로를 독립적으로 변경할 수 있다
- 하위 클래스: 정사각형(Square) -> 가로를 바꾸면 세로도 함께 바뀐다

### 3. DIP와 Dependency Injection의 차이는 무엇인가?
-> DIP는 상위 수준 코드가 구체 구현이 아니라 안정된 추상화에 의존하도록 의존 방향을 설계하는 원칙이다. Dependency Injection은 필요한 의존 객체를 외부에서 전달하는 구현 방법이다. 현재 코드에서 `ResponseTimeCalculator`가 구체 Policy가 아닌 `ResponseTimePolicy`에 의존하는 것은 DIP이고, 생성자로 실제 Policy 객체를 전달받는 것은 DI이다. 구체 클래스만 외부에서 주입한다고 해서 DIP까지 자동으로 만족하는 것은 아니다.

### 4. 현재 Ticket 상태 전이를 Strategy로 분리하지 않는 이유는 무엇인가?
-> 현재 상태 전이 규칙은 Ticket 자신의 현재 상태만으로 허용 여부를 판단할 수 있는 도메인 규칙이므로 Ticket이 직접 보호하는 것이 적절하다. 이를 외부 Strategy로 분리하면 Ticket이 자신의 유효한 상태를 지키는 책임이 나뉘어 캡슐화가 약해질 수 있다. 또한 현재 요구사항에는 서로 교체해야 하는 여러 상태 전이 정책이 존재하지 않으므로 Strategy를 도입할 실질적인 변경 축도 없다. 상태별 행동과 전이 규칙이 크게 복잡해진다면 State 패턴 등을 검토할 수 있지만, 현재 실습에서는 enum과 의도가 드러나는 메서드만으로 충분하다.

- Strategy 패턴: "어떤 알고리즘(방법)을 사용할 것인가"에 초점을 맞춘다. 클라이언트가 상황에 맞는 전략을 외부에서 명시적으로 선택하여 주입한다. (예: 결제 수단 선택 - NaverPayStrategy, TossPayStrategy)
- State 패턴: "객체의 상태에 따라 행동이 어떻게 달라지는가"에 초점을 맞춘다. 상태 변화에 따라 객체의 행동이 내부에서 자연스럽게 바뀌며, 상태 스스로가 다음 상태를 결정(전이)하기도 한다.
