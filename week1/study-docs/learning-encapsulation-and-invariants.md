# Learning Note — 캡슐화, 불변조건, 상태 전이

> 작성일: 2026-08-19
> 주차: Week 1

## 핵심 질문

> 필드를 `private`으로 선언하는 것만으로 객체의 상태와 도메인 규칙을 안전하게 보호할 수 있는가?

## 학습 목표

- 접근 제한과 캡슐화의 차이를 설명한다.
- 불변조건과 상태 전이 규칙을 구분한다.
- Domain Object, Application Service와 Controller의 책임 경계를 설명한다.
- 범용 Setter가 객체 규칙을 우회하는 과정을 반례로 설명한다.

## 한 문장 설명

캡슐화란 데이터와 행동을 객체 안에 함께 두고, 외부에는 의도가 드러나는 제한된 인터페이스만 제공하여 객체의 상태와 불변조건을 보호하는 설계 원칙이다.

## 핵심 흐름

1. 생성자가 유효한 초기 상태의 객체만 만든다.
2. 외부 코드는 `setStatus()` 같은 범용 변경 메서드 대신 `startProgress()`나 `resolve()`처럼 의도가 드러나는 행동을 요청한다.
3. 객체가 현재 상태를 기준으로 사전조건을 검사한다.
4. 허용된 요청만 상태를 변경하며, 거부된 요청은 기존 상태를 보존한다.

## 핵심 개념

### 캡슐화(Encapsulation)

캡슐화는 내부 구현을 무조건 감추는 데 목적이 있는 것이 아니다. 외부 코드가 객체를 잘못된 상태로 만들지 못하도록 상태 변경 경로를 제한하고, 객체가 자신의 규칙을 지키게 하는 것이 핵심이다.

필드를 `private`으로 선언해도 외부에서 호출할 수 있는 `setStatus()`가 전달받은 값을 검증 없이 대입한다면 객체는 여전히 잘못된 상태가 될 수 있다.

### 불변조건(Invariant)

클래스 불변조건은 생성자가 정상적으로 완료된 뒤부터 외부에서 관찰 가능한 정상 상태와 공개 동작의 실행 전후에 참이어야 하는 조건이다. 동작이 실패하더라도 객체를 유효하지 않은 상태로 남겨서는 안 된다.

예를 들면 다음과 같다.

- Ticket의 `status`는 `null`이 아니다.
- 은행 계좌가 마이너스 잔액을 허용하지 않는다면 잔액은 항상 0 이상이다.

불변조건을 지키는 대표적인 방법은 다음과 같다.

1. 필드를 `private`으로 선언해 외부의 직접 변경을 막는다.
2. 생성자에서 입력을 검증해 처음부터 유효한 객체만 만든다.
3. 상태를 변경하는 공개 메서드에서 상태 전이 조건을 검증한다.
4. 실패할 경우 상태를 변경하지 않거나 원래의 유효한 상태로 유지한다.

### 루프 불변조건(Loop Invariant)

루프 불변조건은 반복문의 각 반복을 시작하거나 마치는 특정 지점마다 유지되는 조건이다. 알고리즘의 정당성을 설명할 때 사용한다.

예를 들어 정렬 알고리즘에서 매 반복이 시작될 때 현재 인덱스 앞부분이 이미 정렬되어 있다는 조건을 둘 수 있다.

### 불변조건과 상태 전이 조건

| 구분 | 의미 | `resolve()` 예시 |
|---|---|---|
| 불변조건 | 유효한 객체 상태에서 계속 지켜야 하는 조건 | `status != null` |
| 사전조건 | 동작을 시작하기 전에 충족해야 하는 조건 | 현재 상태가 `IN_PROGRESS` |
| 사후조건 | 동작이 성공한 뒤 보장되는 조건 | 상태가 `RESOLVED` |
| 실패 보장 | 동작이 실패했을 때 보장되는 조건 | 기존 상태가 변경되지 않음 |

### 클래스와 객체

- 클래스(Class): 객체가 가질 상태와 행동을 정의한 타입
- 객체(Object): 클래스를 기반으로 런타임에 생성되어 실제 상태를 가진 인스턴스

클래스가 설계와 규칙을 정의한다면 객체는 그 정의에 따라 생성되어 실행 중에 상태를 가진다.

## 책임 구분

`OPEN → IN_PROGRESS → RESOLVED`처럼 Ticket 하나의 현재 상태만으로 판단할 수 있는 규칙은 Ticket이 직접 보호한다.

| 구성 요소 | 책임 |
|---|---|
| `Ticket` | 현재 상태와 허용된 상태 전이 검증 |
| Application Service | Ticket 조회, 사용자의 행동 권한 확인, 트랜잭션과 저장 조정 |
| Authentication 계층 | 현재 사용자가 누구인지 확인 |
| Controller | 요청을 애플리케이션 호출로 변환하고 결과를 응답으로 변환 |

Service에서만 상태 전이 규칙을 검사하면 다른 Service나 Test가 Ticket을 직접 사용할 때 규칙을 우회할 수 있다. 반대로 Ticket이 상태 전이를 정확히 검사해도 Service에서 권한을 검사하지 않으면 권한이 없는 사용자가 허용된 순서 안에서 다른 사용자의 Ticket 상태를 변경할 수 있다.

## 최소 예제

안전한 Ticket은 범용 Setter를 제공하지 않고 다음과 같이 의도를 나타내는 행동만 제공한다.

```java
void resolve() {
    if (status != TicketStatus.IN_PROGRESS) {
        throw new IllegalStateException(
            "only IN_PROGRESS ticket can be resolved"
        );
    }

    status = TicketStatus.RESOLVED;
}
```

전체 예제의 실행 절차와 관찰 결과는 [티켓 상태 전이 실험](../lab-ticket-state-transition.md)에 기록했다.

## 실패·반례

- 실패 조건: `OPEN` Ticket에 `resolve()`를 호출한다.
- 보호 동작: `IllegalStateException`을 발생시키고 상태를 `OPEN`으로 유지한다.
- 반례: `UnsafeTicket.setStatus()`는 현재 상태를 검사하지 않아 `OPEN → RESOLVED` 직접 변경과 `null` 대입을 허용했다.
- 원인: 필드의 접근 제한과 별개로 공개된 변경 인터페이스가 객체의 규칙을 보호하지 않았다.

`setStatus(TicketStatus)`의 매개변수에는 임의의 문자열을 직접 전달할 수 없다. 문제는 `null`이나 현재 상태에서 허용되지 않는 다른 `TicketStatus` 값을 전달할 수 있다는 점이다.

## 대안과 사용 경계

| 선택지 | 적합한 조건 | 비용·위험 |
|---|---|---|
| 의도가 드러나는 도메인 행동 | 상태 전이마다 의미와 규칙이 있을 때 | 행동별 메서드와 검증 코드가 필요함 |
| 제한된 내부 Setter | ORM 매핑 등 기술적 제약 때문에 필요할 때 | 접근 범위를 넓히면 규칙 우회 가능성이 생김 |
| Application Service 검증 | 사용자 권한이나 여러 객체를 함께 판단할 때 | 도메인 객체 하나의 규칙까지 맡으면 우회 경로가 생길 수 있음 |

- 사용할 조건: 객체가 상태를 가지며 허용된 변경 순서나 값의 범위가 있을 때
- 사용하지 않을 조건: 단순 데이터 전달처럼 행동과 불변조건이 없는 값 구조
- Ticket 예제에서의 적용: 상태 변경을 의도가 드러나는 행동 Method로 제한하고, 전이 조건을 객체 내부에서 검사한다.

## JShell과 JUnit

### JShell

JShell은 Java 9부터 제공되는 Java REPL(Read-Eval-Print Loop) 도구다. 클래스나 `main` 메서드를 포함한 프로젝트를 먼저 만들지 않고도 Java 선언문, 문장과 표현식을 입력해 결과를 확인할 수 있다. 세션에서 만든 변수와 클래스는 기본적으로 현재 세션에만 존재하며, `/exit`로 종료해도 소스 파일이나 정식 프로젝트 산출물로 자동 저장되지 않는다.

### JUnit

JUnit은 JVM에서 반복 가능한 자동 테스트를 작성하고 실행하기 위한 테스트 프레임워크 생태계다. 단언문을 사용해 반환값, 객체 상태와 예외 발생 여부 등이 예상과 일치하는지 검증할 수 있다. 거부 전이에서는 Exception Type뿐 아니라 행동 후 객체 상태가 유지되는지도 별도로 확인해야 한다.
