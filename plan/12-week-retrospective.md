# SW AI Lab 심화과정 12주 회고

> 학습 기간: 2026-08-18 ~ 2026-11-09
> 범위: 학습 결과, 확인한 증거, 수료 후 4–8주 개발과 포트폴리오 정리

## 판단이 달라진 지점

### 화면에서 실패를 봤을 때 저장 여부를 확인하는 기준

11월 7일에는 상태 변경 요청의 `500`을 보고 요청 전달이나 저장이 실패했다고 해석했고, 요청 전후 상태가 같은지 보겠다고 답했다. 이후 DB가 Commit을 거부한 사례와 Commit 뒤 응답만 유실된 사례를 구분했다. 첫 경우에는 DB에서 상태 버전과 새 이력이 함께 되돌아갔는지 확인할 수 있다. 두 번째는 원래 UUID의 이력이 이미 남아 있을 수 있다. 현재 상태는 다른 요청으로도 바뀌므로 그 제출을 식별할 수 있는 이력이 필요했다. 11월 9일에는 최초 문의에 같은 기준을 적용해 원래 UUID와 제목, 본문을 유지하고 동일 Ticket ID와 DB의 저장 건수를 비교한다고 설명했다. [11월 7일 학습 기록](../week12/study-notes/2026-11-07-study-questions.md), [11월 9일 적용 문답](../week12/study-notes/2026-11-09-study-questions.md)

### 접근이 막혔다는 사실과 기존 기록이 보존됐다는 사실

권한 회수 사례에서는 접근이 차단됐고 조회만 했으니 기록 보존도 문제가 없을 것으로 봤다. 실험에서 보낸 요청은 과거 제출의 UUID를 담은 재확인 POST였다. 같은 세션에서 회수 전에는 `200`, 회수 후에는 `404`를 관찰했다. 기록 보존의 직접 근거로는 기존 확인 행 전체를 전후 비교한 SQL을 들었다. 행 수가 같아도 작성자나 원래 가리키던 Message가 달라질 수 있다는 점이 다른 보존 검사에도 적용된다. [11월 7일 보존 문답](../week12/study-notes/2026-11-07-study-questions.md#보존과-접근-권한을-검증하는-방법)

### 누가 요청을 시작하고 어디서 응답을 받는지

7주차 초반에는 AI 응답도 브라우저의 요청처럼 인증과 CSRF 필터를 거쳐 Controller로 들어오는 것으로 생각했다. 실제 Lab에서 브라우저는 문의를 접수하고, 서버 Worker가 Provider Adapter를 통해 별도의 외부 요청을 시작한다. 그 응답은 서버 내부 HTTP Client가 받고, 앱이 출력과 현재 실행권을 확인한 뒤 제안을 저장한다. 요청 방향을 그려 보면서 Spring AI가 담당하는 호출과 형식 요청, 앱이 담당하는 검증과 저장을 나눠 설명할 수 있었다. [7주차 WIL](../week7/wil.md#schema를-통과한-것과-올바른-판단은-다르다)

11월 8일에는 반대로 문제의 가정 자체를 점검했다. UUID K의 변경이 저장되지 않았는데 상태 버전이 3이 됐다면, 중간에 실제로 어떤 상태 변경이 Commit됐는지 물었다. 별도 해결과 명시적 재개를 넣어 타임라인을 완성하자, 기존 K가 없고 기대 버전이 1인 새 변경은 현재 버전 3과 충돌한다고 설명할 수 있었다. [11월 8일 학습 기록](../week12/study-notes/2026-11-08-study-questions.md)

## 과정에서 확인한 범위

기술 심화 공지에서 별도 실습 프로젝트가 제시된 기술 분야는 12개였다. 12개 모두에서 개념을 학습하거나 실습한 기록을 확인했다. 분야별로 선택한 주제와 확인한 범위는 아래와 같다.

| 분야 | 학습하거나 실습한 범위 |
|---|---|
| 객체지향 | 문의 객체가 상태 전이 규칙을 지키도록 설계하고 JUnit으로 확인했다. Strategy와 합성도 별도 예제로 비교했다. [1주차 WIL](../week1/wil.md) |
| Git | 작업 트리의 상태와 변경 내용을 확인하고 작은 커밋으로 기록했다. 스테이징 차이와 복구 명령의 설명은 1주차에 부분 완료로 기록했다. [Git 점검](../week1/wil.md#계획-대비-결과) |
| 웹의 동작원리 | REST API와 HTTP 오류 응답을 비교하고, 실제 브라우저에서 Fetch와 CORS 요청을 확인했다. [2주차 WIL](../week2/wil.md), [6주차 WIL](../week6/wil.md) |
| 웹 백엔드 | Spring MVC에서 요청이 지나가는 계층과 입력 검증, 예외 처리의 책임을 다뤘다. 이후 공식 답변과 담당자 배정에도 적용했다. [2주차 WIL](../week2/wil.md), [10주차 기록](../week10/README.md) |

| 웹 프런트엔드 | 이벤트 루프, Promise와 렌더링을 학습했다. 5주차는 부분 완료였고, 6주차에 문의 화면과 비동기 요청 처리를 연결했다. [5주차 WIL](../week5/wil.md), [6주차 WIL](../week6/wil.md) |

LoRA와 VLM, 미니 셸은 남은 세부 주제로 두었다. 10–12주차에는 앞서 학습한 백엔드, DB와 브라우저 검증을 공식 답변, 인계, 고객 후속 글, 확인과 상태 변경에 적용했다. 이 기능의 근거는 로컬 PostgreSQL, 대표 브라우저와 해당 Commit의 CI다. 운영은 수료 후 파일럿에서 검증한다. [10주차 기록](../week10/README.md), [11주차 기록](../week11/README.md), [12주차 WIL](../week12/wil.md)

업무 정책은 사용자가 검토했다. 예를 들어 인계 시 현재 담당자와 배정 버전을 검사하고, 고객의 후속 글과 해결 상태 변경을 서로 다른 명령으로 두었다. Codex는 기술 계약, 구현, 테스트, 자료 정리를 도왔다. 사용자 직접 실행, 문답에서의 설명, 자동화 검증은 각각의 근거로 남겼다. [11월 4일 실행과 CI 기록](../week12/lab-reports/2026-11-04-final-review-publication.md)

## 마감과 후속 범위

- 11월 9일에 12주차 WIL과 전체 회고를 작성했다. 10–12주차 통합 블로그 작성과 포럼 등록도 같은 날 작성자가 완료했다고 확인했다.
- 현재 Lab은 한 건의 문의가 접수된 뒤 답변, 인계, 고객 후속 글, 확인과 명시적 해결/재개까지 이어지는 학습 구현이다. 최초 접수 재확인, 개인별 운영 계정, 데이터 보호, 배포 후보 검증은 첫 파일럿의 과제다. 승인표의 G0는 결정 대기, G1–G5는 검증 대기다. [Lab 로드맵의 출시 기준](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/main/docs/roadmap.md#파일럿-출시-기준)
- AgentOps, 인물 관계 V2와 개인정보 모델 고도화는 기존 후속 범위로 관리한다. 첫 파일럿은 한 조직의 텍스트 지원 서비스에서 초대받은 사용자와 진행하며 AI는 비활성 상태로 시작한다. [파일럿 범위와 결정 로그](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/main/docs/pilot-decision-log.md)

## 수료 후 4–8주 진행안

세부 개발 순서와 합격 기준은 [Lab 로드맵](https://github.com/HyungminYoon1/ai-helpdesk-learning-lab/blob/main/docs/roadmap.md)에 둔다. 아래는 선행 조건을 기준으로 묶은 진행안이다. 취업 일정에 맞춰 작업 시간을 정하고, 과정 중 사용한 기술 과업 주 6시간을 시작 기준으로 삼는다. 주차 수는 예상 작업 묶음이며 출시일은 출시 기준을 충족한 뒤 정한다.

| 기간 | 개발과 학습 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 1–2주 | 최초 접수 재확인의 API와 DB 계약을 좁혀 로컬에서 구현한다. 계정 운영 방식과 기존 접수 호출자의 전환 조건을 병행 검토한다. | 같은 계정과 UUID의 `201/200`, 내용 변경의 `409`, 동시 요청과 응답 유실 뒤 같은 Ticket ID, Rollback 뒤 새 행 0건을 대조한다. |
| 3–4주 | 앞 단계 근거와 계정 운영 결정을 바탕으로 개인별 초대, 복구, 비활성화와 서비스 권한을 검증한다. 내 문의와 직원의 미배정 업무 진입 경로를 연결한다. | 다른 고객과 다른 서비스의 접근이 차단된다. 권한 회수 뒤 기존 세션을 검증하고 접수부터 재개까지 합성 계정으로 수행한다. |
| 5–6주, 필요 시 | 승인된 보관과 삭제 정책을 기준으로 접근 제한, 로그, 반복 접수 대응과 백업 복원 뒤 재노출 방지를 검증한다. | 격리 복원본에 삭제 기록을 반영한 뒤 고객 화면과 API의 재노출 및 DB 참조를 대조한다. |
| 7–8주, 선행 검증 뒤 | 별도 검증 환경의 후보 Digest, HTTPS, 빈 DB 설치, 부하와 복구를 점검한다. | 확정한 G0–G5 근거를 후보에 연결하고 운영 책임자와 데이터 책임자의 판정을 기록한다. |

포트폴리오에서는 '응답 유실 뒤 원래 제출 재확인'과 '권한 회수 뒤 접근 차단 및 행 보존'을 두 개의 짧은 사례로 정리한다. Java 백엔드 면접에서는 같은 Ticket의 잠금과 Commit, AI/AX 면접에서는 접수와 Worker의 분리 및 출력 검증을 각각 실제 관찰 범위에서 설명한다. 첫 복습은 최초 문의의 응답 유실 사례를 DB 증거까지 포함해 자기 말로 다시 설명하는 것이다.
