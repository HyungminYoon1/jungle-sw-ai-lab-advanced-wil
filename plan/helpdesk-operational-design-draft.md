# AI Helpdesk 실사용 설계 초안

> 작성일: 2026-10-24
> 상태: O1~O6 Accepted. 10/24 별도 요청으로 로컬 구현과 Test 착수. 실서비스 준비 전체는 Draft
> 대상: 향후 작성자가 운영할 소규모 서비스의 고객지원 또는 조직 내부 IT 문의
> 현재 구현 기준: Lab 194cca2, V9. 이 문서는 구현 또는 운영 준비 완료 증거가 아님

## 1. 해결하려는 문제와 완료의 의미

문의 원문과 대응 이력을 잃지 않고, 누가 다음 조치를 책임지는지 분명히 하며, 고객이 자신의 문의에 대한 답변을 확인하게 한다. AI는 긴 문의의 요약, 분류와 우선순위를 제안해 담당자의 판단을 보조한다. AI 없이도 접수, 담당자 응대와 이력 조회는 동작해야 한다.

실사용의 목표는 'AI 응답을 받는다'가 아니라 '고객이 문의하고, 담당자가 이어서 대응하고, 필요한 추가 질문을 주고받으며 처리 결과를 확인한다'이다. 고객의 문제 해결 여부와 AI Job 성공 여부를 같은 상태로 취급하지 않는다. 처리시간 감소나 응대 품질 향상은 이후 Pilot에서 측정할 목표이지 현재 입증한 효과가 아니다.

[ADR-0012](./decisions/0012-helpdesk-operational-target.md)는 이 활용 목적을 기록한다. 학습 과정의 완료와 실서비스 출시를 구분하며, 후속 기능 전체를 Week 10 또는 12주 안에 완료한다고 약속하지 않는다.

## 2. 현재 기반과 실제 사용 전의 차이

| 영역 | 현재 확인한 기반 | 실사용 전 필요한 작업 |
|---|---|---|
| 접수와 이력 | 문의 원문, 공식 답변과 정정, 소유권, 같은 제출 중복 방지 | 고객의 후속 메시지, 내 문의와 담당 업무 목록, 고객이 이해할 수 있는 처리 안내 |
| 담당 책임 | AGENT Role에 따른 답변 허용. 배정 기능 없음 | 책임 담당자 배정, 인계, 미배정 업무 확인, 변경 이력 |
| 인증 | 설정 계정의 Session 로그인과 영속 내부 ID 연결 | 실제 개인별 계정 발급과 비활성화, 권한 변경 및 Session 정책. 고객 서비스 인증 연동 또는 인증 저장소 이전 방식은 별도 선정 |
| AI | 합성 입력의 처리 및 실패 경계, 검증된 제안 저장 | 실제 입력 범위, 외부 전송과 보관 정책, 품질 및 개인정보 평가, 운영 한도. 승인 전 일반 입력 AI는 비활성 |
| 운영 | 과거 Cloud 배포와 복구 실험, CI와 Image 검증 | 새 버전의 배포, 복원 훈련, 장애 대응, 접근 통제, 운영 예산과 유지 시간 확정 |

지금 계정 설정이나 합성 전용 개인정보 검사를 그대로 두고 실제 고객에게 공개하지 않는다. 고객지원용 계정과 조직 내부 계정을 같은 공용 USER 계정으로 운영하지 않는다.

## 3. O3. 한 조직의 여러 자사 앱을 공통 Helpdesk로 지원

**합의, 2026-10-24:** 한 운영 조직의 여러 자사 앱을 Helpdesk 하나와 DB 하나에서 서비스별로 구분한다. 처음의 '한 서비스 또는 한 조직별 별도 배포'라는 표현을 이 범위로 명확히 했다. 적용 대상 앱마다 Source를 복사하거나 App과 DB를 하나씩 운영하지 않는다. 고객은 여전히 자기 문의만 읽고 지원 직원의 접근 범위도 서버가 검사한다. 내부 IT를 함께 운영한다면 같은 조직이라는 이유만으로 모든 직원에게 문의를 공개하지 않는다. 구체적인 직원 조회 범위는 O5에서 검토한다.

여기서 서비스는 지원 대상 제품 또는 앱이고, 조직은 독립적인 운영 주체다. 자사 앱 A와 B는 같은 지원 조직에 속할 수 있지만 다른 회사 C는 별도 조직이다. 서비스 구분 컬럼은 여러 조직의 격리를 구현한 tenant 경계가 아니다.

| 안 | 비용과 운영 특성 | 현재 판단 |
|---|---|---|
| 적용 앱마다 전용 App 및 DB | 최소 실행 자원과 운영 단위가 반복될 수 있음 | 기본안으로 권하지 않음 |
| 같은 조직의 여러 앱을 하나의 Helpdesk에서 구분 | 공통 기반을 재사용하되 서비스별 접근 검사가 필요 | 사용자 합의, 현재 코드에는 미적용 |
| 여러 독립 조직이 같은 App 및 DB를 공유 | 공유 자원의 비용 효율을 기대할 수 있으나 조직 간 격리, 부하 및 운영 영향 통제가 추가됨 | 외부 조직에 제공할 필요가 생기면 별도 SaaS 설계 |

AWS도 [전용 Silo의 유휴 자원과 운영 비용](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/silo-isolation.html), [공유 Pool의 효율과 격리 위험](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pool-isolation.html)을 함께 설명한다. 또한 [SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)는 Silo와 Pool 및 혼합형 모두 SaaS에서 가능하다고 설명한다. SaaS라는 제공 방식과 모든 DB를 공유한다는 배포 방식은 동의어가 아니다. 이 자료를 바탕으로 한 조직의 앱을 먼저 묶는 안을 제안했으며, 현재 구성의 월 금액이나 절감 배수를 산정한 것은 아니다.

여러 회사가 같은 DB를 공유하는 SaaS, 동적 조직 생성과 교차 조직 담당자는 별도 설계로 남긴다. 이 방식을 나중에 채택하면 모든 조회, FK와 Unique, Job 입력, 파일 및 Log의 조직 경계를 다시 검토해야 한다. 지금 컬럼 하나를 추가한 것으로 다중 조직 격리를 확보했다고 하지 않는다.

처음부터 외부의 독립 조직들에게 공유형 SaaS를 제공하는 것이 주목적이라면 이 권장안의 전제부터 다시 검토한다. 한 조직용 모델을 나중에 저비용으로 자동 전환할 수 있다고 약속하지 않는다. 공통 조직의 자사 앱 운영과 여러 고객 조직을 대상으로 하는 사업은 구분해야 한다.

초기 구조는 기존 Controller / Application Service / Domain / Repository와 PostgreSQL, Application 내부 Worker를 유지하는 안이다. 실제 필요 없이 Microservice, 분산 Queue나 Kubernetes를 추가하지 않는다. 단일 App의 재시작 시 재로그인하는 정책을 허용할지, 다중 App 및 공유 Session이 필요한지도 운영 요구에 맞춰 별도로 정한다.

내부 IT의 민감 문의를 일반 고객지원과 동일하게 모든 직원에게 공개하지 않는다. 비공개 요청, 지원팀별 조회와 관리자 권한 범위는 실제 대상 조직을 정한 뒤 확정한다. 이 권한 계약이 준비되지 않은 범주의 민감 업무는 Pilot 대상에 포함하지 않는다.

## 4. 담당자 한 명과 여러 사람의 협력은 양립한다

권장안은 '현재 책임 담당자 한 명, 필요한 협력자는 별도'다. 여러 담당자가 동시에 고객에게 독립적인 답변을 보내는 방식 대신 책임자가 대응을 정리한다. 협력자는 향후 권한 범위 안에서 조회 또는 내부 의견을 제공할 수 있지만, 내부 메모 기능이 이미 있다는 뜻은 아니다.

| 구분 | 의미 | 바뀌지 않아야 할 점 |
|---|---|---|
| 문의 등록자 | 문의를 소유한 고객 또는 직원 | 담당자가 바뀌어도 고객 소유권은 유지 |
| 현재 책임 담당자 | 미배정이면 없음, 배정되면 한 명 | AGENT Role만으로 현재 담당자가 되지는 않음 |
| 메시지 작성자 | 각 문의와 답변을 실제로 작성한 사람 | 인계 후에도 과거 작성자를 새 담당자로 바꾸지 않음 |
| AI Job 실행권 | Worker가 특정 Attempt를 처리하는 권한 | 사람의 담당자 배정과 별개 |

[Zendesk의 배정 안내](https://support.zendesk.com/hc/en-us/articles/4408887127450-Manually-assigning-a-ticket)는 담당 Agent와 Group 배정을 설명하고, [협업 안내](https://support.zendesk.com/hc/en-us/articles/4408829504154-Collaboration-overview)는 내부 의견과 다른 팀의 참여를 별도로 설명한다. 이를 참고해 책임과 협력을 분리한다. 해당 제품이 비담당자의 공개 답변을 항상 금지한다는 뜻은 아니다. 아래의 '현재 담당자만 공식 답변'은 우리 첫 운영 버전에 채택한 더 제한적인 정책이며 현재 Lab에는 미구현이다.

## 5. 배정과 인계 정책: 합의와 검토안 구분

### O1. 공식 답변과 조회

**합의, 2026-10-24:** 새 공식 답변과 정정은 현재 책임 담당자만 작성한다. 지원관리자도 먼저 명시적으로 재배정한 뒤 답변한다. 현재 Lab에 구현된 정책은 아니며 다음 기능의 권한 계약으로 반영한다. 아래 조회 범위와 세부 운영 조건은 별도 설계로 구체화한다.

- 공식 답변과 정정은 현재 책임 담당자만 새로 저장한다. 미배정 문의는 먼저 담당자를 정한다.
- 지원관리자도 명시적으로 재배정한 뒤 대응한다. 지원관리자의 실제 Role 이름과 부여 절차는 아직 확정하지 않는다.
- 다른 담당자의 조회는 지원 조직의 접근 범위 안에서만 허용한다. 담당자가 아니라는 이유로 고객 소유권 검사를 생략하지 않는다.
- 기존의 등록자 미확인 제한은 별도로 유지한다. 담당자가 정해져도 고객 등록자를 모르는 Ticket에 답변을 공개하지 않는다.
- 배정과 답변은 Ticket 상태를 자동 변경하지 않는다. RESOLVED의 추가 안내와 답변 및 상태 변경 분리는 기존 원칙을 유지하는 안이다.

### O2. 배정 시작과 교체

**합의, 2026-10-24:** 권한 있는 인간 직원이 미배정 문의를 직접 가져가고, 이후 교체는 현재 담당자 또는 지원관리자의 명시적 인계로 처리한다. 자동 분배나 타인의 업무를 임의로 가져오는 방식은 채택하지 않았다. 인계 효력이 상대방 수락 없이 발생하는지는 O4에서 추가 확인한다.

'가져오기'는 외부 AI나 Worker가 아니라 인증된 인간 직원 AGENT가 화면에서 '담당하기'를 선택하는 동작이다. '아무나'가 아니라 해당 문의에 접근하고 배정받을 권한이 있는 활성 직원만 가능하다. 먼저 클릭한 순서는 보장하지 않으며, DB가 미배정 여부를 확인하고 먼저 Commit한 배정이 유효하다. 앞선 Transaction이 Rollback되면 기다리던 다른 직원의 요청이 성공할 수 있다. FIFO 업무 분배나 자동 배정은 아니다.

자기 선택 방식에는 쉬운 문의만 가져가거나 오래된 문의가 방치될 위험이 있다. 따라서 미배정 목록에서 대기 시각과 정렬을 제공하고 지원관리자가 누락을 확인할 수 있어야 한다. 나중에 필요한 경우 순환 배정이나 수동 지정을 검토하되 현재 자동 배정 정책으로 추가하지 않는다.

- 활성 AGENT는 접근 가능한 미배정 문의를 자기 업무로 가져갈 수 있다. 동시에 두 명이 가져가면 한 명만 성공하고 다른 요청은 충돌로 처리한다.
- 현재 담당자 또는 지원관리자는 같은 지원 범위의 활성 AGENT에게 인계한다. 다른 AGENT가 남의 업무를 임의로 빼앗는 동작은 허용하지 않는다.
- 인계의 확정 시점은 O4의 검토안이다. 상대방 수락 없이 Commit으로 적용하는 안을 권하지만 아직 합의하지 않았다.
- 누가, 언제, 누구에게, 왜 인계했는지 기록한다. 응답을 잃은 동일 인계 요청은 같은 제출 ID로 확인하며 자동으로 다른 대상에게 다시 배정하지 않는다.
- 직원 지원권한 비활성화와 기존 업무의 처리 방식은 O6에서 검토한다. 과거 작성자 이력은 변경하지 않는다.

O1~O3은 사용자 동의로 확정됐다. 인계의 확정 시점과 세부 조회 및 권한 회수 조건은 아래에서 추가 검토한다. 업무 코드와 Migration은 아직 바꾸지 않았으며 현재 P1의 동작과 후속 O1~O3의 미구현 상태를 구분한다.

## 6. 데이터와 Transaction의 기술 초안

다음은 후속 Migration 검토 대상이며 V9를 편집하거나 새 DDL을 실행하지 않는다.

구체적인 컬럼, 제약, 요청과 응답 및 실패 사례는 [배정과 인계 기술 계약 초안](../week10/ticket-assignment-contract-draft.md)에 기록했다. O1~O3을 합의된 전제로 반영하되 O4~O6의 추가 검토에 따라 세부 흐름을 조정한다. 현재 API에 적용된 것으로 취급하지 않는다.

| 대상 | 후보 데이터 | 책임 |
|---|---|---|
| Ticket | service_id, nullable assignee_user_id, assignment_version | 지원 대상 서비스, 현재 담당자 한 명과 배정 변경 버전. 미배정은 NULL이며 가짜 담당자 ID를 만들지 않음 |
| 배정 이력 | Ticket, 이전 및 새 담당자, 변경 Actor, 서버 시각, 이유, 배정 버전, 인계 제출 ID | 현재 상태 변경과 같은 Transaction으로 저장. 변경 이력 실패 시 배정도 Rollback |
| 계정 및 권한 | 영속 사용자 ID와 계정 활성 상태, 서비스별 직원 권한 및 활성 상태 | 존재하는 사용자라는 FK만으로 담당자 자격이 입증되지는 않음. 실제 인증과 권한 수명은 별도 계약 |
| 기존 Message | 작성자, 제출 UUID와 정정 참조 유지 | 인계가 과거 본문, 작성자, 문의 등록자 또는 AI 입력을 바꾸지 않음 |

공식 답변과 인계는 같은 Ticket Row를 먼저 잠그고 최신 배정과 권한을 확인한 뒤 저장하는 안이다. 인계 요청의 예상 배정 버전과 현재 버전이 다르면 조용히 덮어쓰지 않고 충돌로 알린다. 여러 Row를 잠글 필요가 있으면 모든 쓰기 경로의 잠금 순서를 통일한다.

새 답변에도 예상 배정 버전을 요구하고 신규 답변의 저장 당시 버전을 기록하는 기술안을 권한다. A→B→A처럼 담당자가 돌아온 뒤 오래된 초안을 제출하는 경우까지 포함한다. 현재 엄격한 DTO와 재전송 비교 계약을 명시적으로 개정해야 하므로 기술 검토안으로 구분하며, 현재 API에 미래 필드를 먼저 보내서는 안 된다.

배정 변경 후 이전 담당자의 Session이나 화면이 남아 있어도 새 답변의 권한은 DB 최신 상태로 다시 검사한다. 먼저 답변이 Commit됐으면 그 답변은 남고 이후 인계가 진행된다. 먼저 인계가 Commit됐으면 이전 담당자의 새 답변은 거부한다. '브라우저에서 버튼을 숨겼다'는 것으로 이 경쟁 조건을 해결하지 않는다.

이미 저장한 답변의 응답만 잃은 경우도 별도로 설계한다. 이전 담당자가 여전히 해당 대화의 조회 권한을 가진다면 자신의 동일 제출 결과를 200으로 재확인하고 새 답변은 만들지 않는 안을 권한다. 조회 권한이나 계정 활성 권한 자체를 잃었다면 재전송 키만으로 결과를 공개하지 않는다. 새로운 쓰기의 배정 검사와 이미 저장된 결과의 확인 순서는 별도 Test로 고정한다.

업무 담당은 수시간 또는 수일 유지할 수 있지만 DB Row Lock은 저장 Transaction 동안만 유지한다. 답변을 작성하는 시간 전체나 외부 AI 호출 동안 잠그지 않는다. 담당자가 한 명이어도 여러 탭, 인계와 답변의 경쟁, 재전송이 있으므로 짧은 잠금과 Unique는 계속 필요하다. 필요한 FK 및 조회 Index는 실제 담당 업무 목록 Query와 함께 검토하며 성능 개선 수치를 미리 주장하지 않는다.

## 7. 실사용까지의 단계와 출시 조건

| 단계 | 결과물 | 진입 또는 완료 조건 |
|---|---|---|
| 현재 기반 | 접수, AI 처리 경계, 공식 답변과 대화 조회의 로컬 검증 | 기존 근거를 유지. 운영 준비 완료로 표시하지 않음 |
| 지원 업무 연결 | 배정 및 인계, 고객 후속 메시지, 내 문의와 미배정 및 내 담당 목록, 명시적 상태 처리 | 핵심 정책 승인 후 작은 기능별 구현. 각각 권한, 중복, 동시성 및 기존 데이터 보존 Test |
| 제한된 Pilot 준비 | 실제 개인별 계정과 권한 수명, 안전한 오류 화면, 문의 누락 탐지, 보관 및 삭제 절차 | 먼저 합성 데이터로 통합 검증. 개인정보와 접근 범위를 확정하기 전 실제 데이터 투입 금지 |
| 운영 인수 | 새 Image의 배포 및 복원, 장애 알림과 대응, 사용 안내와 운영 비용 | Backup 복원으로 문의 및 답변 대조. 운영 담당자, 유지 시간, 실패 대응과 예산 합의 |

기본 지원 업무는 AI를 꺼도 동작해야 한다. AI 활성화는 독립 Gate로 둔다. 실제 문의의 외부 전송 허용 범위, 입력 전처리 실패 시 차단, Prompt Injection과 출력 검증, 내용 품질 평가, Provider 장애와 비용 한도를 확인한 뒤 켠다. 불확실한 개인정보 입력은 검사 실패를 무시해 보내지 않는다. 인물 관계 V2나 특정 경량 모델 도입이 유일한 해결책이라고 미리 고정하지 않는다.

초기 Pilot에서 내부 메모, 첨부 파일과 알림이 필요한지는 사용 시나리오로 선정한다. 내부 메모를 도입한다면 고객 대화 조회와 알림에 노출되지 않는 별도 공개 범위가 필수다. Dashboard, 자동 배정과 다중 조직 SaaS는 기본 업무와 운영 Gate를 대신하지 않는다.

보관 및 삭제 기간, 첨부 파일 허용 여부, 요청 제한, 운영 알림 채널, 복구 목표와 가용성은 아직 정하지 않았다. 기존 학습 Log의 365일 보관을 새 고객 원문의 영구 보관 근거로 사용하지 않는다. 기존 월 3만 원 학습 예산은 실서비스의 가용성이나 새 리소스 실행을 승인하는 계약이 아니며 실제 운영 예산을 별도로 확인한다.

## 8. 먼저 검증할 실패 사례

1. 두 AGENT가 같은 미배정 문의를 가져가도 현재 담당자와 성공한 변경 이력은 한 건으로 정합성을 유지한다.
2. 인계와 이전 담당자의 새 답변이 동시에 실행될 때 같은 Ticket 잠금과 Commit 순서에 맞는 한 결과를 낸다.
3. 인계 뒤 과거 문의, 답변 작성자와 정정 참조, 고객 소유권, AI Job 입력 및 예약은 변하지 않는다.
4. 변경 이력 저장 실패는 배정도 Rollback한다. 이전에 Commit한 고객 문의를 취소하지 않는다.
5. 비활성 계정이나 다른 지원 범위의 계정을 인계 대상으로 지정해도 서버가 거부한다.
6. 결과 미확인 답변 및 인계 재확인은 같은 제출을 중복 저장하지 않으며, 권한이 사라졌으면 결과를 누출하지 않는다.
7. 고객 후속 메시지의 공개 범위와 AI 재처리 여부는 별도 계약으로 확인한다. 최신 Message를 임의로 기존 Job 입력에 덮어쓰지 않는다.
8. 실제 출시 전 USER A/B와 AGENT A/B, 지원관리자의 API 및 Browser 흐름과 실제 PostgreSQL Row를 대조한다.

## 9. 구현 전 남은 핵심 정책

| 정책 | 상태 | 확인한 내용 또는 남은 선택 |
|---|---|---|
| O1 새 공식 답변 권한 | 합의 | 현재 담당자만 작성. 지원관리자도 재배정 후 대응 |
| O2 배정과 인계 주체 | 합의 | 직원의 직접 가져오기, 현재 담당자 또는 지원관리자의 명시적 인계 |
| O3 조직 및 서비스 경계 | 합의 | 한 운영 조직의 여러 자사 앱을 공통 Helpdesk에서 서비스별로 구분 |
| O4 인계의 확정 시점 | 합의 | 상대방 수락 대기 없이 Commit 즉시 적용 |
| O5 같은 서비스 직원의 조회 범위 | 합의 | 활성 직원은 같은 서비스의 미배정 및 다른 담당자 문의와 배정 이력 조회 가능 |
| O6 직원 지원권한 회수 | 합의 | 새 직원 조회와 쓰기를 거부. 기존 배정과 이력을 유지하고 관리자가 명시적으로 재배정 |

### O4. 인계의 확정 시점: 합의

상대방 수락 대기 없이 인계 Transaction의 Commit으로 새 담당자가 책임을 맡는다. 업무 목록은 DB의 새 배정을 기준으로 표시하며, 미래의 알림 발송 실패가 이미 확정된 인계를 취소하지 않는다. 수락 대기를 채택하면 기존 담당자의 책임 유지, 수락 및 거절, 미응답과 취소 상태를 추가 설계해야 하므로 첫 버전에는 즉시 인계를 권한다. 이는 아직 합의 전이며 알림 기능을 이번에 구현한다는 뜻은 아니다.

### O5. 같은 서비스 직원의 조회 범위: 합의

해당 서비스의 활성 지원 직원은 미배정 문의와 다른 담당자의 문의 및 배정 이력을 조회할 수 있다. 새 공식 답변은 O1에 따라 현재 담당자만 작성한다. 다른 서비스는 별도로 권한을 부여받지 않으면 조회할 수 없고 지원관리자의 범위도 해당 서비스로 제한한다. 고객은 자기 문의만 조회한다. 이 기본 권한으로 처리할 수 없는 민감 내부 문의는 첫 Pilot 범위에서 제외하고 별도 비공개 권한을 설계한다.

### O6. 직원 지원권한 회수: 합의

해당 서비스의 직원 권한을 비활성화하면 기존 Session이 남아 있어도 그 권한으로 하는 새 직원 조회와 쓰기는 서버에서 거부한다. 기존 담당자 및 변경 이력을 자동 삭제하거나 문의를 자동 해제하지 않고 지원관리자가 남은 업무를 확인해 명시적으로 재배정한다. 권한 회수를 인계 성공 때까지 지연하지 않는다. 일반 USER로 자기 문의를 읽는 권한과 계정 전체의 로그인 비활성화 및 Session 폐기는 별도 인증 정책으로 구분한다.

O4~O6을 확인한 뒤 배정과 인계 첫 버전의 기술 계약을 확정한다. 버전, Unique와 FK, 재전송 및 잠금 순서는 기존 합의를 지키는 기술 설계로 구체화하며 같은 업무 정책을 반복 질문하지 않는다. 실제 인증 모듈, 고객 후속 메시지와 운영 및 보관 정책 전체를 이번 기능의 정책 검토에 섞지 않는다. 이번 문서 갱신은 업무 코드 변경, 배포, 실제 AI 호출, Commit 또는 Push의 자동 승인이 아니다.
