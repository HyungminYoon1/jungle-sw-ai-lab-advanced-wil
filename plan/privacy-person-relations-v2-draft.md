# 개인정보 검사 결과의 인물 관계 계약 초안

> 상태: Deferred — 독립 구조 검증·관계 보존 치환은 Test 완료. Guard·Provider 전송 계약과 Main 조립은 배포 마감 이후 후속 과업
> 기준: [ADR 0003의 실명 최소화와 관계 보존 정책](./decisions/0003-contextual-person-masking.md)

10/19 승인한 [배포 우선 결정](./decisions/0009-deployment-first-and-deferred-privacy-enhancement.md)에 따라 후속 구현을 분리한다. 계약과 구현·평가 근거는 보존하며, 제한된 합성 배포 실험을 위해 V2를 먼저 연결하지 않는다. 일반 입력으로 AI 처리를 확장할 때 다시 검토한다.

## 목적과 현재 계약

실명은 전송용 복사본에서 가리되, 같은 사람이 반복 등장했는지 다른 사람의 정보가 노출됐는지는 유지한다. 이름이 같다는 이유만으로 동일인을 확정하거나 다른 문의의 사람과 연결하지 않는다.

현재 `AiPrivacyScanResultValidator`는 `{completed, spans}`와 항목별 `field`·`start`·`end`·`type`만 허용한다. `AiInputSpanMasker.DetectedSpan`도 같은 네 정보를 담고 PERSON은 공통 `[PERSON_REDACTED]`로 바꾼다. 관계 필드를 기존 결과에 덧붙이면 현재 검증기는 추가 필드로 거부한다. 따라서 기존 계약을 조용히 확장하지 않고 별도 Version으로 검토한다.

## 검토한 선택지

| 안 | 장점 | 문제 |
|---|---|---|
| 같은 이름 문자열을 같은 사람으로 묶음 | 단순함 | 동명이인·표기 차이를 잘못 판단 |
| 각 이름 위치에 서로 다른 사람 번호를 붙임 | 반복 위치를 구분하기 쉬움 | 같은 사람의 반복 등장이나 미확인 관계를 다른 사람으로 왜곡 |
| 등장 위치 번호와 그 사이의 관계를 분리 | 반복 등장·동명이인·미확인을 구분 | 관계 검증과 치환·전송 방식 추가 필요 |

권장안은 세 번째다. `mentionId`는 **사람 ID가 아니라 원문에서 이름이 등장한 위치의 번호**다. 같은 사람이 두 번 등장해도 위치 번호는 두 개이며, 두 번호 사이에 SAME 관계를 둔다.

## JSON 초안

합성 본문 `김철수와 동명이인 김철수`에서 두 이름의 Code Point 범위는 각각 `[0, 3)`과 `[10, 13)`이다.

```json
{
  "schemaVersion": 2,
  "completed": true,
  "spans": [
    {"field": "body", "start": 0, "end": 3, "type": "PERSON", "mentionId": "m1"},
    {"field": "body", "start": 10, "end": 13, "type": "PERSON", "mentionId": "m2"}
  ],
  "personRelations": [
    {"left": "m1", "right": "m2", "relation": "DIFFERENT"}
  ]
}
```

`m1`·`m2`는 이 검사 호출에서만 사용한다. 같은 Message를 다시 검사해도 이전 호출의 번호와 신원 관계를 만들지 않는다. 번호에는 실제 이름·Username·Ticket ID·DB 사용자 ID를 넣지 않는다. PERSON이 아닌 항목은 기존 네 필드만 사용한다.

### 관계 값

- `SAME`: 문맥상 같은 사람으로 판단한 두 등장 위치다.
- `DIFFERENT`: 문맥상 다른 사람으로 판단한 두 등장 위치다. 동명이인 명시는 이 판단의 근거가 된다.
- `UNDETERMINED`: 두 위치 모두 이름으로 탐지했지만 동일인인지 판단하기 어렵다고 명시한 결과다.

이는 Scanner가 보고한 판단이다. 형식 검증만으로 그 판단이 원문에 맞는지 확인한 것은 아니다. 명확한 동명이인을 SAME으로 분류한 응답은 JSON 계약을 지키더라도 내용 평가에서 실패한다.

## 구조 검증 권장안

1. 호출부가 기대 계약 Version을 명시한다. V1·V2를 자동 변환하거나 V1 결과를 이름 문자열 비교로 V2처럼 꾸미지 않는다.
2. V2는 위 Root 필드를 모두 요구한다. PERSON에는 `mentionId`, 다른 종류에는 기존 네 필드만 허용한다. 추가·누락 필드와 타입 강제 변환은 거부한다.
3. 등장 번호는 중복 없는 `m1`부터 `mN`까지의 목록이다. Title 다음 Body, 각 필드의 원문 위치 순으로 대응한다. 같은 위치의 완전히 같은 중복 항목은 하나로 보고, 서로 다른 번호나 종류가 같은 위치를 주장하면 거부한다.
4. 기존 Code Point 범위·두 필드 검증·중복/겹침 거부·Byte/개수 상한을 유지한다. 위치가 다른데 번호가 같아도 거부한다. 같은 사람의 반복 등장은 같은 번호가 아니라 SAME으로 표현한다.
5. `personRelations`는 각 서로 다른 등장 위치 쌍마다 정확히 한 항목을 요구한다. 자기 자신·없는 번호·중복 쌍·알 수 없는 관계 값은 거부한다. PERSON이 0개나 1개이면 빈 배열이다.
6. 관계 항목 누락을 UNDETERMINED로 채우지 않는다. 판정이 어려운 경우에도 Scanner가 그 값을 명시해야 한다. `completed: false`는 유효한 판단 보류로 바꾸지 않는다.
7. 관계표는 SAME의 추이 관계까지 일관된 결과여야 한다. A와 B, B와 C가 SAME인데 A와 C가 DIFFERENT이거나 최종 관계표에서 UNDETERMINED이면 거부하고 임의로 수정하지 않는다. DIFFERENT에는 같은 추이 규칙을 적용하지 않는다.
8. 관계 개수는 PERSON이 N개일 때 `N * (N - 1) / 2`로 증가한다. 별도의 명시적 상한과 기존 응답 Byte 상한을 함께 둔다. 넘으면 일부 쌍을 버려 정상 처리하지 않는다. 실제 상한은 실행 자원 측정 전까지 확정하지 않는다.

관계표의 내부 일관성과 원문에 맞는 의미 판단은 다르다. 전자는 서버 검증기로 확인하고, 후자는 별도의 실제 모델 평가로 확인한다.

## 전송용 표현의 권장 방향

원문 DB는 바꾸지 않는다. 서버가 검증한 위치만 치환하고 등장 번호를 실제 신원으로 해석하지 않는다. SAME이면 같은 인물 표시를 사용할 수 있고, DIFFERENT이면 구분한다. 관계가 UNDETERMINED이면 다른 번호를 붙였다는 이유만으로 다른 사람이라고 표현하지 않는다.

외부 AI에는 치환한 제목·본문과 실명 없는 관계 정보만 전달하는 안을 검토한다. 이때 관계 정보도 원문에서 유도한 입력 데이터이지 Tool 실행이나 권한 변경을 허용하는 지시가 아니다. 원문 이름과 표시의 역변환 목록·원본 위치·실제 사용자 식별자는 함께 보내지 않는다.

미확인 관계는 미확인이라고 전달하며 SAME이나 DIFFERENT로 바꾸지 않는다. 이는 유효한 의미 판단 보류이며, 검사 실행 실패·미완료·필수 필드 누락과 다르다.

독립 치환기는 아래 규칙으로 표시 충돌과 미확인 관계를 처리한다. `AiInputPrivacyGuard`가 새 표시를 다시 치환하지 않도록 하는 검증과 Provider 입력에 관계를 담는 구체적인 형식은 전송 연결 전에 확정할 대상이다. 모델에 전체 본문을 다시 쓰게 하거나 현재 Known Fragment Guard를 제거하지 않는다.

### 독립 치환기의 표현

`AiPrivacyScanResultV2Masker.validateAndMask(title, body, rawResult)`는 같은 원문 문자열로 검증과 치환을 진행한다. 다른 원문에서 검증한 메타데이터를 따로 받는 API는 두지 않는다. 이 호출 내부의 일치와 Scanner 요청·응답의 대응은 다른 경계이므로, 후속 Preparer에서도 검사에 보낸 원문을 그대로 전달해야 한다.

| 보고한 관계 | 치환한 표시 | 반환하는 관계 |
|---|---|---|
| SAME | 같은 `[PERSON_1]` 공유 | 동일 표시에 묶여 있으므로 별도 자기 관계 없음 |
| DIFFERENT | `[PERSON_1]`·`[PERSON_2]` | 두 표시 사이 DIFFERENT |
| UNDETERMINED | `[PERSON_1]`·`[PERSON_2]` | 두 표시 사이 UNDETERMINED |

표시는 Title 다음 Body의 첫 등장 순서로 생성한다. SAME으로 묶인 집합 사이의 관계는 하나씩 반환한다. 다른 표시를 다른 사람이라는 확정으로 읽지 않으며, 미확인 관계를 제거하지 않는다. 결과에는 치환한 제목·본문과 생성 표시 사이의 관계만 있고 원본 위치·이름 역변환 목록·Scanner의 `m1` 같은 번호는 없다.

원문에 예약 접두사 `[PERSON_`가 있으면 생성 표시로 오인하지 않도록 치환 결과 전체를 거부한다. 해당 문자를 원문에서 지우거나 검사 없이 전송하지 않는다. 정상적인 설명 문장에 접두사를 쓴 경우도 AI 준비가 거부될 수 있으며, Escape를 지원하는 Provider 표현은 후속 검토다. 제목·본문을 합친 치환 후 UTF-8 Byte 상한을 명시하되 전체 HTTP Body 상한과 구분한다.

## 검증할 Case

- 같은 이름이지만 동명이인임이 명시됨: 등장 번호 두 개·DIFFERENT.
- 앞서 말한 사람을 다시 지칭함: 등장 번호 두 개·SAME.
- 이름 두 곳을 찾았지만 동일인 판단이 어려움: 명시적인 UNDETERMINED, 원문 이름은 치환하고 관계의 불확실성 유지.
- 이름 두 곳과 `completed: true`를 보냈지만 관계 항목 누락: 계약 위반으로 거부, 외부 Provider 호출 없음.
- 동일한 이름이 다른 문의에 등장함: 이전 문의의 신원이나 번호를 재사용하지 않음.
- SAME·DIFFERENT가 서로 모순됨: 구조적으로 거부. 원문과 다른 일관된 관계 판단은 실제 모델 내용 평가에서 별도 실패.
- 제목·본문의 반복 등장, 이모지 앞뒤 위치, 겹침, 잘못된 참조·종류·Version·응답 상한 초과.
- 치환 결과·실제 전송 직전 Body·DB 원문 보존, 검사 실패의 원문/예약 보존·외부 전송 차단.

## 구조 검증 구현 범위

명시적인 UNDETERMINED는 보존하고 필수 관계 항목의 누락은 거부한다는 처리 원칙을 문답으로 확인했다. Lab의 `AiPrivacyScanResultV2Validator`에 위 구조·범위·참조·일관성 검사를 독립 구현했다. 기존 V1을 수정하거나 새 검사기를 Main에 자동 등록하지 않았다.

생성자로 응답 Byte·원시 Span 개수·관계 개수 상한을 명시한다. 관계 상한 0은 PERSON이 0~1개인 결과만 허용하는 제한 설정이며 배포 기본값은 아니다. 관계 쌍의 방향과 출력 순서는 정규화하되, 누락·잘못된 판정 값을 채우거나 고치지 않는다. 같은 사람이 제3자와 갖는 관계도 같아야 하므로, A=B일 때 A와 C는 DIFFERENT·B와 C는 UNDETERMINED라고 보고한 최종 관계표는 거부한다.

검증기는 불변 메타데이터만 반환하며 원문·JSON을 결과에 보관하지 않는다. 같은 이름 비교·문의 간 신원 연결·원문 의미의 진위 판정은 하지 않는다. 독립 치환기는 같은 호출의 문자열을 검증·치환에 함께 사용하며, Scanner 호출의 입력 결합과 실제 전송 직전 검증은 후속 연결에 포함한다.

구조 검증 단계의 핵심 402개에는 새 V2 Test 172개가 포함된다. 여기에 독립 치환 Test 37개를 추가한 핵심 439개가 통과했다.
