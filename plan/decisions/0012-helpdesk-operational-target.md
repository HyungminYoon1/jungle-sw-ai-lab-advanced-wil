# ADR-0012 Helpdesk의 후속 목표에 실제 지원 업무 활용을 추가한다

> 상태: Accepted — 활용 목적 및 O1~O6. 10/24 별도 로컬 구현·Test·Commit 요청. 실서비스 준비 전체는 Draft
> 결정일: 2026-10-24
> 근거: 작성자가 향후 소규모 서비스 고객지원 또는 조직 내부 IT 문의 창구로 활용할 의사를 밝히고 실사용을 고려한 설계를 요청

## 배경

학습 과정은 제품 기능 수보다 원리, 실제 계층 연결과 실패 검증을 우선했다. Week 10에는 공식 답변과 대화 조회의 첫 확장을 구현했다. 작성자는 문의별 전담 담당자의 필요성을 질문하고, 최종 앱을 실제 운영에 활용할 계획이라고 밝혔다.

기존 학습 완료를 실서비스 출시 완료로 표현할 수는 없다. 설정 계정과 합성 입력 중심 검증을 넘어 계정 수명, 담당 책임, 고객 후속 메시지, 실제 데이터의 접근 및 외부 전송, 운영과 복구 조건을 별도로 설계할 필요가 있다.

## 검토한 선택지

| 안 | 장점 | 한계 |
|---|---|---|
| 학습용 예제로만 유지 | 범위가 작음 | 사용자가 밝힌 실제 활용 목적을 반영하지 못함 |
| 즉시 범용 다중 조직 SaaS로 확장 | 다양한 조직을 한 시스템으로 지원 가능 | 인증, 조직 격리와 운영 범위가 급증하며 기존 학습과 취업 일정 침해 위험 |
| 검증된 기반 위에 제한된 운영 목표를 단계적으로 설계 | 기존 구조와 근거를 재사용하면서 실제 업무의 누락을 확인 가능 | 세부 권한과 운영 조건의 추가 검토가 필요 |

## 결정과 이유

세 번째 접근으로 설계 작업을 진행한다. 실제 활용 목적과 O1~O6의 담당자 전용 새 답변, 직접 가져오기/명시적 인계, 서비스 구분, Commit 즉시 인계, 직원 조회와 권한 회수는 사용자 동의로 확정됐다. [실사용 설계 초안](../helpdesk-operational-design-draft.md)은 이 확정 범위와 개인별 인증, 보관/삭제 및 운영 예산 등 후속 선택을 구분한다.

처음의 '서비스 또는 조직별 분리 배포'라는 표현은 같은 운영 조직의 여러 자사 앱을 하나의 Helpdesk에서 서비스별로 구분하는 합의로 보완했다. 적용 앱마다 별도 App과 DB를 반드시 운영하지 않으며, 독립 조직들이 자원을 공유하는 SaaS와도 구분한다. 초기 O1~O3 합의만으로 업무 코드를 변경하지 않았다. 이후 O4~O6 동의와 별도의 작은 구현·Test·Commit 요청을 근거로 V10과 서비스 권한 및 배정을 로컬에서 구현한다.

기존 Ticket / Message / Job / Suggestion 분리와 계층 책임을 유지한다. 담당자 배정은 사람의 업무 책임이며 Worker Attempt의 실행권이나 DB 잠금 수명과 같지 않다. DB 설계 점검 지침은 짧은 Transaction, 일관된 잠금 순서와 FK 및 필요한 Index 검토에 사용하며 Supabase 도입이나 성능 개선 완료를 의미하지 않는다.

## 기존 결정과의 관계

- ADR-0001의 학습 우선과 검증 근거를 유지한다. 실사용을 염두에 둔다는 이유로 실제 개인정보나 Cloud에 먼저 적용하지 않는다.
- ADR-0002 및 ADR-0004의 취업 우선, 전체 12주 틀과 기술 작업 주 6시간 경계는 변경하지 않는다. 운영 준비 전체를 이번 주의 필수 마감으로 추가하지 않는다.
- Week 10 P1~P8과 V9는 최초 구현의 근거로 보존한다. 이후 별도 요청으로 V10과 서비스 권한/담당자 전용 쓰기를 개정하고 로컬 검증했다. 실제 인증 모듈로의 이전은 별도 과업이다.
- 개인정보 고도화의 후속 분리는 유지한다. 다만 실제 AI 입력을 허용하려면 해당 운영 위험의 해소 또는 AI 비활성이 출시 조건이다.

## 영향 파일과 후속 확인

- [실사용 설계 초안](../helpdesk-operational-design-draft.md): 활용 목표, 업무 담당과 협력, 데이터 및 실패 경계, 운영 Gate와 정책 질문
- [총괄 계획](../advanced-track-12-week-plan.md), [계획 안내](../README.md): 학습과 실사용 준비의 구분
- [Week 10 계획](../../week10/weekly-plan.md), [현재 답변 설계](../../week10/official-reply-conversation-design-draft.md): 기존 첫 기능의 완료 기준은 보존하고 새로운 후속 요청을 연결

O1~O6은 합의했으므로 같은 질문을 다시 하지 않는다. 실제 인증, 고객의 후속 메시지와 운영 인수는 별도 과업이다. 최초 구현 요청은 배정·인계의 로컬 구현, Test와 Commit까지였으며 Push, 배포, 실제 AI 호출이나 운영 권한 변경은 포함하지 않았다. 이후 문서 검토·Push 승인은 별도 공개 단계이고, 배포나 운영 권한 변경을 뜻하지 않는다.

## 10/24 후속 검토 기록

- O1 동의는 확정으로 반영했다. O2와 배포 경계의 질문을 동의로 해석하지 않았다.
- 배정은 인간 직원의 명시적 선택이며 DB에서 먼저 확정한 요청이 유효하다고 설명했다. 클릭 순서나 자동 분배를 보장하지 않는다.
- AWS의 Silo / Pool / Bridge 자료를 대조해 공유 자원의 효율과 격리 비용을 구분했다. 현재 운영 사양의 월 비용 계산이나 SaaS 전환 완료 근거는 아니다.
- [배정과 인계 기술 초안](../../week10/ticket-assignment-contract-draft.md)에 Schema, API와 실패 Case를 구체화했다. 최초 작성 당시에는 미확정 전제가 있어 구현 기준으로 자동 승격하지 않았으며, 이후 합의와 확정은 아래 후속 기록을 따른다.
- 후속 사용자 동의로 O2의 직접 가져오기 및 명시적 인계, O3의 한 조직 안 여러 자사 서비스 구분을 합의로 변경했다. 이전 질문 시점의 미확정 기록은 당시 상태로 보존한다. 배정과 인계 구현 전에는 남은 O4~O6만 확인하며 이미 합의한 큰 방향은 반복 검토하지 않는다.
- 마지막 세 항목의 사용자 동의로 O4 Commit 즉시 인계, O5 같은 서비스 활성 직원 조회, O6 권한 회수 후 기존 배정·이력 보존을 확정했다. 같은 요청의 작은 구현·Test·Commit 승인을 근거로 V10과 후속 API를 진행한다. 이전 문단의 미구현 설명은 그 승인 전 상태다.
- 구현 뒤 코드 문답에서 배정 버전, Commit, 과거 이벤트와 현재 상태 및 답변/인계 경쟁을 검토했다. 마지막 권한 회수 Transaction 질문은 미응답으로 남았다. 이후 사용자 요청으로 질문을 중단하고 [학습 자료](../../week10/study-docs/ticket-assignment-and-commit-boundaries.md)와 [학습 기록](../../week10/study-notes/2026-10-24-study-questions.md)을 작성해 현재 기능의 기술 설계를 마감한다. 결과 미확인과 확인된 Rollback의 문구를 정교화하되 업무 정책, 코드와 운영 조건을 새로 바꾸지 않는다.

## 10/27 고객 후속 대화의 합의와 조사

**Context:** 사용자가 11주차 학습/개발을 재개하고 설계 보완 방향을 요청했다. 고객 후속 메시지는 등록자 본인만 작성하는 안에 동의했고, AI 자동 재호출 제외는 설명을 들은 뒤 별도로 승인했다. 이후 나머지 정책도 자세히 조사해 제시하도록 요청했다.

| 항목 | 검토한 선택지 | 결정과 이유 |
|---|---|---|
| 작성자 | 등록자 본인 / 대리 작성 또는 공유 참여자 | F01 Accepted. 등록자 본인만 고객 후속 글 작성. 기존 고정 ID와 소유권 검사를 확장하고 공식 답변과 구분 |
| AI 갱신 | 후속 글마다 재요약 / 사람의 대화 저장부터 연결 | F02 Accepted. 첫 구현은 후자. 최초 제안의 기준과 추가 대화 미반영을 표시하고 전체 대화 재요약은 별도 입력/실행 계약으로 설계 |
| 나머지 정책 | 즉시 일괄 확정 / 조사 후 업무 선택과 기술 계약을 분리 | 조사/제시만 요청됨. F01/F02 외의 권장안은 사용자 합의로 간주하지 않음 |

최초 문의의 AI 처리나 기존 Job 정책은 바꾸지 않는다. 후속 글의 새 메시지 종류와 DB 제약, UUID 재확인 및 담당자 확인 동선은 아직 구현 전이다. 추가 대화로 현재 판단이 달라질 수 있으므로 오래된 AI 제안을 현재 대화 전체의 판단처럼 표시하지 않는다.

영향 파일은 [실사용 설계](../helpdesk-operational-design-draft.md), [11주차 안내](../../week11/README.md), [정책 검토](../../week11/customer-followup-policy-review.md)와 저장소/계획 안내다. 후속 검토는 F04/F07/F11의 업무 선택부터 진행하고 기존 Architecture, 취업 우선/주 6시간과 합성 로컬 검증 경계를 유지한다. 새 업무 코드, Cloud, Secret이나 실제 AI를 변경하지 않는다.

### F04와 F07 및 F11의 후속 검토

사용자가 세 항목의 권장안/선택 이유와 묶음 질문을 요청했다. F04는 모든 기존 상태의 작성 허용과 상태 변경 분리, F07은 새 글 정정을 권장안으로 유지하고 사례와 대안을 보완했다.

F11은 최근 활동 표시만 제공하는 최소안과 현재 담당자의 명시적 확인까지 제공하는 안을 비교했다. 표시만으로는 확인 범위를 남길 수 없어 실제 지원 업무를 위한 권장안은 명시적 확인으로 구체화한다. 확인한 Message ID까지만 기록하고 단순 조회, 이후 도착한 글과 인계 후 새 담당자의 확인을 구분한다. 추가 저장/API 작업이 필요한 검토안이며 사용자 동의나 구현 완료로 기록하지 않는다. F01/F02의 합의 상태는 그대로다.

이후 사용자가 F04와 F07에 동의하고 F11은 명시적 확인까지 포함하도록 선택했다. 위 문단은 설명 당시의 미합의 상태이며 현재 결정은 다음과 같다.

| 항목 | 최종 선택과 이유 | 영향과 후속 검토 |
|---|---|---|
| F04 | 기존 세 상태 모두 작성 허용, 메시지 저장과 상태 변경 분리. 감사 인사나 본문 추측으로 자동 재개하지 않음 | 새 고객 쓰기의 상태 검사와 RESOLVED의 새 글 표시. T03 재개 자격/API는 별도 |
| F07 | 새 글 정정. 원문과 그 원문을 근거로 한 답변의 경과를 보존 | 일반 수정/삭제 API는 추가하지 않음. R11의 민감 정보 예외 절차는 별도 |
| F11 | 첫 구현에 현재 담당자의 명시적 확인 포함. 누구의 어느 배정에서 어디까지 확인했는지 구분 | 확인 지점은 같은 배정에서 후퇴하지 않으며 새 글/인계 후 확인을 덮어쓰지 않음. Schema/API와 충돌/재확인은 기술 설계에서 구체화 |

영향 파일은 정책 검토, 실사용 설계와 주차/저장소 안내다. 합의한 다섯 항목은 반복 질문하지 않고 F03/F05/F12를 다음 검토로 진행한다. 정책 합의와 구현 완료는 구분하며 기존 Architecture와 주간 시간 경계를 유지한다.

## 11/3 주제 구분과 공개 및 내 문의 목록 합의

**Context:** 12주차 계획을 반영한 뒤 사용자가 F03/F05/F12의 묶음 질문에 각각 동의했다. 위 10/27 기록의 다음 검토 항목은 이 답변으로 다음과 같이 확정됐다.

| 항목 | 선택지 | 결정과 이유 | 영향과 후속 검토 |
|---|---|---|---|
| F03 | 주제를 추측해 거부/이동하거나 원문 보존 후 새 문의 안내 | 같은 문제는 기존 Ticket, 독립적인 문제는 새 Ticket으로 안내. 자동 주제 판단으로 고객 설명을 잃지 않음 | 유효한 후속 글 보존. 자동 분리/병합은 추가하지 않고 인증/입력 검사는 유지 |
| F05 | 승인 대기 또는 Commit 후 공개, 실명/표시명 또는 역할명 | Commit 직후 기존 조회 범위에 공개하고 고객에게는 고객/담당자 표시. 실제 작성자와 공개 표시를 분리 | 내부 고정 ID 보존, 실명/로그인 ID/배정 사유 비공개. 별도 업무 표시명 도입은 후속 |
| F12 | Ticket ID 직접 입력 유지 또는 내 문의 목록 추가 | 첫 구현에 본인 목록 포함. 문의를 다시 찾고 대화에 진입할 수 있게 함 | 번호/제목/상태/최근 활동과 소유권 검사. 활동 시각 산정과 Cursor는 다음 설계 |

영향 파일은 [정책 검토](../../week11/customer-followup-policy-review.md), [실사용 설계](../helpdesk-operational-design-draft.md), [12주차 계획](../../week12/weekly-plan.md)과 주차/상위 안내다. 이 묶음 직후의 합의는 F01/F02/F03/F04/F05/F07/F11/F12 여덟 항목이었으며, 특정 답변 인용과 최근 활동 시각을 다음 세부 선택으로 제시했다. 코드 구현 완료나 나머지 상태/운영 정책의 일괄 승인으로 해석하지 않는다.

### F13과 목록 활동 시각의 추가 합의

사용자가 첫 버전은 Ticket 단위로 작성하고 최근 활동은 공개 대화 기준으로 계산하는 안에 각각 동의했다. F13은 특정 답변의 자동 연결과 별도 인용 기능을 첫 구현에서 제외한다. 작성 중 새 답변이 도착해도 참조가 바뀌지 않고 일반 후속 글을 공식 답변 정정으로 취급하지 않기 위한 선택이다.

F12의 최근 활동은 Commit된 공개 Message 중 마지막 메시지의 작성 시각이다. 최초 문의/고객 후속 글/공식 답변을 포함하고 내부 인계나 확인만으로 갱신하지 않는다. 고객이 새 대화가 있는 문의를 찾는 목적이며 상태 API의 공개 이벤트는 해당 기능에서 재검토한다.

현재 합의는 아홉 항목이며 후속 대화의 핵심 업무 선택을 마쳤다. [기술 계약](../../week12/customer-followup-contract-draft.md)에서 Message 확장, 배정별 확인 기록과 유효 범위, 종류별 제출 재확인, 목록 Cursor와 Commit/실패 검증을 구체화한다. 이력/체크포인트 저장 대안, 32 KiB 입력 한도 초안과 관련 영향/후속 Test는 그 계약의 기술 선택 기록에 남긴다. 일반 AI, Cloud나 실제 고객 데이터의 실행 조건은 바꾸지 않는다.

첫 저장 단위는 이후 Lab 645b3df/V11로 로컬 구현/검증했다. 32 KiB 한도와 양방향 메시지 종류 비교를 포함하며 [검증 보고서](../../week12/lab-reports/2026-11-03-customer-followup-storage.md)의 실제 근거를 따른다. 이는 첫 단위의 코드/실행 결과이고 나머지 목록/확인/상태/출시 준비를 완료 처리하는 결정은 아니다.

이후 본인 목록/고객 작성 화면을 7018c0b/104d031에서 검증했고, 80e5de9/6b3ba1d의 V12는 합의한 F11의 확인 저장/API를 구현했다. append-only 기록과 같은 Ticket/현재 배정의 MAX(through_message_id)를 사용하며 만료/삭제나 새 배정으로의 복사는 하지 않는다. 구체적인 대안/결정/이유/영향/후속 점검은 [기술 계약](../../week12/customer-followup-contract-draft.md)과 [실행 보고서](../../week12/lab-reports/2026-11-03-customer-message-confirmations.md)에 연결한다. 직원 표시/버튼/새 Browser 흐름, 상태 API와 출시 준비는 남아 있으며 기존 정책을 재합의한 것으로 기록하지 않는다.
