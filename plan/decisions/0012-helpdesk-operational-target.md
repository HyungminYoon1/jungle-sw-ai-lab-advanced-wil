# ADR-0012 Helpdesk의 후속 목표에 실제 지원 업무 활용을 추가한다

> 상태: Accepted — 활용 목적 및 O1~O6. 10/24 별도 로컬 구현·Test·Commit 요청. 실서비스 준비 전체는 Draft
> 결정일: 2026-10-24
> 근거: 작성자가 향후 소규모 서비스 고객지원 또는 조직 내부 IT 문의 창구로 활용할 의사를 밝히고 실사용을 고려한 설계를 요청

## 배경

학습 과정은 제품 기능 수보다 원리, 실제 계층 연결과 실패 검증을 우선했다. Week 10에는 공식 답변과 대화 조회의 첫 확장을 구현했다. 작성자는 문의별 전담 담당자의 필요성을 질문하고, 최종 앱을 실제 운영에 활용할 계획이라고 밝혔다.

기존 학습 완료를 실서비스 출시 완료로 표현할 수는 없다. 설정 계정과 합성 입력 중심 검증을 넘어 계정 수명, 담당 책임, 고객 후속 메시지, 실제 데이터의 접근 및 외부 전송, 운영과 복구 조건을 별도로 설계할 필요가 있다.

## 검토한 선택지

| 안 | 장점 | 한계 |
|---|---|---|
| 학습용 예제로만 유지 | 범위가 작음 | 사용자가 밝힌 실제 활용 목적을 반영하지 못함 |
| 즉시 범용 다중 조직 SaaS로 확장 | 다양한 조직을 한 시스템으로 지원 가능 | 인증, 조직 격리와 운영 범위가 급증하며 기존 학습과 취업 일정 침해 위험 |
| 검증된 기반 위에 제한된 운영 목표를 단계적으로 설계 | 기존 구조와 근거를 재사용하면서 실제 업무의 누락을 확인 가능 | 세부 권한과 운영 조건의 추가 검토가 필요 |

## 결정과 이유

세 번째 접근으로 설계 작업을 진행한다. 실제 활용 목적과 O1~O6의 담당자 전용 새 답변, 직접 가져오기/명시적 인계, 서비스 구분, Commit 즉시 인계, 직원 조회와 권한 회수는 사용자 동의로 확정됐다. [실사용 설계 초안](../helpdesk-operational-design-draft.md)은 이 확정 범위와 개인별 인증, 보관/삭제 및 운영 예산 등 후속 선택을 구분한다.

처음의 '서비스 또는 조직별 분리 배포'라는 표현은 같은 운영 조직의 여러 자사 앱을 하나의 Helpdesk에서 서비스별로 구분하는 합의로 보완했다. 적용 앱마다 별도 App과 DB를 반드시 운영하지 않으며, 독립 조직들이 자원을 공유하는 SaaS와도 구분한다. 초기 O1~O3 합의만으로 업무 코드를 변경하지 않았다. 이후 O4~O6 동의와 별도의 작은 구현·Test·Commit 요청을 근거로 V10과 서비스 권한 및 배정을 로컬에서 구현한다.

기존 Ticket / Message / Job / Suggestion 분리와 계층 책임을 유지한다. 담당자 배정은 사람의 업무 책임이며 Worker Attempt의 실행권이나 DB 잠금 수명과 같지 않다. DB 설계 점검 지침은 짧은 Transaction, 일관된 잠금 순서와 FK 및 필요한 Index 검토에 사용하며 Supabase 도입이나 성능 개선 완료를 의미하지 않는다.

## 기존 결정과의 관계

- ADR-0001의 학습 우선과 검증 근거를 유지한다. 실사용을 염두에 둔다는 이유로 실제 개인정보나 Cloud에 먼저 적용하지 않는다.
- ADR-0002 및 ADR-0004의 취업 우선, 전체 12주 틀과 기술 작업 주 6시간 경계는 변경하지 않는다. 운영 준비 전체를 이번 주의 필수 마감으로 추가하지 않는다.
- Week 10 P1~P8과 V9는 최초 구현의 근거로 보존한다. 이후 별도 요청으로 V10과 서비스 권한/담당자 전용 쓰기를 개정하고 로컬 검증했다. 실제 인증 모듈로의 이전은 별도 과업이다.
- 개인정보 고도화의 후속 분리는 유지한다. 다만 실제 AI 입력을 허용하려면 해당 운영 위험의 해소 또는 AI 비활성이 출시 조건이다.

## 영향 파일과 후속 확인

- [실사용 설계 초안](../helpdesk-operational-design-draft.md): 활용 목표, 업무 담당과 협력, 데이터 및 실패 경계, 운영 Gate와 정책 질문
- [총괄 계획](../advanced-track-12-week-plan.md), [계획 안내](../README.md): 학습과 실사용 준비의 구분
- [Week 10 계획](../../week10/weekly-plan.md), [현재 답변 설계](../../week10/official-reply-conversation-design-draft.md): 기존 첫 기능의 완료 기준은 보존하고 새로운 후속 요청을 연결

O1~O6은 합의했으므로 같은 질문을 다시 하지 않는다. 실제 인증, 고객의 후속 메시지와 운영 인수는 별도 과업이다. 최초 구현 요청은 배정·인계의 로컬 구현, Test와 Commit까지였으며 Push, 배포, 실제 AI 호출이나 운영 권한 변경은 포함하지 않았다. 이후 문서 검토·Push 승인은 별도 공개 단계이고, 배포나 운영 권한 변경을 뜻하지 않는다.

## 10/24 후속 검토 기록

- O1 동의는 확정으로 반영했다. O2와 배포 경계의 질문을 동의로 해석하지 않았다.
- 배정은 인간 직원의 명시적 선택이며 DB에서 먼저 확정한 요청이 유효하다고 설명했다. 클릭 순서나 자동 분배를 보장하지 않는다.
- AWS의 Silo / Pool / Bridge 자료를 대조해 공유 자원의 효율과 격리 비용을 구분했다. 현재 운영 사양의 월 비용 계산이나 SaaS 전환 완료 근거는 아니다.
- [배정과 인계 기술 초안](../../week10/ticket-assignment-contract-draft.md)에 Schema, API와 실패 Case를 구체화했다. 최초 작성 당시에는 미확정 전제가 있어 구현 기준으로 자동 승격하지 않았으며, 이후 합의와 확정은 아래 후속 기록을 따른다.
- 후속 사용자 동의로 O2의 직접 가져오기 및 명시적 인계, O3의 한 조직 안 여러 자사 서비스 구분을 합의로 변경했다. 이전 질문 시점의 미확정 기록은 당시 상태로 보존한다. 배정과 인계 구현 전에는 남은 O4~O6만 확인하며 이미 합의한 큰 방향은 반복 검토하지 않는다.
- 마지막 세 항목의 사용자 동의로 O4 Commit 즉시 인계, O5 같은 서비스 활성 직원 조회, O6 권한 회수 후 기존 배정·이력 보존을 확정했다. 같은 요청의 작은 구현·Test·Commit 승인을 근거로 V10과 후속 API를 진행한다. 이전 문단의 미구현 설명은 그 승인 전 상태다.
- 구현 뒤 코드 문답에서 배정 버전, Commit, 과거 이벤트와 현재 상태 및 답변/인계 경쟁을 검토했다. 마지막 권한 회수 Transaction 질문은 미응답으로 남았다. 이후 사용자 요청으로 질문을 중단하고 [학습 자료](../../week10/study-docs/ticket-assignment-and-commit-boundaries.md)와 [학습 기록](../../week10/study-notes/2026-10-24-study-questions.md)을 작성해 현재 기능의 기술 설계를 마감한다. 결과 미확인과 확인된 Rollback의 문구를 정교화하되 업무 정책, 코드와 운영 조건을 새로 바꾸지 않는다.
