## 1. 진행 방식과 근거

작성자는 실제 코드와 함께 배정/인계 기능을 설명하고 핵심 질문을 묶어 진행하도록 요청했다. Codex가 현재 Lab 2c8477a의 Service, JDBC Repository, Controller, V10 및 관련 Test를 읽어 설명했다. 문답 중 업무 코드를 수정하거나 Test를 새로 실행한 것은 아니다.

이 기록은 사용자가 제시된 코드와 상황을 해석한 근거다. Codex의 구현/검증, 작성자의 독립 구현 및 운영 배포와 구분한다. 사용자가 답하지 않은 문제의 정답을 자료에 넣어도 학습 확인 완료로 바꾸지 않는다.

## 2. 첫 묶음: 버전과 Commit

| 상황 | 실제 답변과 판정 |
|---|---|
| A→B→A 이후 담당자는 다시 A지만 예상 버전은 예전 1 | 담당자가 같아도 현재 3과 달라 오래된 초안이라고 설명. 맞음 |
| A/1에서 B/2로 UPDATE한 뒤 이력 INSERT 실패 및 Rollback | 최종 A/1, 기존 Commit된 문의 원문 유지라고 답변. 맞음 |
| 미배정 0을 본 두 직원 중 A가 Commit한 뒤 B가 잠금 획득 | B의 예상 0과 DB 1의 충돌로 거부해야 한다고 답변. 맞음 |

잠금은 동시 요청의 순서를, 예상 버전은 과거 화면의 전제를 검사한다는 차이를 설명했다. Service 본문 return과 실제 Commit 및 Browser 응답 수신도 구분했다.

## 3. 두 번째 묶음: 과거 이벤트와 현재 배정

A가 B에게 인계한 버전 2의 응답만 유실됐고, 이후 C에게 인계된 버전 3에서 같은 제출을 재확인하는 상황이었다.

- 첫 답변은 201/추가 이력 1건/B/버전 2였다. 새 인계가 성공할 때의 결과와 재확인을 혼동한 것으로 정정했다.
- 정답은 200/추가 이력 0건/현재 C/버전 3이라고 설명했다. 과거 event와 현재 assignment의 의미를 나눴다.
- 같은 UUID에서 예상 버전만 최신으로 바꾸는 자동 재전송에는 반대했고, DB의 최신 상태를 화면에 표시해야 한다고 답했다. 화면 조회 방향은 맞지만 원래 제출 비교에서 왜 409가 되는지에 대한 직접 답변은 충분히 확인하지 않았다.
- 서비스 권한이 회수된 A에게 기존 Session의 ROLE_AGENT만으로 재확인 결과를 주면 안 된다고 답했다. 매번 권한을 읽는 비용에 대한 질문도 제기했다.

### 추가 확인과 설명 보완

event는 B/2, assignment는 C/3인 상황에서 다시 B를 현재 담당자로 선택했지만 새 이력 INSERT 금지는 맞게 답했다. 같은 원리로 D에게 인계된 버전 4를 제시한 후에는 다음 두 항목을 모두 맞게 답했다.

1. 과거 event는 B에게 인계한 결과, 버전 2.
2. 현재 assignment는 D 담당, 버전 4.

따라서 처음부터 두 값을 구분했다고 기록하지 않는다. 설명과 재확인을 거쳐 해당 사례를 구분한 것으로 남긴다.

권한 30초 캐시에 과거 active=true가 남으면 즉시 회수 정책을 지켰다고 할 수 없다는 질문에는 "안 됩니다"라고 답했다. 실제 권한 조회는 해당 서비스의 구성원만 대상으로 하고 기본키 Index가 있지만, 비용을 실측하지 않았으므로 빠르다고 단정하지 않았다. 매 요청 권한 검사와 모든 설계에서 DB를 반드시 조회해야 한다는 주장은 구분했다.

## 4. 세 번째 묶음: 답변과 인계 경쟁

| 상황 | 실제 답변과 판정 |
|---|---|
| A 답변 Commit 뒤 B로 인계 Commit | 기존 답변 유지, 저장 당시 배정 버전 1이라고 답변. 맞음 |
| B로 인계 Commit 뒤 A의 새 답변 | 저장하지 않으며 담당자 검사에서 먼저 거부된다고 답변. 맞음 |
| A가 버전 1에서 이미 Commit한 동일 답변을 인계 뒤 재확인 | 200, 추가 답변 Row 0건이라고 답변. 맞음 |

기존 제출 조회가 현재 담당자 검사보다 앞에 있지만, 현재 서비스 조회 권한 확인보다 뒤에 있다는 순서를 코드로 설명했다. 저장된 결과의 재확인이 새 답변 권한을 회복시키는 것은 아니다.

## 5. 권한 회수의 두 Transaction: 미응답

다음 문제를 제시한 뒤 사용자는 실시간 질의 대신 문서화하고 설계를 마무리하도록 요청했다. 두 문제의 사용자 답변은 없다.

1. 답변이 active=true와 공유 잠금을 먼저 확보하고 회수 UPDATE가 기다리는 경우, 회수가 이미 확정됐는지와 답변이 먼저 Commit될 수 있는지.
2. 회수 UPDATE가 먼저였지만 미확정 상태에서 Rollback한 경우, 이후 어떤 권한 값을 기준으로 새 요청을 처리하는지.

정답과 순서도는 자율 학습 문서 7절 및 9절에 제공했다. 이는 Codex의 설명이며 작성자의 이해 확인 결과가 아니다. 오늘 다시 질문하거나 즉시 답하도록 요구하지 않는다.

## 6. 이번 문서화와 이후 범위

- 구현이 끝났는데 후보/미구현으로 남은 설명을 정리하고 V10의 실제 제약 및 API 이름과 대조했다.
- 확인된 Commit 거부/Rollback과 Commit ACK 또는 HTTP 응답 유실에 따른 결과 미확인을 명시적으로 구분했다.
- 배정/인계의 현재 기능 설계는 마감하고, 미확인 학습은 나중에 읽을 수 있게 남겼다.
- 계정 전체 수명, 여러 제품의 접수 라우팅, 고객 후속 메시지와 상태 API, 보관/삭제 및 운영 인수는 별도 설계/승인 대상이다.
- 기존 Test 결과를 새 실행으로 재기록하지 않았다. 설계 마감 단계에서는 문서만 수정했고 업무 코드, DB Schema, AWS, 실제 AI와 원격 전달은 변경하지 않았다. 후속 문서 검토 및 공개는 실행 보고서의 별도 기록으로 구분한다.

이번 회차는 주간 WIL 또는 통합 블로그 발행 완료가 아니다. 실제 주간 순작업 시간과 독립 재현 여부도 임의로 추정하지 않는다.
