# Week 10 학습 및 구현 계획: 공식 답변과 대화 조회

> 작성일: 2026-10-23
> 상태: In Progress. V9 답변/대화와 V10 배정/인계의 기술 설계 및 로컬 검증 완료. 10/24 코드 문답 뒤 자율 학습 문서로 전환. 실제 가용시간 확인과 주간 마감은 남음
> 작업일: 2026-10-23, 2026-10-24, 2026-10-26
> 핵심 질문: AI 제안과 공식 답변을 구분하면서, 권한이 있는 사용자가 Ticket의 대화를 안전하게 작성하고 조회하게 만들 수 있는가?

## 계획 배경

문의 접수, 최초 Message 저장, AI 제안과 Cloud 배포 및 복구의 핵심 검증을 마쳤다. 8–9주차 저장소 WIL은 최종 검토와 Push를 완료했고, 10/23 작성자의 확인으로 블로그 작성과 포럼 업로드도 완료로 기록했다.

이제 기존 Ticket과 Message를 활용해 담당자의 공식 답변 작성과 대화 내역 조회를 한 흐름으로 연결한다. 여러 기능을 동시에 추가하지 않고 요구사항, 데이터와 권한을 먼저 검토한 뒤 작은 구현과 실제 PostgreSQL 및 Browser 검증으로 이어간다. 전체 기능의 상세 설계를 미리 완성하는 일정은 잡지 않는다.

상위 계획의 취업 우선 원칙은 유지한다. 지원, 면접과 Coding Test는 이 구현의 완료를 기다리지 않으며, 프로젝트 작업은 기존 주 6시간 상한 안에서 배분한다.

## 10/23 최초 구현 기준선

| 항목 | 확인한 상태 | 이번 작업의 변화 |
|---|---|---|
| Ticket | 제목과 OPEN, IN_PROGRESS, RESOLVED 상태 | 답변은 상태 변경과 분리하고 RESOLVED의 추가 안내도 허용하기로 합의 |
| Message | 본문과 인증 작성자 저장, Ticket 참조 | 문의와 공식 답변 구분, 대화 조회 추가 |
| 문의 접수 | Ticket, 최초 Message, AI Job의 단일 Transaction | 인증된 계정과 연결된 고정 사용자 ID를 등록자로 저장하기로 합의 |
| 권한 | USER와 AGENT 접수 가능, 기존 Ticket 및 AI 조회는 AGENT 전용 | USER의 자기 대화 조회, AGENT의 전체 조회와 답변에 합의. 등록자 미확인 문의는 AGENT 조회만 허용 |
| AI | Job에 고정된 입력 Message 사용 | 공식 답변 저장과 대화 조회로 새 Job을 만들지 않는 안 |
| 실행 | 로컬 개발, Cloud 실행 리소스 정리 완료 | AWS를 재생성하지 않고 로컬에서 구현 및 검증 |

구현 전 조사 기준은 Lab `832b1b74ab7666a5bf50c9aa702b14f97b517d59`다. 이후 사용자 요청에 따라 기술 계약을 확정하고 작은 단위로 구현했다. 정책과 기술 결정은 [설계 문서](./official-reply-conversation-design-draft.md), 현재 Commit과 실행 결과는 [23일 보고서](./lab-reports/2026-10-23-official-reply-conversation-lab.md)를 따른다.

## 목표와 학습 범위

| 구분 | 학습 및 구현 목표 | 완료 근거 |
|---|---|---|
| 요구사항 | AI가 만든 제안과 사람이 공개한 공식 답변의 차이 설명 | 사용자 정책 검토와 수정된 계약 |
| 권한 | Role과 개별 Ticket 소유권을 구분 | 서로 다른 USER 두 명과 AGENT의 접근 Test |
| 영속성 | 답변 저장, 중복 요청과 Commit 결과 구분 | 실제 PostgreSQL의 Row와 실패 Test |
| 대화 조회 | 문의와 답변의 순서, 제한된 조회와 화면 상태 처리 | API Test와 Browser 대화 조회 |
| 회귀 | 기존 접수와 AI 입력 및 Job 정책 유지 | 기존 Test와 신규 Test의 실행 결과 |
| 설명 | 채택한 정책, AI 구현 범위와 직접 검토한 부분 설명 | 짧은 학습 기록과 시연 근거 |

Codex는 반복 구현과 Test 초안을 지원하고 작성자는 핵심 정책, 데이터 흐름, 권한과 실패 경계 및 결과를 검토한다. 기초 함수 문답을 반복하지 않고, 정책 선택이나 실패 결과 해석이 필요한 질문을 한 번에 2~3개씩 다룬다.

**10/24 후속 진행 방식:** 사용자 요청으로 지금의 질의형 학습을 중단한다. 합의한 배정/인계 설계는 마감하고 [자율 학습 자료](./study-docs/ticket-assignment-and-commit-boundaries.md)에 코드, 사례와 정답을 남긴다. 미응답 문제를 완료 처리하거나 문서 읽기를 신규 구현의 승인 절차로 요구하지 않는다. 추가 학습의 날짜와 새 기능 범위를 자동으로 정하지 않는다.

### 포함할 범위

- AGENT가 기존 Ticket에 공식 답변 한 건을 저장하는 흐름
- 최초 문의와 공식 답변을 함께 보여주는 대화 API와 최소 화면
- USER의 자기 Ticket 조회와 등록자 식별 정책
- 인증 작성자, 입력 검증, 중복 제출과 안전한 오류 응답
- 기존 로그인 유지 및 고정 ID의 명시적 연결, 같은 Ticket의 공식 답변을 참조하는 정정
- 읽기와 쓰기의 권한 Test, Migration 보존 Test, PostgreSQL Integration Test와 대표 Browser 흐름

### 이번 작업에 포함하지 않을 범위

- 고객의 후속 Message 작성, 내부 메모와 답변 초안 및 승인 Workflow
- 답변 수정과 삭제, 검색, 전체 Ticket 목록과 Dashboard. 담당자 배정은 10/24 별도 후속 요청으로 아래 범위에 추가
- Ticket 상태 변경 API 신설과 재개 Workflow
- AI의 고객 답변 자동 생성 및 자동 게시, 추가 AI 처리와 Job 재시도
- 개인정보 모델 고도화, 인물 관계 V2, 일반 입력 AI 활성화
- Cloud 재배포, IAM이나 DNS 변경, Secret 변경과 실제 AI 호출

위 항목은 삭제하지 않고 후속 목록으로 보존한다. 대화 조회의 작은 페이지 제한은 이 기능에 필요한 응답 크기 제어이며, 범용 검색 및 목록 기능을 추가하는 것은 아니다.

### 10/24 추가 요청: 실제 사용을 고려한 후속 설계

작성자는 UNIQUE가 Commit 순서를 보장하지 않으며 같은 Ticket 잠금 뒤 Message를 INSERT해야 한다고 답했다. 이어 문의별 전담 담당자의 필요성을 질문하고, 앱을 향후 소규모 서비스 고객지원 또는 조직 내부 IT 창구에 활용할 목표를 밝혔다.

[실사용 설계 초안](../plan/helpdesk-operational-design-draft.md)에 책임 담당자 한 명과 협력, 배정과 인계, 실제 계정 및 데이터, 출시 Gate를 구분한다. O1~O6은 모두 사용자 동의로 확정했다. [배정과 인계 기술 계약](./ticket-assignment-contract-draft.md)에 Schema, API와 실패 Case 및 기존 답변 권한의 개정을 기록했다. 별도의 작은 구현·Test·Commit 요청을 근거로 V10과 최소 업무 화면을 진행한다. 최초 기능의 누락이 아니라 새 후속 요청이며 기존 V1~V9와 당시 근거는 보존한다. 실제 주간 시간은 미확인이므로 임의로 잔여 시간을 산정하거나 상위 경계를 늘리지 않는다.

## 구현 순서와 착수 조건

### 1. 요구사항과 정책 검토

- [설계 초안의 P1~P8](./official-reply-conversation-design-draft.md#사용자와-먼저-검토할-핵심-정책)는 합의했다. 공개와 권한, 상태 분리, 정정, 고정 ID 및 기존 로그인 연결, 미확인 등록자와 중복 제출 정책을 다시 미확정으로 되돌리지 않는다.
- 이번 기능 범위에서 추가 필수 업무 정책은 현재 식별하지 못했다. 인증 연결 구조, Schema 및 Migration, API와 오류 계약, Test Case를 기술 세부사항으로 정리한다.
- 기존 정책을 바꿔야 하는 충돌이나 새 위험이 발견되면 다시 확인한다. 질문 수를 늘리기 위해 합의한 정책을 반복 검토하지 않는다.
- 8–9주차 공개 마감과 10/23의 별도 구현 요청은 확인했다. 실제 주간 잔여 시간은 미확인이며, 기술 계약과 구현 근거를 혼동하지 않는다.

### 2. 데이터와 Backend

- 기존 Migration은 보존하고 다음 Migration의 추가 변경으로 설계한다.
- 등록자와 메시지 종류의 기존 데이터 처리부터 Test로 확인한다.
- 기존 인증 계정과 고정 ID의 명시적 연결, 정정 대상 참조와 제출 Unique의 DB 제약을 구체화한다.
- Domain, Application Service, Repository Port와 JDBC Adapter, Controller 순서로 책임을 나눈다.
- 권한, 중복 요청과 저장 실패 Test를 구현 단위와 함께 작성한다.
- 답변 처리에 새 AI Job이나 Provider 호출이 생기지 않는지 검증한다.

### 3. 최소 화면과 통합 검증

- Ticket ID로 대화를 조회하고 AGENT에게만 답변 입력을 표시한다.
- 서버의 권한 검사를 유지하며, 본문은 textContent로 표시한다.
- Session과 CSRF, 전송 결과 미확인, 이전 조회의 늦은 응답을 구분한다.
- USER A, USER B와 AGENT로 대표 흐름을 실행하고 실제 PostgreSQL Row와 대조한다.
- 재로그인 후 저장된 대화 조회와 기존 문의 및 AI 제안 회귀를 확인한다.

### 10/24 후속 구현 및 검증

O1~O6을 모두 합의하고 배정·인계의 작은 단위 구현·Test·Commit을 승인받았다. V10, 서비스 권한과 담당자 전용 쓰기, 같은 제출 재확인, 동시 인계 및 권한 회수 실패 경계를 로컬 PostgreSQL에서 검증했다. 최소 업무 화면을 연결해 USER 두 명과 AGENT 두 명, 지원관리자의 실제 Browser 흐름을 대조했다. Java 1,068건과 패키징 후 2건, Node 331건 및 Lint가 통과했다. 최종 보강된 배정 25건과 Browser 1건도 다시 통과했으며 겹치는 실행은 합산하지 않는다.

[24일 실행 기록](./lab-reports/2026-10-24-ticket-assignment-lab.md)에 작은 Commit, 최초 회귀 실패와 Fixture 보완, DB 원문/AI Row 보존 및 검증 한계를 남겼다. 이후 버전/Commit, 과거 event와 현재 assignment, 답변/인계 경쟁의 문답을 진행했다. 권한 회수 Transaction 문답은 답변 전에 중단했으며 그 뒤 사용자 요청으로 설명과 정답을 [자율 학습 자료](./study-docs/ticket-assignment-and-commit-boundaries.md), 실제 이해 확인을 [24일 노트](./study-notes/2026-10-24-study-questions.md)에 정리한다.

현재 기능 설계의 미정 표현과 코드 불일치를 정리하고, 명확한 Rollback과 결과 미확인을 구분했다. 이는 추가 업무 정책이나 신규 기능 적용이 아니다. 고객 후속 메시지, 운영 인증과 여러 제품의 접수 연동 및 SaaS는 별도 과업이며 주간 시간 경계나 Cloud 실행 범위를 확대하지 않는다. 설계 문서화 단계에서는 Test/Browser를 다시 실행하거나 Push, Cloud 및 실제 AI 호출을 하지 않았다. 이후 별도 요청으로 문서 검토·Commit·Push를 진행했고 Lab `6eed98c`의 원격 CI 통과를 확인했다. [24일 실행 보고서](./lab-reports/2026-10-24-ticket-assignment-lab.md#후속-문서-검토와-원격-전달)에 로컬/원격 근거와 WIL의 CI 비대상을 구분했다.

## 10–12주차 블로그 발행 계획

**합의, 2026-10-23:** 주차별 블로그 세 편 대신 10–12주차 통합 글 한 편을 작성한다. 취업 우선 기간의 작은 기능 확장과 검증, 정책 판단 및 최종 회고를 연결한다. 실제 발행 날짜나 제목은 아직 정하지 않는다.

기록까지 마지막 주로 미루지는 않는다. 기존 주간 취업 활동 요약과 필요한 학습 기록은 유지하고, 구현 결과, 직접 판단한 정책, Test 근거와 남은 문제를 그때그때 짧게 남긴다. 저장소 기록과 공개 블로그의 작성 주기를 분리한다. 회사명이나 면접 내용 등 비공개 정보를 통합 글에 옮기지 않는다.

과정에서 주간 포럼 제출을 의무로 요구하는지는 이번 검토에서 확인하지 않았다. 별도 제출 의무가 있다면 그 주기는 지키면서 블로그만 묶는다. 상위 계획과 콘텐츠 계획에 이번 합의를 반영했으며, 아직 작성하지 않은 글을 완료 처리한 것은 아니다. [기록 주기 결정](../plan/decisions/0011-combined-week10-12-blog.md)에 선택지와 이유를 남겼다.
