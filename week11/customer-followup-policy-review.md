# 고객 후속 메시지와 실제 운영을 위한 정책 검토

> 기준일: 2026-10-27
> 재개일: 2026-11-03. F03/F05/F12/F13 및 공개 대화 기준 활동 시각 추가 합의
> 상태: F01/F02/F03/F04/F05/F07/F11/F12/F13 Accepted. 나머지는 사용자 선택 또는 기술 검토안
> 설계 시작 기준: Lab 6eed98c/V10. 이후 V11 고객 대화/목록/화면과 V12 확인 저장/API는 별도 실행 보고서로 추적. 직원 확인 화면과 전체 출시의 완료 문서는 아님

문의 등록자가 담당자의 답변에 다시 응답하고, 담당자가 새 내용을 놓치지 않으면서 처리 결과를 기록하는 흐름을 다음 설계 대상으로 삼는다. 기존 P1~P8과 O1~O6은 유지한다. 등록자 본인의 후속 작성과 첫 구현의 AI 자동 재호출 제외에 이어 F04의 모든 기존 상태 작성 허용, F07의 새 글 정정과 F11의 명시적 확인을 합의했다.

11/3에는 F03의 주제 구분과 원문 보존, F05의 Commit 직후 공개/역할 표시, F12의 첫 구현에 내 문의 목록 포함을 추가 합의했다. 이어서 고객 후속 글은 Ticket 단위로 작성하는 F13과 공개 대화 기준의 최근 활동 시각도 합의했다. 남은 기술 계약은 [12주차 초안](../week12/customer-followup-contract-draft.md)으로 구체화한다.

같은 날 V11 후속 저장/종류별 재확인은 [첫 저장 보고서](../week12/lab-reports/2026-11-03-customer-followup-storage.md), 본인 목록/고객 작성 화면은 [화면 보고서](../week12/lab-reports/2026-11-03-my-tickets-and-followup-ui.md), V12 명시적 확인 저장/API는 [확인 API 보고서](../week12/lab-reports/2026-11-03-customer-message-confirmations.md)에 기록했다. 직원 목록의 확인 표시/버튼과 새 Browser 흐름은 후속이며 아래 정책 전체의 구현 완료로 확대하지 않는다.

검토 범위는 한 운영 조직이 자사 서비스의 고객지원 또는 내부 IT 문의를 처리하는 인증된 Web 서비스다. 아래 40개 항목은 구현할 기능 40개나 사용자에게 물을 질문 40개가 아니다. 이미 합의한 원칙은 재사용하고, 업무 선택이 필요한 항목과 Codex가 구체화할 기술 계약을 구분한다. 외부 조직 SaaS, 자동 환불과 계정 조작, 범용 Workflow Engine은 대상에 포함하지 않는다.

읽는 순서는 1절의 확정 사항, 3절의 고객 후속 대화, 6절의 검토 순서다. 상태 API와 실제 운영 준비는 해당 기능 또는 출시 전에 결정한다. 모든 운영 정책을 이번 후속 메시지 구현의 선행 조건으로 묶지는 않는다.

### F01 후속 메시지의 작성자

**합의:** Ticket 등록자 본인만 고객 후속 메시지를 작성한다. 서버가 인증된 Principal과 고정 사용자 ID 및 DB의 requester_user_id를 대조한다. Browser가 작성자 이름이나 ID를 보내도 권한 근거로 사용하지 않는다.

직원은 고객을 대신하는 작성자로 가장하지 않고 기존 공식 답변 경로를 사용한다. 직원 계정이 자신의 문의를 등록한 경우처럼 한 사람이 두 자격을 가질 때는 F14의 경로별 자격 구분으로 처리한다. 대리 접수, 소유자 변경과 참여자 초대는 이번 합의에 포함하지 않는다.

### F02 후속 대화와 AI 처리의 분리

**합의:** 첫 구현에서는 후속 메시지를 저장하고 조회하되, 그 저장을 이유로 새 AI Job이나 Provider 호출을 만들지 않는다. 기존 최초 문의의 Job 입력과 제안을 변경하지 않는다. 최초 접수의 기존 AI 처리 정책은 그대로다.

화면에는 요약뿐 아니라 분류와 우선순위도 최초 문의 기준임을 표시하고, 추가 대화가 반영되지 않았음을 알린다. 과거 제안이 현재 대화 전체에 대한 최신 판단인 것처럼 표시해서는 안 된다. 새로운 긴급 정보는 담당자가 직접 확인해야 하며 담당자의 공식 분류/우선순위는 R17에서 따로 설계한다.

이 합의는 후속 메시지 기능이나 위 표시가 이미 구현됐다는 뜻이 아니다. 이후 전체 대화 재요약을 추가하려면 R08의 입력 범위와 처리 계약이 필요하다.

## 3 고객 후속 대화의 정책

F03~F14는 첫 후속 대화 기능을 설계할 때 검토할 12개 항목이다. '기존 원칙 재사용'은 같은 큰 정책을 다시 질문한다는 뜻이 아니다.

### F03 같은 문제와 새 문제의 경계

**합의, 2026-11-03:** 같은 문제의 진행 상황, 추가 증거와 답변에 대한 질문은 기존 Ticket에 추가한다. 독립적인 새 문제는 새 Ticket으로 안내하되 서버나 AI가 글의 주제만 추측해 저장을 거부하거나 원문을 다른 문의로 옮기지 않는다. 인증/권한과 입력 검증은 기존 원칙대로 적용한다.

예를 들어 로그인 문의에 결제 문제도 함께 적혔다면 그 메시지를 보존하고 직원이 새 문의 분리를 안내한다. 향후 분리/병합 기능에는 원본과 새 Ticket의 연결, 고객에게 보이는 범위 및 AI 입력 보존이 필요하다.

### F04 메시지를 작성할 수 있는 Ticket 상태

**합의, 2026-10-27:** OPEN, IN_PROGRESS, RESOLVED에서 후속 메시지를 허용하되 메시지 등록 자체는 상태를 바꾸지 않는다. RESOLVED는 읽기 전용 잠금이나 삭제 상태로 해석하지 않는다. 실제 재개는 T03에서 별도로 정한다.

'감사합니다'와 '아직 해결되지 않았습니다'를 같은 자동 재개로 묶지 않는 이유다. 해결된 문의의 새 글이 업무 목록에서 사라지지 않도록 F11을 함께 적용한다. F04는 고객 후속 작성과 상태 유지의 합의이며 T03의 재개 자격이나 상태 변경 API까지 합의한 것은 아니다.

예를 들어 RESOLVED 문의에 '안내 감사합니다'를 저장해도 상태는 그대로다. '같은 오류가 계속됩니다'도 우선 고객 메시지로 저장하고 담당자가 발견할 수 있게 표시한다. 실제 재개 자격과 전이는 T03에서 따로 정한다. 이 단계에서 단어를 분석해 상태를 바꾸지 않는다.

해결된 문의의 작성을 막는 안은 고객이 같은 문제의 경과를 새 Ticket에 다시 설명해야 할 수 있다. 모든 글로 자동 재개하는 안은 감사 인사까지 처리 중 업무로 돌릴 수 있다. 메시지 허용과 상태 변경을 분리하면 글의 의미를 서버가 추측하지 않고 기존 대화와 처리 이력을 유지할 수 있다.

### F05 공개 시점과 조회 범위

**합의, 2026-11-03:** 후속 메시지는 Commit 직후 등록자와 해당 서비스의 활성 지원 직원에게 공개한다. 별도 직원 승인 대기를 두지 않는다. 고객 화면의 작성자 표시는 우선 '고객/담당자'로 구분하고 실명, 로그인 ID, 배정 사유와 내부 식별자는 넣지 않는다. 다른 고객, 다른 서비스 직원, 단순히 같은 조직에 속한 사용자는 읽지 못한다.

임시 저장, 직원 승인 후 공개와 참여자 초대는 첫 구현에 추가하지 않는다. 작성 중인 내용과 서버가 접수한 메시지는 화면에서도 구분한다. 자료 근거는 2절의 Atlassian 공개 범위와 참여자 모델이며, 우리 범위는 기존 O5를 유지하는 선택이다.

조회 대상은 기존 O5를 재사용하며 이번 합의는 공개 시점과 역할 표시를 확정한 것이다. 역할명은 메시지의 고객 글/공식 답변 구분을 따르며 계정의 전역 AGENT Role만으로 정하지 않는다. 내부에는 실제 작성자의 고정 ID를 보존하고 인계 후에도 과거 작성자를 바꾸지 않는다. 업무 표시명 공개가 필요해지면 로그인 username과 분리해 관리하는 대안을 검토한다.

### F06 본문 형식과 입력 한도

**기술 계약 권장:** 기존 TicketMessage와 같은 비공백 및 최대 2,000 Unicode Code Point 규칙을 우선 재사용한다. 현재 규칙은 strip한 복사본으로 길이를 재고 원문은 그대로 저장한다. 의미 있는 내용까지 공백 제거·요약으로 바꾸어 저장하지 않는다.

HTML과 Markdown을 실행하거나 렌더링하지 않고 Text로 표시한다. 작성자, Message 종류, 서비스 ID, Job 설정과 상태는 고객 입력 필드가 아니다. 업무 문자 수와 HTTP 요청 Byte 제한은 다르므로 큰 공백/JSON Escape에 대한 별도 한도도 첫 API의 기술 구체화에서 R13과 함께 정한다.

### F07 고객 메시지의 수정과 철회

**합의, 2026-10-27:** 첫 구현에는 본문 덮어쓰기와 일반 삭제를 제공하지 않고 새 메시지로 보충/정정한다. '이전 메시지를 정정합니다'라는 글을 서버가 기존 본문 변경으로 해석하지 않는다. 구조화된 고객 정정 참조를 도입할지는 별도 선택으로 남긴다.

이 원칙은 개인정보나 실수로 올린 비밀값을 영구히 노출하겠다는 뜻이 아니다. 접근 제한과 통제된 가림/삭제는 R11의 예외 절차로 분리한다. 직원 답변의 기존 P3/P8 정정 계약은 그대로 유지한다.

예를 들어 고객이 '오류는 오전 9시에 발생했습니다'라고 적고 담당자가 이를 근거로 답변한 뒤 시간을 10시로 고치려는 경우다. 첫 글을 덮어쓰기보다 '앞서 적은 발생 시각을 오전 10시로 정정합니다'라는 새 글을 남기면 당시 답변의 근거를 설명할 수 있다.

수정 이력을 보존하는 직접 편집도 가능한 대안이다. 다만 이전/현재 버전, 충돌, 어떤 버전으로 답변했는지와 재전송 비교를 추가로 설계해야 한다. 첫 구현은 새 글 정정으로 시작하고 편집 기능의 필요성을 별도로 판단하는 쪽을 권한다. 비밀값 노출은 이 일반 편집 제한을 이유로 방치하지 않는다.

### F08 제출 UUID와 중복 판단

**기존 원칙 확장. 권장안:** 같은 Ticket/작성자/UUID의 같은 종류·같은 원문·같은 참조는 200으로 기존 결과를 반환하고 새 Row를 만들지 않는다. 새 저장의 Commit은 201이며 같은 키로 내용 또는 종류가 달라지면 409다. 새 UUID의 동일 본문은 사용자의 새 제출로 본다.

기존 Unique는 공식 답변과 후속 메시지에 공유될 수 있으므로 종류까지 비교해야 한다. 공식 답변의 UUID를 후속 메시지 요청에 재사용했는데 본문만 같다는 이유로 성공 처리하면 안 된다. 업무 DB의 Unique와 서버 비교가 책임을 맡고 버튼 비활성화나 본문 유사도는 대체 수단이 아니다. HTTP 표준이 이 특정 UUID 구조를 요구하는 것은 아니다.

### F09 저장 순서와 Commit 범위

**기존 원칙 재사용. 권장안:** 같은 Ticket을 잠근 뒤 후속 Message ID를 발급해 저장하고 Commit한다. 최초 문의, 기존 답변, 고객 소유권, 현재 배정 및 AI Job 입력을 변경하지 않는다. 외부 AI와 알림 호출을 이 Transaction에 넣지 않는다.

확인된 Rollback은 새 메시지를 취소하며 앞서 Commit된 대화는 유지한다. 시각은 서버가 기록하고 고객이 보낸 시각을 저장 순서나 권한의 근거로 쓰지 않는다. 다른 Ticket의 전역 ID/기록 시각까지 Commit 순서를 보장한다고 확대하지 않는다.

### F10 응답 유실과 Browser 복구

**기존 원칙 확장. 권장안:** POST 결과를 모르면 원래 UUID/본문/참조를 유지해 명시적으로 재확인한다. 201/200으로 저장을 확인한 뒤 GET만 실패했다면 GET을 재시도한다. Ticket 변경 뒤 도착한 늦은 응답은 화면에 반영하지 않는다.

첫 구현에서 제출 정보는 메모리에만 보관하고 이동/새로고침 전 유실 가능성을 안내하는 기존 정책을 우선 유지한다. 키를 잃었다면 대화 조회로 저장 여부를 확인하고 자동으로 새 제출을 만들지 않는다. 재로그인 뒤 재확인도 현재 소유권을 검사한다. Browser에 원문을 영구 저장하는 개선은 별도 개인정보/복구 계약이 필요하다.

### F11 새 고객 메시지를 담당자가 발견하는 방법

**합의, 2026-10-27:** 첫 구현에 업무 목록의 최신 고객 메시지 시각/확인 필요 표시와 현재 담당자의 명시적 '여기까지 확인'을 포함한다. RESOLVED의 새 메시지도 대상이며 상태와 별도로 발견할 수 있게 한다. 단순 GET이나 화면 열기는 확인 기록을 바꾸지 않는다.

표시만 제공하는 최소안과 명시적 확인까지 제공하는 안을 비교한 뒤 사용자가 후자를 선택했다. 표시만 제공하는 안은 구현이 작지만 누가 어디까지 확인했는지 남지 않는다. 실제 지원 업무에서 확인할 글을 구분할 수 있도록 확인 범위를 저장한다.

확인하는 사람, 범위와 인계 경계는 다음과 같다.

- 해당 서비스 권한이 유효한 현재 담당자가 자신이 확인한 마지막 고객 Message ID를 명시한다. 다른 직원의 조회로 담당자의 확인 상태를 바꾸지 않는다.
- 서버는 같은 Ticket의 고객 메시지인지와 현재 담당자/배정 버전을 검사한다. 그 시점의 최신 ID를 대신 채워 고객이 새로 올린 글까지 확인한 것으로 만들지 않는다.
- 예를 들어 담당자가 71번까지 확인한 뒤 72번이 도착했다면, 71번 확인 요청이 나중에 Commit돼도 72번은 확인 필요로 남는다.
- 같은 배정의 확인 지점은 후퇴하지 않게 구현한다. 이미 80번까지 확인한 뒤 늦게 도착한 71번 확인 요청이 현재 지점을 71로 낮추지 않는다.
- 확인은 담당자가 확인했다고 기록하는 동작이며 실제로 내용을 이해했다는 자동 증명이 아니다. 확인 기록만으로 답변 완료나 RESOLVED를 만들지 않는다.
- B에게 인계되면 A의 확인을 B의 확인으로 복사하지 않는다. 새 담당자에게 인계 후 확인이 필요함을 표시하되 과거 글을 방금 도착한 새 글로 표시하지 않는다. A에게 다시 돌아온 배정도 과거 A의 확인과 구분한다.

합의 당시에는 저장/API/화면 작업이 필요했다. 이후 기술 계약과 V12 확인 저장/API를 구현해 로컬 검증했으며 직원 목록 표시/버튼은 남아 있다. 정책 합의, backend 검증과 전체 화면 완료를 나누어 기록한다.

### F12 고객의 내 문의 목록과 페이지 조회

**합의, 2026-11-03:** 첫 구현에 '내 문의 목록'을 포함한다. 문의 번호, 제목, 상태와 최근 활동 시각을 보여주고 목록에서 대화로 이동하게 한다. 서버가 인증된 고정 ID로 본인 문의만 반환하며 Browser가 보낸 작성자 ID로 조회하지 않는다. 직원 업무 목록은 기존 서비스 권한을 유지한다.

**기술 검토:** 목록과 대화의 기본 50/최대 100건 제한 재사용, '더 보기' 및 명시적 새로고침을 우선안으로 둔다. 최근 활동순 목록은 조회 도중 순서가 바뀔 수 있어 Cursor의 정의를 별도 설계한다. 가변 목록의 Cursor를 누락 없는 업무 처리 원장으로 사용하지 않는다. 실시간 Push나 복잡한 검색은 첫 조건이 아니다.

진입 흐름은 '로그인 → 내 문의 목록 → 문의 선택 → 대화 조회/후속 작성'이다. 고객의 내 문의와 직원의 내 담당 목록은 서로 다른 권한 범위다. 상세 대화 API뿐 아니라 목록 자체도 서버에서 소유권을 확인한다. 목록을 포함하면서 필요한 Query와 화면 작업은 첫 구현의 범위로 반영한다.

**활동 시각 추가 합의, 2026-11-03:** 첫 버전의 최근 활동은 Commit된 공개 Message 중 마지막 메시지의 작성 시각으로 정한다. 최초 문의, 고객 후속 글과 공식 답변을 포함하고 내부 인계나 명시적 확인만으로는 갱신하지 않는다. 고객이 새 대화를 찾기 쉽도록 하는 기준이다. 향후 상태 API의 공개 이벤트를 포함할지는 해당 기능에서 재검토한다. 같은 시각의 정렬과 Cursor는 기술 계약에서 구체화한다.

### F13 특정 답변을 지정하는 후속 글

**합의, 2026-11-03:** 첫 구현의 후속 글은 Ticket 전체에 속하는 대화로 저장하고, 서버가 '가장 최근 답변'을 자동 참조하지 않는다. 특정 답변을 선택하는 별도 인용 기능은 후속으로 둔다. 도입 시 같은 Ticket의 공개 Message ID만 명시적으로 선택하게 한다.

고객의 일반 후속 글과 직원의 공식 정정은 별개다. correctsMessageId를 재사용해 고객이 공식 답변의 정정 작성자가 되는 구조를 만들지 않는다. 인용 도입 시 대상의 공개 범위와 삭제/가림 이후 표시도 함께 정한다.

예를 들어 82번 답변을 읽고 글을 작성하는 사이 83번 답변이 도착할 수 있다. 서버가 가장 최근 답변을 자동 선택하면 작성자가 의도하지 않은 83번에 연결된다. 첫 구현은 일반 후속 글로 추가하고 특정 답변에 관한 설명은 본문으로 남긴다. 별도 인용을 도입하면 사용자가 직접 고른 대상 ID와 공개 범위를 함께 검증한다. F07의 새 글 정정 원칙은 유지한다.

### F14 구형 데이터와 여러 자격을 가진 사용자

**기존 원칙 재사용. 권장안:** 등록자가 확인되지 않은 Ticket에는 고객의 신규 후속 쓰기를 허용하지 않고 이름 일치로 소유권을 메우지 않는다. 기존 고객의 확인된 소유권 조회와 구형 데이터 보존 정책은 유지한다.

AGENT이면서 해당 Ticket의 등록자인 사용자는 고객 경로에서는 본인 자격으로, 공식 답변 경로에서는 현재 담당자 자격으로 검사한다. 서비스 지원권한 회수와 계정 전체 중지는 구분한다. 고객 후속 요청에 직원용 expectedAssignmentVersion을 요구하거나 현재 담당자가 바뀌었다는 이유만으로 본인 작성을 거부하지 않는 안을 권한다.

## 4 상태 변경 API 전에 정할 정책

현재 Domain에는 OPEN → IN_PROGRESS → RESOLVED만 있고 상태 변경 HTTP API와 재개 동작은 없다. 아래 T01~T08을 정한 뒤 상태 Schema/API를 추가한다. F04에서 메시지 허용 상태를 정하는 것과 상태 변경 API를 구현하는 것은 별도다.

### T01 상태의 의미와 대기 상태

**사용자 선택. 권장안:** 첫 상태 API는 기존 세 상태를 유지한다. OPEN은 접수 또는 재개 후 처리 시작 전, IN_PROGRESS는 처리 진행, RESOLVED는 담당자가 해결 결과를 기록한 상태로 설명한다. 배정 유무와 동일한 뜻으로 사용하지 않는다.

고객 답변 대기, 외부 부서 대기, 변경 불가능한 CLOSED를 추가하려면 각각의 진입/종료 조건과 고객 표시를 정한다. Zendesk의 여섯 상태를 기능 수 기준으로 가져오지 않는다. 첫 버전에는 무응답 자동 종료와 영구 잠금을 두지 않는 안을 권한다.

### T02 누가 상태를 변경하는가

**사용자 선택. 권장안:** 일반 처리 시작과 해결은 현재 담당자가 수행한다. 지원관리자도 일상 처리는 먼저 인계받는 기존 책임 원칙과 맞춘다. 고객의 재개 자격은 T03으로 별도 정의한다.

O1은 공식 답변 권한의 합의이므로 모든 상태 변경 권한을 이미 합의했다고 간주하지 않는다. 향후 관리자 긴급 처리 예외가 필요하면 별도 권한과 이유를 기록하고 일반 쓰기 우회 권한으로 만들지 않는다.

### T03 해결 후 재개

**사용자 선택. 권장안:** 고객의 일반 메시지는 상태를 바꾸지 않고 등록자가 '같은 문제가 해결되지 않음'을 명시적으로 요청하면 RESOLVED → OPEN으로 재개하는 안이다. 기존 담당자/배정 버전은 보존하고 비활성 담당자의 업무는 지원관리자가 명시적으로 인계한다.

OPEN을 권하는 이유는 재개됐다는 사실만으로 누군가 작업 중이라고 표시하지 않기 위해서다. 바로 IN_PROGRESS로 돌아가는 대안이나 담당자 승인 후 재개도 가능하지만 대기 중인 재개 요청의 누락 방지가 추가로 필요하다. 새로운 Ticket을 자동 생성하거나 담당자를 자동 해제하지 않는다. Domain에 새 전이와 이력 검증이 필요하며 현재 코드는 이 동작을 제공하지 않는다.

### T04 해결 처리의 근거

**사용자 선택. 권장안:** 해결 결과/사유와 관련 공식 답변을 기록하고 담당자가 실제로 확인한 고객 메시지 범위를 남긴다. 단순히 AI Job이 SUCCEEDED거나 HTTP가 200이라는 이유로 해결하지 않는다.

관련 공식 답변의 존재만으로 내용이 고객 문제를 해결했다고 자동 판정할 수는 없다. 고객 확인을 필수로 받을지, 직원 판단으로 해결하고 고객에게 재개 권한을 줄지는 운영 방식에 맞춰 선택한다. 첫 권장안은 직원의 명시적 해결과 고객의 명시적 재개다. 해결 답변 저장과 상태 변경을 별도 요청으로 유지하므로 한쪽만 성공한 화면 복구도 다룬다.

11/3 문답에서 사용자는 고객 또는 담당자의 명시적인 종료 처리가 필요하다는 의견을 제시했다. 메시지 저장/HTTP 성공과 해결 상태를 분리한다는 기존 원칙과 맞는 방향이다. 추가 글의 의미만으로 자동 미해결/재개를 판정하지 않으며, 이 답변으로 고객과 담당자 양쪽 모두의 해결 권한이나 재개 절차를 확정하지 않는다. T02~T04의 권한/전이는 해당 기능 전에 별도로 검토한다.

### T05 상태 변경 이력과 버전

**기술 계약 권장:** 변경 전/후 상태, Actor, 사유, 서버 시각, 제출 UUID와 결과 버전을 같은 Transaction으로 기록한다. assignment_version은 배정에만 사용하고 상태 버전과 혼용하지 않는다. 같은 제출 재확인에서는 과거 이벤트와 현재 상태를 나누어 반환한다.

기록 시각이나 현재 상태 문자열만 비교하면 재개 후 같은 상태로 돌아온 중간 변경을 놓칠 수 있다. 새 Row와 버전은 실패 시 함께 Rollback한다. HTTP If-Match를 도입하면 그 표준의 조건 실패와 응답 규칙을 따르고, 기존 JSON 버전/409 계약을 쓰면 이를 별도 Application 계약으로 명시한다. 두 방식을 혼동해 RFC가 특정 UUID나 409를 요구한다고 설명하지 않는다.

### T06 새 메시지와 해결 요청의 경쟁

**사용자 선택 및 기술 검토. 권장안:** 담당자가 읽은 이후 새 고객 메시지가 먼저 Commit됐다면 오래된 화면의 해결 요청을 충돌로 거부하고 새 내용을 확인하게 한다. 반대로 해결이 먼저 Commit되면 뒤의 고객 메시지는 F04와 T03을 따른다.

상태 버전만으로 새 메시지를 발견할 수 없으므로 마지막 확인 Message ID 또는 대화 버전 같은 별도 기준이 필요하다. 일반 답변 작성에 모든 대화 변경을 이유로 충돌을 강제할지와 해결 처리의 엄격한 기준은 구분한다. Ticket 잠금은 Commit 순서를 정하지만 작성자가 본 대화 범위를 증명하지는 않는다.

### T07 취소와 중복 문의 및 자동 종료

**사용자 선택. 권장안:** 취소, 중복, 답변 대기와 해결을 같은 결과로 저장하지 않는다. 필요한 시점에 별도 종료 사유나 상태를 설계하고 고객의 철회와 운영자의 Spam 격리도 구분한다.

첫 구현에서 무응답 자동 해결, 내용 유사도에 의한 자동 병합과 자동 삭제는 제외한다. 문의 분리/병합을 도입해도 이미 공개된 대화와 고객 소유권을 다른 고객에게 옮기지 않는다. 새 관련 Ticket은 명시적으로 연결한다.

### T08 고객 표시와 성공의 의미

**기존 원칙 확장. 권장안:** Ticket 처리 상태, AI Job 상태, 담당자 검토 상태와 알림 전달 상태를 별도로 표시한다. 조회 200은 조회 성공이지 문의 해결이나 AI 성공이 아니다. 재개 버튼, 현재 상태 및 충돌 후 새로고침 안내를 구분한다.

고객에게 내부 Provider 오류나 직원 인계 사유를 그대로 노출하지 않는다. 실제 운영 시간이 정해지기 전 '곧 답변'이나 확정된 처리 시간을 약속하지 않는다. HTTP 처리 시간, AI 처리 시간과 사람의 응대 시간은 별도 지표다.

## 5 실제 운영 전에 정할 정책

R01~R18은 로컬 합성 실습 전체를 이번 주에 실서비스로 바꾸는 계획이 아니다. 실제 고객 데이터와 사용자를 받기 전에는 해당 운영 범위에 맞는 선택과 검증이 필요하다.

### R01 개인별 인증과 계정 등록

**출시 전 사용자 선택. 권장안:** 첫 제한 Pilot은 명시적으로 발급한 개인 계정을 사용하고 공용 고객/직원 계정을 피한다. 초대형 계정인지 대상 서비스의 기존 인증을 연결할지, 등록과 복구를 누가 맡을지 정한다. Session 방식은 필요 없이 JWT와 함께 교체하지 않는다.

고정 내부 ID는 이미 있지만 개인별 Password 발급/재설정과 계정 운영은 별개다. 이름 재사용으로 소유권을 이전하지 않는다. 로그인 성공 후 자신의 문의/업무 화면으로 이동하도록 진입 동선도 정하고 현재의 루트 404를 정상 사용자 안내로 남기지 않는다.

### R02 계정 전체 중지와 Session 종료

**출시 전 사용자 선택. 권장안:** 직원의 특정 서비스 권한 회수, 전체 계정 중지, Password 변경과 로그아웃의 적용 범위를 구분한다. 긴급 중지 시 기존 Session을 어떻게 무효화하고 다음 요청에서 무엇을 확인할지 설계한다.

현재 membership.active 검사가 계정 전체 중지를 구현한 것은 아니다. 다른 계정으로 전환하면 이전 대화와 초안을 지우고 Session 만료 시 결과 미확인 제출을 자동 재전송하지 않는다. 공유 Session 저장소 도입은 다중 App 필요와 운영 조건을 확인한 뒤 선택한다.

### R03 서비스별 접수와 계정 연결

**출시 전 사용자 선택. 권장안:** 접수 서비스는 신뢰하는 서버 경로/인증 문맥으로 선택하고 고객이 보낸 serviceId를 권한 증거로 쓰지 않는다. 여러 자사 앱의 고객 계정을 어떤 신뢰 주체로 연결할지 명시한다.

현재 서버 설정으로 고른 한 서비스의 접수와 여러 서비스의 직원 권한을 혼동하지 않는다. Ticket의 서비스/소유자를 바꾸는 관리 작업은 공개 내용을 재검토하는 별도 절차다. 다른 조직 SaaS와 조직 간 격리는 새 Architecture 검토 대상이다.

최초 접수의 응답 유실로 Ticket을 두 번 만드는 문제도 별도 제출 키로 다룰지 정한다. 기존 Message UUID는 Ticket이 이미 있는 뒤의 제출 계약이며 새 Ticket 접수의 중복 방지를 자동 제공하지 않는다. Ticket/최초 Message/Job의 원자적 Commit과 같은 접수의 재확인은 다른 책임이다.

### R04 민감 내부 문의의 접근 범위

**출시 전 사용자 선택. 권장안:** 인사, 의료, 내부 보안 사고 등은 같은 서비스 직원 전체 공개라는 O5의 기본 범위에 무조건 넣지 않는다. 첫 Pilot에서는 그런 범주를 제외하고 필요한 경우 별도 접근 범위를 먼저 설계한다.

이미 고객이 민감 정보를 올린 경우의 임시 접근 제한과 담당 운영자도 정해야 한다. 입력 안내나 AI 마스킹만으로 권한 격리를 대신하지 않는다. 민감 여부를 AI가 놓칠 수 있으므로 AI 판단을 유일한 접근 통제로 사용하지 않는다.

### R05 내부 메모와 참여자 공유

**기능 도입 전 사용자 선택. 권장안:** 첫 버전에는 내부 메모, 고객 간 공유, CC와 참여자 초대를 추가하지 않는다. 도입 시 조회/작성/알림/AI 입력/Export 각각의 공개 범위를 명시한다.

현재 대화 Query는 Ticket의 Message를 읽으므로 내부 종류를 추가하고 UI에서만 숨겨서는 안 된다. 대리 작성과 소유자 변경은 참여자 추가와도 다르다. 근거는 2절의 Atlassian 두 자료이며 그 제품의 참여자 범위를 우리 서비스에 승인한 것은 아니다.

### R06 첨부 파일과 링크 및 외부 채널

**기능 도입 전 사용자 선택. 권장안:** 첫 버전은 Text와 인증된 Web 경로를 유지한다. 파일, Rich Text, Email 수신, Webhook을 추가할 때 크기/유형/악성 파일 검사, 인증된 다운로드와 보관/삭제를 함께 정한다.

본문의 URL을 서버가 자동 방문하거나 Model/Tool이 실행하도록 하지 않는다. Email 주소나 메시지에 적힌 계정 이름만으로 인증된 작성자라고 취급하지 않는다. 채널별 중복 ID, 인용 본문 및 첨부의 공개 범위도 필요하다.

### R07 알림 발송과 실패 처리

**기능 도입 전 사용자 선택. 권장안:** 누구에게 어떤 변경을 알릴지, 고객의 수신 설정과 기본 채널을 정한다. 내부 정보와 전체 원문을 알림에 복사하기보다 인증 후 조회하는 링크를 우선한다.

업무 변경과 알림 이벤트를 같은 DB Transaction으로 기록하고 실제 발송은 별도로 처리하는 안을 검토한다. 발송 실패로 Commit된 메시지를 취소하지 않는다. 재시도, 중복 알림, 미전달 확인과 운영자 알림을 정하며 '정확히 한 번 전달'을 미리 약속하지 않는다. Microsoft 사례를 참고한 설계 방향이며 이번에 Outbox나 Broker를 도입한 것은 아니다.

### R08 이후 대화 재요약과 AI 제안의 수명

**AI 확장 전 사용자 선택. 권장안:** F02를 유지하고 재요약은 필요성이 확인됐을 때 추가한다. 입력에 포함한 Message ID/범위, 종류와 시점, Prompt/Model/검증 계약 버전을 고정한다. 작업 중 도착한 최신 메시지를 같은 Job 입력에 조용히 섞지 않는다.

누가 실행하는지, 어떤 조건에서 갱신하는지, 같은 입력의 중복과 이전 결과의 수명, 실패 시 화면을 정한다. 기존 제안을 덮어써 최초 판단 근거를 지우지 않는다. 일반 입력의 외부 전송, 개인정보 검사, Provider 보관/처리 조건과 실행 한도도 별도 검토한다. 단순 읽기나 Browser 새로고침은 AI 호출 조건이 아니다.

### R09 수집할 개인정보와 외부 전송

**출시 전 사용자 선택. 권장안:** 지원 목적에 필요한 정보와 금지할 비밀값을 정의하고 접수 전에 안내한다. 내부에서 대화를 저장하는 목적과 외부 AI에 보내는 목적을 구분한다. 실제 데이터의 외부 전송은 합성 실험 승인으로 대체하지 않는다.

대상 조직, 이용자와 처리 지역에 맞는 고지, 적법한 처리 근거 및 공급자 조건을 확인한다. 모든 처리를 일괄 동의 한 번으로 정당화하지 않는다. NIST의 목적/최소화 원칙은 검토 기준이며 특정 법령의 준수나 허용 보관 기간을 이 조사로 확정하지 않는다.

### R10 데이터 종류별 보관과 삭제

**출시 전 사용자 선택. 권장안:** 문의/메시지, 계정 연결, AI 제안/Attempt, 제출 키, 감사 기록, 진단 Log, Export와 Backup에 대해 목적, 보관 시작점, 기간, 삭제 담당자와 보류 사유를 표로 정한다.

학습 Cloud Log의 365일은 고객 본문 보관 기간이 아니다. 탈퇴가 업무 이력 전체 삭제와 같은지도 별도로 판단한다. 제출 키를 원문보다 먼저 지우면 오래된 재전송이 새 저장이 될 수 있으므로 중복 확인 기간과 삭제 이후 응답도 맞춘다. 실제 기간 수치는 운영 목적과 적용 요구를 확인한 뒤 정한다.

### R11 비밀값 노출과 가림 및 삭제 예외

**출시 전 사용자 선택. 권장안:** 실수로 올린 Password/Key나 타인의 민감 정보에 대해 우선 노출을 제한하고 통제된 가림/삭제 절차를 둔다. 누가 요청하고 확인하며 처리 결과를 검증하는지 정한다. 외부에 이미 전송된 Key는 가림만으로 회수되지 않는다.

업무상 원문 보존과 개인정보 예외를 구분한다. DB뿐 아니라 제안, 알림, Export, Log와 Backup의 사본도 검토한다. Backup 복원 뒤 삭제 자료가 다시 서비스되지 않도록 삭제 결정의 재적용 절차가 필요하다. 가림 전 본문을 사용한 UUID 재확인으로 민감 원문을 다시 반환하지 않는 계약도 정한다.

### R12 본인 자료 열람과 Export

**출시 전 사용자 선택. 권장안:** 대화 다운로드, 자료 정정/삭제 요청과 운영자 일괄 Export의 자격을 구분하고 실제 본인 및 위임 여부를 확인한다. 고객 자료에 직원 내부 메모, 다른 고객과 서비스의 정보 또는 불필요한 내부 ID를 넣지 않는다.

발급 링크의 유효기간/재인증, 파일 보관과 다운로드 기록을 정한다. 내보낸 파일은 서비스의 이후 삭제로 자동 회수되지 않으므로 배포 범위와 처리 책임을 정한다. 첫 대화 기능에서 무제한 전체 Export를 자동 제공하지 않는다.

### R13 요청 한도와 악용 대응

**출시 전 사용자 선택 및 기술 검토. 권장안:** 로그인, 신규 문의, 후속 글, 조회와 Export를 구분하고 계정/Ticket/IP별 빈도 및 요청 Byte 한도를 둔다. 공용 네트워크의 여러 고객을 IP 하나로 같은 사람이라 판단하지 않는다.

제한 전 거부된 요청에는 저장 성공을 표시하지 않고 일시 제한이면 429와 재시도 안내를 사용한다. RFC의 예시 수치는 우리 서비스 한도가 아니다. 초기 수치는 이용자 수/직원 수, 예상 빈도와 부하 검증을 근거로 정한다. 고객 요청 한도와 AI 생성 예약 횟수는 별개이며 악용 감지 기록을 고객 문의 카테고리에 자동으로 덮어쓰지 않는다.

### R14 장애와 유지보수 및 복구

**출시 전 사용자 선택. 권장안:** Backup 주기와 보관, 허용 데이터 손실/복구 시간, 실제 복원 확인 담당자를 정한다. 새 DB 복원 시 원문/소유권/답변/상태/배정 이력을 대조하고 Worker의 외부 실행은 안전한 재개 조건 확인 전 막는다.

Image 복귀와 DB 복원은 구분하고 새 Migration이 이전 Image와 호환되는지 검증한다. 유지보수의 쓰기 제한/재시도 안내, Commit 결과 미확인과 Session 재로그인도 사용자 흐름에 포함한다. 과거 Snapshot 실험만으로 새 Schema 전체의 복구가 검증됐다고 하지 않는다.

### R15 감사 기록과 진단 Log

**기존 원칙 확장. 권장안:** 누가 어떤 문의/권한/상태를 변경했는지 남기는 업무 이력과 오류 진단 Log를 구분한다. 변경 이력의 원자성과 기록 권한, 열람 권한 및 운영자 작업 기록을 정한다.

진단에는 필요한 이벤트 종류, 결과와 연결 ID를 우선하고 본문/Password/Cookie/Token/전체 Header를 기록하지 않는다. 내부 사용자 ID도 결합하면 사람을 식별할 수 있으므로 공개 자료로 취급하지 않는다. 기록 실패 시 업무 변경을 취소할 필수 이력과 별도 대응할 진단 Log를 구분한다. 근거는 2절의 OWASP Log 지침이다.

### R16 정책 변경 권한과 적용 시점

**출시 전 사용자 선택. 권장안:** 입력/요청 한도, 응대 시간, 서비스 권한과 AI 실행 설정을 누가 변경하고 언제 적용하는지 정한다. 잘못된 설정은 기동/적용 시 거부하고 변경 이력과 복구 방법을 남긴다.

구조적 권한 규칙을 무제한 외부 설정이나 고객 입력으로 대체하지 않는다. 변경 가능한 운영 값과 코드/Schema 계약을 구분한다. 기존 Job의 정책 Snapshot과 이미 Commit된 제출을 새 설정으로 소급 해석하지 않는다. 정책 버전/설정/코드 변경의 Test 범위를 정의하되 범용 정책 Engine을 먼저 도입하지 않는다.

### R17 담당자가 확정한 분류와 우선순위

**업무 기능 도입 전 사용자 선택. 권장안:** AI 제안과 담당자의 공식 분류/우선순위를 별도로 저장하고 변경자/사유를 남긴다. 후속 대화에서 금전 피해나 영향 인원 등이 새로 드러나면 담당자가 판단을 갱신할 수 있어야 한다.

고객의 긴급도 주장은 참고 입력이고 AI 제안이나 공식 결정과 다르다. 최신 정보를 반영하려고 과거 AI Row를 고치지 않는다. 기존 UNDETERMINED의 명시적 판단 보류와 필드 누락의 계약 위반도 유지한다. 새 공식 우선순위가 배정, 순서나 응대 시간에 미치는 영향은 별도 업무 규칙이다.

### R18 응대 시간과 담당자 부재

**출시 전 사용자 선택. 권장안:** 운영 요일/시간, 휴일, 최초 응답과 최종 해결 목표, 기한 초과의 확인 담당자와 비상 연락 경로를 정한다. 실제 가능한 범위가 정해지기 전 SLA 수치를 고객에게 약속하지 않는다.

비활성 담당자나 모든 직원 부재 시 미처리 문의를 누가 확인할지 필요하다. 고객 추가 글이 기존 우선순위/처리 상태 때문에 목록에서 사라지지 않게 한다. Application의 Job Timeout과 사람의 응대 기한을 같게 보지 않는다. Week 1의 예제 응답시간 Policy를 운영 SLA로 자동 승격하지 않는다.

## 6 결정 순서와 구현 착수 조건

11/3~9의 [12주차 계획](../week12/weekly-plan.md)에서 다음 묶음의 검토와 고객 후속/명시적 확인 구현을 이어간다. 학습 일정에 대한 동의를 아래 미선택 정책에 대한 일괄 동의로 해석하지 않는다. 상태 API와 실제 운영 준비는 별도 우선순위로 남긴다.

F01/F02/F03/F04/F05/F07/F11/F12/F13과 활동 시각 기준은 합의했으므로 같은 업무 선택을 반복 질문하지 않는다. [기술 계약](../week12/customer-followup-contract-draft.md)의 Message/목록/고객 화면과 확인 기록/API는 로컬 검증했고 다음은 직원 표시/확인 버튼이다. F06/F08~F10/F14는 기존 계약을 재사용하되 새 종류와 확인 동작의 차이를 검증한다. T 항목은 상태 API 전에, R 항목은 해당 운영 기능 또는 실제 이용 전에 구체화한다. 학습 이해를 확인하는 문답은 업무 정책의 재합의와 구분한다.

| 순서 | 우선 검토 | 결정의 이유 |
|---|---|---|
| 첫 묶음 완료 | F04 작성 허용 상태, F07 수정/철회, F11 명시적 확인 | 세 항목 합의. Schema/API/화면 구현 완료와는 구분 |
| 11/3 묶음 완료 | F03 주제 경계, F05 공개/작성자 표시, F12 목록 | 원문 보존/새 문의 안내, Commit 직후 역할 표시, 첫 구현의 내 문의 목록 포함 합의 |
| 세부 선택 완료 | F13 Ticket 단위 후속 글, F12 공개 대화 활동 시각 | 특정 답변 자동 연결/인용은 제외하고 목록은 마지막 공개 Message의 시각 사용 |
| 기술 구체화/검증 | F06/F08/F09/F10/F14와 합의한 아홉 항목 | 저장/목록/고객 화면과 확인 API에 반영. 직원 표시/버튼과 Browser 검증은 다음 단위 |

기술 항목의 입력 상한, 잠금 순서와 UUID 비교까지 매번 새로운 업무 질문으로 만들지는 않는다. 기존 Architecture와 합의 범위 안에서 구체화하고 의미가 달라지는 선택만 다시 확인한다. 합의한 아홉 항목을 나머지 31개 항목의 일괄 승인으로 해석하지 않는다.

### 후속 메시지 구현의 최소 검증 사례

1. 등록자 본인은 저장하고 다른 고객과 비등록자 AGENT는 고객 작성자로 가장하지 못한다.
2. 구형 등록자 미확인, 잘못된/추가 필드, 공백, 길이 경계와 CSRF 누락을 거부한다.
3. 같은 제출은 200/추가 Row 0, 새 제출은 Commit 후 201, 같은 키의 다른 본문/종류는 409다.
4. 담당자 답변과 고객 후속 메시지의 동시 쓰기를 같은 Ticket 잠금과 ID 조회 순서로 검증한다.
5. 저장/Commit 거부와 확인된 Rollback에서 기존 원문, 답변, 배정, Job/Attempt/제안이 보존된다.
6. 응답 유실의 재확인, 저장 성공 뒤 GET 실패, Ticket 전환 후 늦은 응답을 구분한다.
7. 후속 작성이 새 AI 작업/예약/호출을 만들지 않고 최초 입력을 바꾸지 않는다. 통제된 Test에서는 Worker를 꺼서 대조하며, 운영 중 기존 Job이 독립적으로 처리될 가능성과 구분한다.
8. 최초 문의 기준 AI 표시와 추가 대화 표시를 확인하고, 미반영 제안을 현재 대화 전체의 결과로 표시하지 않는다.
9. F04/F11에 맞춰 RESOLVED의 새 글, 현재 담당자의 명시적 확인, 이후 도착한 글, 늦은 확인 요청과 인계/재배정 후의 확인 경계를 점검한다. GET이 확인 기록을 바꾸지 않는지도 검사한다.
10. P1~P8/O1~O6, V1~V10의 기존 Row와 과거 공식 답변 재확인 동작을 회귀 검증한다.
