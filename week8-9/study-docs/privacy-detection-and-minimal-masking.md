# 개인정보 탐지와 원문을 보존하는 마스킹

AI에 보낼 문의에서 개인정보를 가리는 일은 두 작업으로 나뉜다. 먼저 어떤 부분이 개인정보인지 찾고, 그 부분을 정해진 표시로 바꾼다. 검사기에게 문의 전체를 다시 쓰게 하는 대신 Java가 확인한 범위만 치환하면, 연락처와 무관한 로그인 복구 사실이나 문의 목적을 유지할 수 있다.

처리 대상은 전송용 복사본이다. 이미 접수한 Message의 DB 원문을 덮어쓰는 작업과 구분한다. 원문의 열람 권한과 보관 정책은 [AI 제안의 신뢰 경계](../../week7/study-docs/ai-suggestion-trust-boundaries.md#원문-보관과-ai-전송은-다른-정책이다)를 함께 참고한다.

## 탐지와 치환의 역할

탐지기는 이메일·전화번호 같은 개인정보의 위치와 종류를 찾는다. 규칙 기반 탐지기는 일정한 형식을 이용하고, NER 같은 모델은 문맥에서 이름·주소 등의 항목을 찾는다. NER는 문장 속 항목의 종류와 범위를 식별하는 작업이며, 자유롭게 문장을 다시 작성하는 작업과 다르다.

치환기는 탐지 결과에 따라 원문의 해당 부분을 표시로 바꾼다. 이메일이면 `[EMAIL_REDACTED]`처럼 확인한 종류를 남기고 실제 값은 제거할 수 있다. 종류가 불확실한 값을 임의로 전화번호라고 바꾸지 않는다. 탐지와 치환을 분리하는 구조는 [Presidio의 Analyzer와 Anonymizer](https://presidio.dataprivacystack.org/text_anonymization/)에서도 사용한다.

미리 지정한 문자열을 찾아 바꾸는 것은 임의의 개인정보 탐지와 다르다. `first@example.invalid`만 등록한 치환기는 `second@example.invalid`를 찾아내지 못할 수 있다. 알려진 문자열 검사 통과는 그 문자열이 남아 있지 않다는 근거이지, 모든 개인정보가 없다는 근거가 아니다.

### 규칙과 NER 모델은 서로 다른 근거로 탐지한다

형식이 비교적 일정한 이메일·전화번호는 패턴과 주변 문맥을 이용한 규칙으로 찾을 수 있다. 이름처럼 정해진 문자 모양만으로 구분하기 어려운 항목에는 NER 모델을 검토할 수 있다. Presidio의 인식기도 규칙·모델 또는 두 방식의 조합을 허용한다. [Presidio의 EntityRecognizer](https://presidio.dataprivacystack.org/analyzer/)

NER는 문장의 어느 부분이 사람·장소·기관·날짜 같은 개체인지 분류하는 작업이다. 문의를 요약하거나 새로운 문장을 만드는 일과 다르다. 다음은 실제 모델의 관찰 결과가 아니라 역할을 설명하기 위한 예다.

```text
합성 문의: 홍길동입니다. 직원 20명이 오늘 18시까지 로그인해야 합니다.

탐지할 후보: 홍길동 → 사람 이름
보존할 업무 사실: 직원 20명 / 오늘 18시까지 / 로그인해야 함
```

**개체로 인식했다는 사실과 외부 전송에서 가려야 한다는 판단은 다르다.** 수량이나 시각도 인식 대상이 될 수 있지만, 위 문장에서 이를 모두 지우면 영향 범위와 마감이 사라진다. 날짜도 업무 마감인지 생년월일인지에 따라 다르게 다뤄야 한다. 개인정보 종류와 문맥에 따른 마스킹 정책을 먼저 정하고, 이름·주소 등을 놓치는 경우와 정상 업무 사실을 잘못 가리는 경우를 각각 평가한다.

일반 NER의 장소 표시는 완전한 주소 탐지와 같지 않다. 모델이 한국어를 지원한다고 이메일·전화번호·비밀번호까지 모두 탐지한다고 가정하지 않는다. 검사기 고유의 Label을 서버의 `SensitiveType`으로 옮기는 규칙도 명시해야 한다. 현재 계약에 없는 종류를 기존 종류로 임의 해석하거나 새로운 Label을 검증 없이 통과시키지 않는다.

규칙과 모델을 함께 쓰더라도 두 탐지기가 반환한 범위를 그대로 무조건 합치지 않는다. 먼저 위치·종류를 같은 계약으로 표현하고, 아래의 중복·겹침 규칙을 적용한다. 모델이 같은 범위를 서로 다른 종류로 지정했다면 충돌을 숨기지 않는다.

### 사람 이름과 업무 사실을 구분한다

`SensitiveType.PERSON`은 사람 이름을 가리는 입력 전처리 종류이며, 치환 표시는 `[PERSON_REDACTED]`다. 문의를 분류하는 `ACCOUNT`·`BILLING` 같은 AI Category와는 다른 계약이다. 이름 전용 종류를 추가했다고 모델이 이름을 정확하게 찾게 되는 것도 아니다.

마스킹은 모든 인명을 지우는 일이 아니다. 먼저 실제 실명이 AI의 업무에 필요한지 판단한다. 불필요한 실명을 제외하되, 문의에 등장한 사람들의 역할·같은 사람인지 다른 사람인지의 관계는 유지해야 한다. 예를 들어 사람이 확인한 불필요한 이름 범위가 `홍길동`이라면 다음처럼 전송용 복사본을 만든다.

```text
원문: 홍길동입니다. 직원 20명이 오늘 18시까지 로그인해야 합니다.
복사본: [PERSON_REDACTED]입니다. 직원 20명이 오늘 18시까지 로그인해야 합니다.
```

영향 인원·마감 시각·해야 할 일은 문의의 중요한 사실이므로 보존한다. 그렇다고 모든 숫자·날짜가 항상 전송 가능한 것은 아니다. 전화번호·생년월일 등은 문맥과 별도 탐지 정책으로 구분해야 한다. 사람 이름을 가린 뒤에도 DB의 접수 원문은 변경하지 않는다.

탐지 결과의 JSON·위치 검사가 모두 통과하더라도, 이름을 놓치거나 일반 단어를 이름으로 잘못 찾을 수 있다. 다음 두 검증은 서로 다른 질문에 답한다.

| 검증 | 확인하는 것 | 이것만으로 확인하지 못하는 것 |
|---|---|---|
| 통제한 이름 위치를 Java에 전달하는 Test | 정해진 위치를 `PERSON` 표시로 가리고 나머지 문장을 보존하는가 | 실제 모델이 이름 위치를 찾는가 |
| 실제 탐지 모델의 합성 입력 평가 | 기대한 개인정보를 찾고 업무 사실을 잘못 가리지 않는가 | 모든 실제 문의의 개인정보가 제거되는가 |

모델이 놓친 이름은 범위 검증기가 자동으로 알아내지 못한다. 형식 검사를 통과한 결과를 곧바로 정확한 탐지 결과로 취급하지 않고, 탐지 누락과 과도한 마스킹을 모두 확인한 뒤 채택 여부를 정한다. 실패 사례에 맞춰 정답을 바꾸거나 문장 전체를 가려 통과시키면 원문 보존 목적을 잃는다.

### 실명 대신 관계를 남긴다

```text
원문: 김철수 계정으로 로그인했는데 김영희의 주문이 보입니다.
목표: 사용자 A 계정으로 로그인했는데 사용자 B의 주문이 보입니다.
```

실명 자체보다 **다른 사람의 정보가 노출됐다**는 관계가 중요하다. 두 이름을 같은 표시로 바꿔 관계를 잃지 않는다. 동일인임을 확인한 반복 지칭은 한 문의 안에서 일관되게, 다른 사람임을 확인한 지칭은 구분해서 표시한다. 같은 이름을 쓴 동명이인이 있을 수 있으므로 문자열 일치만으로 동일인을 확정하지 않는다. 이름·호칭 표기가 다르다는 이유만으로 다른 사람을 만들어내지도 않는다. 관계를 판단하지 못했다면 불확실성을 유지한다.

실제 이름과 표시를 연결하는 역변환 목록은 AI에 보내지 않는다. 가려진 이름이 있어도 문의의 다른 정보로 사람을 알아볼 수 있으므로, 이 처리만으로 익명화가 완료됐다고 단정하지 않는다.

V1 `DetectedSpan`의 필드·시작·끝·종류와 `[PERSON_REDACTED]`만으로는 이 관계를 표현할 수 없다. V2는 등장 번호와 관계표를 함께 검증한 뒤, SAME으로 묶인 위치가 표시를 공유하도록 치환한다. 위의 A/B는 정책을 설명하는 예이며 실제 V2 치환 표시는 아래와 같이 구분한다.

이름이 등장한 위치의 번호와 실제 사람의 구분도 다르다. 같은 사람이 두 번 등장하면 위치 번호는 두 개일 수 있다. `m1`·`m2`처럼 다른 번호가 있다는 이유만으로 서로 다른 사람이라고 판단하지 않는다. 동일인·다른 사람·미확인 관계는 따로 표현해야 한다. 문의마다 번호를 새로 만들며, 같은 이름이 다른 문의에 등장해도 번호나 신원을 연결하지 않는다. [인물 관계 계약 초안](../../plan/privacy-person-relations-v2-draft.md)

### 관계표의 일관성과 실제 의미를 구분한다

동일인인지 판단하기 어렵다고 명시한 `UNDETERMINED`는 유효한 판단 보류다. 이름 위치는 가릴 수 있고, 관계의 불확실성은 유지한다. 반면 필수 관계 항목이 없는 것은 계약 위반이므로 서버가 값을 채워 정상 처리하지 않는다.

같은 사람이라고 보고한 관계에는 일관성이 필요하다. A=B이고 B=C이면 최종 관계표의 A와 C도 SAME이어야 한다. 이 초안은 추이 관계를 정리한 최종 표를 요구하므로 A와 C를 DIFFERENT 또는 UNDETERMINED로 남긴 응답은 서버가 수정해 채택하지 않고 거부한다. A=B인데 A와 C는 DIFFERENT·B와 C는 UNDETERMINED인 결과도 같은 이유로 거부한다.

DIFFERENT는 같은 방식으로 이어 붙이지 않는다. A≠B이고 B≠C라는 사실만으로 A와 C가 다른 사람이라고 확정할 수 없다. 이 경우 A와 C의 명시적인 UNDETERMINED는 보존할 수 있다.

관계표가 일관되더라도 실제로 맞는지는 별개다. 원문에 동명이인이라고 적혔는데 모델이 일관된 SAME을 반환했다면 구조 검증은 통과할 수 있다. 이를 찾는 것은 원문과 모델 판단을 비교하는 내용 평가다. 계약 검증기가 원문의 관계를 이해한다고 가정하지 않는다.

### 치환 표시와 미확인 관계를 함께 읽는다

V2 치환기는 SAME으로 연결된 위치에 같은 `[PERSON_1]`을 사용한다. 같은 사람을 다시 지칭한 위치는 번호가 달라도 치환 후 같은 표시로 묶인다. 다른 SAME 집합은 다른 표시로 구분하고, 그 사이의 명시적인 관계를 별도로 남긴다.

| 두 등장 위치의 관계 | 본문의 표시 | 함께 보존할 정보 |
|---|---|---|
| SAME | `[PERSON_1]`·`[PERSON_1]` | 같은 사람이라고 보고한 관계 |
| DIFFERENT | `[PERSON_1]`·`[PERSON_2]` | 두 표시 사이 DIFFERENT |
| UNDETERMINED | `[PERSON_1]`·`[PERSON_2]` | 두 표시 사이 UNDETERMINED |

번호가 다르다는 것만으로 다른 사람이라고 단정하면 마지막 행의 불확실성이 사라진다. 본문만 전달하고 관계 목록을 버려서도 안 된다. 번호는 한 검사 호출 안의 표시이며 다른 문의의 번호와 연결하지 않는다. 이름과 표시를 연결하는 역변환 목록이나 원본 위치는 전송용 결과에 넣지 않는다.

`AiPrivacyScanResultV2Masker.validateAndMask()`는 같은 제목·본문으로 검증과 치환을 진행한다. 다른 문자열에서 검증한 위치를 치환기에 따로 전달하지 않는다. 그래도 Scanner가 잘못된 입력의 결과를 돌려주는 것까지 알아내는 것은 아니므로, 호출부는 검사에 보낸 원문과 받은 응답의 대응을 유지해야 한다.

원문에 이미 `[PERSON_1]` 같은 문자열이 있다면 서버가 만든 표시와 혼동할 수 있다. 독립 치환기는 `[PERSON_` 접두사가 있는 원문을 결과 전체 거부로 처리한다. 해당 문자를 원문에서 지우거나 원문 그대로 전송하는 방식으로 우회하지 않는다. 이 규칙은 AI 준비에 적용하며, 이미 접수한 DB 원문을 취소하는 규칙이 아니다.

치환 뒤에는 표시가 원래 이름보다 길어질 수 있으므로 결과 텍스트의 UTF-8 Byte도 제한한다. 제목·본문의 합계와 관계 목록·Prompt를 포함한 전체 HTTP Body는 다른 크기다. 기존 Known Fragment Guard가 새 표시를 다시 치환해 본문과 관계 목록이 어긋나지 않는지도 전송 연결 전에 확인해야 한다.

### 이름과 일반명사가 헷갈리는 경우

문맥상 사람 이름인지 일반명사인지 판단이 불분명한 표현은 일반명사로 해석하여 PERSON 마스킹에서 제외한다. 이 선택은 일반 문구를 과도하게 가리는 일을 줄이지만 일부 실제 실명을 놓칠 수 있다. 개인정보가 모두 제거됐다는 보장은 아니다.

| 표현과 문맥 | 정책상 판단 |
|---|---|
| `이메일이 도착하지 않습니다.` | 일반명사. PERSON으로 가리지 않음 |
| `이매일 관련 문의입니다.`처럼 이름인지 오기인지 불분명 | 일반명사 쪽으로 해석 |
| 문의자가 자기 이름이라고 명확히 밝힌 `이메일` | 이름이라는 문맥을 평가. 특이한 이름이라는 이유로 무조건 제외하지 않음 |
| `이메일 담당자 김철수에게 문의했습니다.` | 일반명사와 사람 이름을 분리 |

`이메일`·`이매일`을 항상 허용하는 문자열 예외 목록으로 구현하지 않는다. NER가 PERSON이라고 출력한 사실도 모호한 문맥을 확정하는 충분한 근거가 아니다. 이 판단은 문맥 평가 단계의 정책이며, 범위 치환 함수가 단어의 의미를 이해하는 것은 아니다.

인명 모호성은 이메일 주소·전화번호·비밀번호의 보호를 생략하는 이유가 아니다. 검사 Timeout·미완료·잘못된 JSON을 일반명사 해석으로 대체해 원문을 전송해서도 안 된다. 기존 실패 시 전송 중단 계약을 유지한다.

### 모델 파일 크기와 실행 자원은 다르다

모델 파일이 작아도 App과 함께 실행할 수 있는지는 측정해야 한다. 모델 파일 외에도 Python 또는 다른 추론 Runtime, 라이브러리, 입력 처리용 메모리와 JVM이 자원을 사용한다. 처음 모델을 읽을 때의 시간과 메모리, 반복 추론 때의 시간·CPU·메모리를 나누어 확인한다. Test PC에서의 통과만으로 제한된 Cloud Task에서의 통과를 확정하지 않는다.

모델 이름·Version·해시와 Runtime 의존성을 고정하고 배포 라이선스 표기를 확인한다. 합성 입력으로 정확도와 자원을 검증한 후 기존 `AiPrivacyScanner` Port에 연결하며, 검증 전 모델을 설치하거나 후보로 적어둔 사실을 실제 검사 완료로 기록하지 않는다.

## 위치와 종류를 반환하는 예

다음은 위치를 0부터 세고, 시작 위치는 포함하되 끝 위치는 포함하지 않는 예다. 실제 개인정보가 아닌 합성 이메일을 사용한다.

```text
원문: 메일 a@b.invalid, 로그인 성공
탐지 범위: body의 start=3, end=14, type=EMAIL
치환 결과: 메일 [EMAIL_REDACTED], 로그인 성공
```

`start=3`은 이메일의 첫 글자인 `a`의 위치다. `end=14`는 이메일 뒤 쉼표의 위치이며, 쉼표는 치환 대상에 포함하지 않는다. 탐지 결과는 다음처럼 표현할 수 있다.

```json
{
  "field": "body",
  "start": 3,
  "end": 14,
  "type": "EMAIL"
}
```

Java는 수정된 본문을 검사기에게서 받는 대신, 서버가 보관한 입력과 이 범위를 이용해 복사본을 만든다. 탐지 결과가 적용되는 제목·본문은 검사기에 전달했던 것과 정확히 같아야 한다. 검사 전후에 원문을 자르거나 공백을 없애면 위치가 다른 문자열을 가리킬 수 있다.

## 탐지 결과를 적용하기 전에 검사한다

모델이나 별도 검사기가 반환한 결과도 검증 대상이다. 최소한 다음 조건을 확인한다.

- `field`가 허용된 입력 필드인가?
- `start`와 `end`가 약속한 단위의 정수인가?
- `0 <= start < end <= 원문 길이`인가?
- `type`이 서버가 처리할 수 있는 허용값인가?
- 필요한 필드가 빠지거나, 예상하지 않은 필드가 추가되지 않았는가?
- 여러 범위가 중복되거나 겹칠 때 적용할 정책이 있는가?

본문 길이가 20인데 `start=15`, `end=40`이라면 존재하지 않는 위치를 반환한 것이다. 끝을 임의로 20에 맞추면 실제로 어떤 부분을 가리려 했는지 확인하지 않고 다른 결과로 바꾸게 된다. 이런 결과는 정상적인 검사 완료로 취급하지 않고 외부 전송을 중단한다. 잘못된 항목만 버린 뒤 나머지를 적용해 전송하지 않는다.

위치가 유효해도 개인정보 판단이 맞다는 뜻은 아니다. 로그인 성공 문장 전체를 이메일이라고 표시했다면 범위 검사는 통과할 수 있어도 문의의 의미가 사라진다. 개인정보를 놓치는 경우와 일반 문장을 잘못 가리는 경우를 각각 평가해야 한다.

## 중복과 겹침을 처리한다

탐지 위치 목록의 초기 처리 규칙은 다음과 같다. 먼저 각 항목의 형식과 범위를 검증하고, 같은 입력 필드 안에서 원문 기준 위치와 종류를 비교한다.

| 탐지 결과의 관계 | 처리 |
|---|---|
| 같은 필드·같은 시작과 끝·같은 종류 | 중복을 제거하고 한 번만 치환 |
| 같은 필드·같은 시작과 끝·서로 다른 종류 | 종류 충돌로 외부 전송 중단 |
| 같은 필드에서 서로 다른 두 범위가 부분적으로 겹침 | 외부 전송 중단 |
| 같은 필드에서 한 범위가 다른 범위를 포함함 | 외부 전송 중단 |
| 같은 필드에서 한 범위의 끝과 다음 범위의 시작이 같음 | 겹침이 아니므로 다른 검증을 통과하면 각각 치환 |

범위가 `[3, 14)`와 `[14, 18)`이면 첫 범위는 14를 포함하지 않으므로 두 범위는 겹치지 않는다. 제목과 본문은 별도 문자열이므로 위치 숫자가 같다는 이유만으로 중복이나 겹침으로 판단하지 않는다.

겹친 범위를 무조건 합치면 개인정보와 무관한 문의 내용까지 가릴 수 있다. 종류가 충돌했을 때 임의로 하나를 선택하면 연락 수단을 잘못 표현할 수도 있다. 처리 규칙이 없는 충돌은 전송을 멈추며, 접수한 Ticket·Message는 유지한다. 동일 항목의 중복 제거와 충돌 항목의 임의 보정은 다른 처리다.

## 위치의 단위를 맞춘다

Byte, Unicode Code Point, Java의 UTF-16 Code Unit은 같은 단위가 아니다. Java `String`의 일반 인덱스와 `length()`는 UTF-16 Code Unit 기준이며, 일부 이모지는 두 자리를 차지한다. [Java String의 문자 표현](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html)

예를 들어 위치 계약을 Unicode Code Point로 정했다면, 그 숫자를 그대로 `substring()`에 넣어서는 안 된다. 원문에서 `offsetByCodePoints()`로 Java 인덱스를 계산한 뒤 사용한다. 아래는 범위 검증을 마쳤다는 전제의 변환 예다.

```java
int startIndex = body.offsetByCodePoints(0, startCodePoint);
int endIndex = body.offsetByCodePoints(0, endCodePoint);
String selected = body.substring(startIndex, endIndex);
```

`"A😀B"`에서 `B`의 Code Point 위치는 2지만 Java 인덱스는 3이다. 이때 Code Point 범위 `[2, 3)`의 시작과 끝을 각각 변환하면 Java 범위 `[3, 4)`가 된다. 시작 위치만 변환하거나, 치환한 문자열에서 위치를 다시 계산하지 않는다.

서로 다른 언어나 라이브러리로 검사기와 치환기를 만들 때도 단위를 명시하고 변환해야 한다. 이모지 앞뒤의 이메일을 가리는 Test를 두면 ASCII 입력만으로 발견하기 어려운 위치 오류를 확인할 수 있다.

여러 범위를 치환할 때는 원문 좌표를 유지해야 한다. 앞부분을 긴 자리표시자로 바꾸면 뒤쪽 위치가 달라진다. 검증과 중복 제거를 마치고 충돌이 없는 범위만 사용해 원문의 구간을 순서대로 이어 붙이거나, 원문 좌표를 Java 인덱스로 변환한 뒤 뒤쪽부터 치환하는 방법을 사용할 수 있다.

## Java 범위 치환기의 처리 순서

Lab의 `AiInputSpanMasker`는 제목·본문과 `DetectedSpan` 목록을 받아 전송용 `MaskedInput`을 만든다. `DetectedSpan`에는 입력 필드, 원문 기준 Code Point 시작·끝, 개인정보 종류가 들어간다. 개인정보를 찾아내는 일과 감지된 위치를 치환하는 일은 분리한다.

처리는 다음 순서로 진행된다.

1. 제목·본문이 비어 있지 않은지 확인하고, 각 항목의 필드·종류·범위를 검증한다. 범위 상한은 해당 필드의 Code Point 수다.
2. 필드·시작·끝·종류가 모두 같은 항목만 중복 제거한다. 제목과 본문의 같은 위치는 서로 다른 항목이다.
3. 원문의 `offsetByCodePoints()`로 시작과 끝을 Java 인덱스로 바꾼다.
4. 필드별 범위를 정렬하고 겹침·종류 충돌을 검사한다. 제목과 본문 모두 검증을 마친 뒤 문자열을 만든다.
5. 원문의 앞부분, 종류별 자리표시자, 다음 원문 구간을 차례로 이어 붙인다. 이미 치환한 문자열에서 다음 위치를 계산하지 않는다.

예를 들어 다음 호출은 `B`만 가린다.

```java
var masked = new AiInputSpanMasker().mask("문의", "A😀B", List.of(
        new DetectedSpan(InputField.BODY, 2, 3, SensitiveType.CONTACT)));
// masked.body(): "A😀[CONTACT_REDACTED]"
```

위치는 0부터 시작하고 끝은 포함하지 않는다. `B`의 원문 범위 `[2, 3)`을 Java 인덱스 `[3, 4)`로 변환하므로 이모지와 그 앞의 `A`는 그대로 남는다.

잘못된 범위나 충돌은 내용과 원인을 포함하지 않는 고정 오류 `PRIVACY_SCAN_INVALID_RESULT`로 거부한다. 일부 항목만 적용한 결과는 반환하지 않는다. `MaskedInput.toString()`도 내용을 출력하지 않는다. 마스킹에서 놓친 정보가 있을 수 있기 때문이다.

이 API는 Java의 Enum과 `int`로 표현한 위치 목록을 받는다. 외부 검사기의 JSON을 연결할 때는 필수 필드·추가 필드·정수 여부·허용된 필드명과 종류도 별도로 검증해야 한다. 범위 치환기 자체는 검사 완료 여부나 탐지 정확도를 판단하지 않으며, 예외를 Job의 DB 상태로 저장하지도 않는다.

## 검사 완료와 탐지 성공을 구분한다

검사기가 정상적으로 끝내고 빈 목록을 반환한 것과, Timeout으로 검사를 끝내지 못한 것은 다르다. 검사 실패를 빈 목록으로 바꾸면 개인정보가 발견되지 않은 것처럼 보인다. 검사 실패를 원문 그대로 전송하는 경로로 연결하면 검사 장애가 보호 생략으로 이어진다.

이미 접수한 Ticket·Message은 유지하면서 AI 전송을 멈추는 처리와, 문의 접수를 취소하는 처리는 구분한다. 로컬 검사기의 실패와 외부 AI Provider의 실패도 같은 사건이 아니다.

탐지 목록이 비어 있어도 검사기가 모든 개인정보를 찾았다고 보장하지는 않는다. 한국어 문의에 사용할 모델과 규칙은 합성 입력으로 탐지 누락·잘못된 탐지·CPU 처리시간을 확인해야 한다. Presidio의 기본 구성은 영어이며, 추가 언어에는 NLP 모델과 인식기의 설정이 필요하다. [Presidio의 언어별 구성](https://github.com/data-privacy-stack/presidio/blob/main/docs/analyzer/languages.md)

### 완료 표시를 포함한 JSON 계약

위치 목록만 받으면 빈 목록이 ‘검사 완료 후 발견 0건’인지 ‘검사 미완료’인지 구분하기 어렵다. 다음처럼 완료 여부와 위치 목록을 함께 받는다.

```json
{
  "completed": true,
  "spans": [
    { "field": "body", "start": 3, "end": 14, "type": "EMAIL" }
  ]
}
```

| 결과 | 해석과 처리 |
|---|---|
| `completed: true`, `spans: []` | 완료된 검사에서 탐지 0건. 형식 검증을 통과할 수 있지만 모든 개인정보가 없다는 보장은 아님 |
| `completed: false`, `spans: []` | 검사 미완료. 빈 목록만 보고 전송하지 않음 |
| `completed: true`, 잘못된 위치 항목 포함 | 결과 계약 위반. 정상 항목만 골라 전송하지 않음 |
| 제한 시간까지 검사 응답이 없음 | 검사 실행부에서 Timeout을 확인하고 외부 전송 중단 |

`completed`는 필수 Boolean이며, 문자열 `"true"`나 숫자 `1`로 대신하지 않는다. `spans`는 필수 배열이다. 최상위 필드는 이 두 개만 허용하고, 각 항목에는 `field`·`start`·`end`·`type` 네 필드만 허용한다. `field`는 `title` 또는 `body`, `type`은 기존 개인정보 종류의 정확한 Enum 이름이다. 위치는 JSON 정수여야 하며 문자열·소수·지수 표기 값을 정수로 자동 변환하지 않는다. 필드 누락·추가·중복 이름, JSON 뒤의 추가 값도 거부한다.

`AiPrivacyScanResultValidator.validateAndMask()`는 이 형식과 완료 표시를 확인한 뒤, 원문과 위치 목록을 기존 `AiInputSpanMasker`에 전달한다. 제목·본문 양쪽의 범위·겹침 검증까지 통과해야 전송용 복사본을 반환한다. 검사기에게서 받은 전체 JSON이나 Parser의 상세 오류는 예외에 담지 않고, `InvalidScanResultException`의 고정 코드 `PRIVACY_SCAN_INVALID_RESULT`만 남긴다.

`completed: false`라는 응답만으로 Timeout이었다고 단정하지 않는다. 이 검증기는 완료된 결과가 아니라는 이유로 거부한다. 실제 제한 시간 초과 여부는 검사 실행부가 확인하며, 그 사건을 `PRIVACY_SCAN_TIMEOUT`으로 구분한다. 검증기가 예외를 던졌다는 사실만으로 Job 실패가 DB에 저장된 것은 아니다.

검증기 생성 시 응답의 UTF-8 Byte 상한과 항목 수 상한을 명시적으로 전달한다. 중복 제거 전의 전체 항목 수도 제한하며, 계약에 필요한 JSON 중첩 깊이까지만 읽는다. 이 함수는 이미 받은 문자열을 검증하므로, 검사 실행부에서도 응답을 읽는 도중 크기·시간을 제한해야 한다. Unit Test의 상한을 측정 없이 배포 기본값으로 사용하지 않는다.

탐지 정확도의 한계와 검사 실패 시 전송 중단은 다른 문제다. 합성 문의로 탐지 누락과 과도한 마스킹을 평가해 탐지기를 개선할 수 있지만, JSON 검사만으로 탐지 정확성을 증명할 수는 없다. 개인정보가 전혀 남지 않았다는 보장이 필수인 입력은 그 보장 없이 외부 전송을 허용하지 않고, 로컬 처리나 사람의 확인 같은 별도 경로를 검토해야 한다.

## 검사 실패를 Job에 기록한다

로컬 검사기의 실패를 외부 Provider의 실패로 기록하면 어느 단계에서 문제가 생겼는지 구분할 수 없다. 초기 실패 처리 계약에서는 다음 두 코드를 사용한다.

- `PRIVACY_SCAN_TIMEOUT`: 로컬 검사기가 정해진 시간 안에 검사를 끝내지 못했다.
- `PRIVACY_SCAN_INVALID_RESULT`: 검사 결과의 필드·위치·종류가 계약을 위반하거나, 같은 필드의 범위가 겹치거나 종류가 충돌했다.

두 경우 모두 외부 AI 전송을 중단하고 이미 저장한 Ticket·Message는 유지한다. 현재 실행권·상태·처리 기한이 유효한 Job을 `FAILED`로 마감하며 해당 실패 코드를 남긴다. 검사 실패를 `ABSTAINED`나 빈 탐지 목록으로 바꾸지 않는다. 실패 코드와 상태를 DB에 기록하지 못했다면 실패 처리의 Commit까지 완료됐다고 단정하지 않는다.

초기 계약에서는 이 두 실패의 자동 재시도를 하지 않는다. 반복 Polling이나 담당자의 읽기 전용 조회가 재검사·새 Provider 호출을 시작해서는 안 된다. 검사 재시도가 필요해지면 대상 단계·횟수·대기·처리 기한과 현재 실행권을 별도 정책으로 정한다. 외부 AI의 Rate Limit 대기나 출력 보완 정책을 로컬 검사 실패에 그대로 적용하지 않는다.

구현에서는 실패 코드의 Java 허용값·PostgreSQL 제약·조회 응답과 UI 허용값을 함께 맞춘다. 이전 Attempt의 늦은 실패가 새 실행이나 완료된 결과를 덮어쓰지 않도록 기존 현재 실행권 검사도 유지한다. 일반 오류 전체를 두 코드 중 하나로 묶지 않으며, 원문·검사 결과 전체·외부 오류 메시지 대신 고정 코드로 실패 단계를 기록한다.

### 실패 상태와 재시도 차단을 함께 저장한다

실패를 기록하는 일도 하나의 저장 작업이다. Attempt의 자동 복구 차단과 Job의 최종 실패를 별도 Commit으로 나누면, 중간에 DB 오류나 Process 종료가 발생했을 때 일부만 남을 수 있다.

```text
이미 끝난 접수 Transaction
  Ticket + Message + PENDING Job → Commit

실행권 확보 Transaction
  현재 Attempt + 생성 요청 예약 → Commit

검사 실패를 확인한 호출부
  → 짧은 실패 기록 Transaction
      현재 Job·Attempt 확인
      Attempt: AUTO_RETRY_BLOCKED
      Job: FAILED + PRIVACY_SCAN_TIMEOUT 또는 PRIVACY_SCAN_INVALID_RESULT
    → 두 변경을 함께 Commit
```

실패 기록 도중 DB 쓰기가 실패하면 이 Transaction의 변경은 Rollback한다. 앞서 Commit한 문의 원문이나 호출 예약까지 취소하는 것은 아니다. **실패가 발생했다는 사실과 실패 기록의 Commit이 성공했다는 사실도 구분한다.** [Spring의 독립 Transaction 설명](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html#tx-propagation-requires_new)

Lab의 `failPrivacyScanIfCurrent()`는 검사 실패를 저장하는 메서드다. 검사기를 실행하거나 개인정보를 탐지하지 않으며, 외부 AI를 호출하지도 않는다. 호출부는 먼저 실패 종류를 확인해야 한다. 같은 코드를 일반 실패 기록 메서드로 전달해도 재시도 차단 정책을 생략하지 않는다.

현재 Attempt가 달라졌거나 Job이 이미 완료됐다면 늦게 도착한 실패를 저장하지 않는다. 최종 실패가 Commit된 뒤의 Worker Polling은 그 Job을 다시 실행하지 않고, 담당자의 GET은 HTTP `200`으로 `job.status=FAILED`와 고정 실패 코드·`suggestion=null`을 읽는다.

외부 전송 전에 검사가 실패해도 생성 요청 예약이 이미 Commit됐을 수 있다. 예를 들어 예약 1건과 실제 Provider 호출 0회는 함께 성립한다. 예약 횟수를 실제 AI 실행 횟수라고 해석하거나 실패 후 예약을 지워 한도를 복구하지 않는다.

DB 허용값을 늘릴 때는 Java·UI의 허용값도 맞추고 기존 Migration의 Checksum을 바꾸지 않는다. 또한 새 실패 코드를 모르는 예전 Image는 해당 Row를 정상적으로 해석하지 못할 수 있으므로, Schema 호환성과 코드의 값 해석 호환성을 각각 확인한다.

## 검사 결과를 Job 처리 흐름에 연결한다

각 부품의 검증을 마쳤다면 Processor에서 다음 순서로 연결한다.

```text
실행권·예약 Commit → Job에 고정된 Message 원문 조회
  → AiScannedInputPreparer
      AiPrivacyScanner: 로컬 검사 Adapter에 정확히 같은 제목·본문 전달
      AiPrivacyScanResultValidator: 완료·JSON·위치 검증과 범위 치환
      AiInputPrivacyGuard: 기존 알려진 민감 문자열의 추가 치환
  → 남은 처리 시간·현재 Attempt·Lease 재확인
  → Provider Adapter → HTTP Client의 실제 요청 Body 검사·전송
```

`AiPrivacyScanner`는 검사기를 연결할 Port다. 인터페이스를 만들었다고 탐지 모델이 실행되는 것은 아니다. 실제 Adapter는 로컬 검사를 실행하고 응답 크기와 실행 시간을 제한해야 한다. 이 Port를 외부 생성형 AI로 구현하면 개인정보를 가리기 전에 외부로 보내는 문제가 생기므로, 별도 승인 없는 우회 경로로 사용하지 않는다.

`AiScannedInputPreparer`는 검사기·JSON 검증기·기존 Guard를 조립한다. 먼저 원문으로 검사하고, 그 원문 좌표에 범위 치환을 적용한 뒤 알려진 문자열을 추가로 치환한다. 알려진 문자열을 먼저 길이가 다른 표시로 바꾸면 검사기가 반환한 원문 좌표가 맞지 않을 수 있다. DB 원문을 덮어쓰거나 검사기에게 본문 전체를 다시 쓰게 하지 않는다.

검사에 전달하는 시간은 명시적으로 설정한 검사 상한과 Job의 남은 시간 중 작은 값이다. 호출이 돌아온 뒤에도 단조 증가 시간으로 예산 초과를 확인해 늦은 결과를 거부한다. **이 반환 후 검사는 영원히 돌아오지 않는 호출을 중단시키지는 못한다.** 실제 Adapter에서 실행·읽기 대기를 제한하고, 취소·자원 회수까지 검증해야 한다.

Processor는 `ScanTimeoutException`과 `InvalidScanResultException`을 타입으로 구분해 기존 실패 기록 경계를 호출한다. 오류 메시지의 문자열을 검색해 실패 종류를 추측하지 않는다. 예상하지 않은 Adapter 오류를 두 개인정보 코드로 꾸미지도 않는다. 실패 기록 Transaction 자체가 실패하면 고정 내부 오류를 전달하며 `FAILED` 저장 성공으로 응답하지 않는다.

검사가 성공한 뒤에도 현재 실행권을 다시 확인한다. 검사하는 동안 새 Worker가 Attempt를 얻었거나 Lease·처리 기한이 지났다면 이전 실행은 Provider에 전송하지 않는다. 검사 전의 시간 예산을 Provider에 그대로 주지 않고 남은 시간을 다시 계산한다. 검사 대기 중에는 접수·실행권 Transaction이나 Job Row Lock을 유지하지 않는다.

자동 Worker의 조립에는 `AiScannedInputPreparer`를 명시적으로 제공해야 한다. 기존 알려진 문자열 Guard만 있다고 빈 검사기를 자동 생성하지 않는다. 검사 전처리기가 없는데 Worker를 켰다면 Spring 객체 조립 단계에서 실패한다. 이는 이미 실행 중인 Job의 `FAILED`와 다른 실패다. Test 전용 빈 결과 Fixture가 Main의 기본 검사기가 되어서는 안 된다.

## NER의 Token과 마스킹 범위를 구분한다

NER는 입력의 각 Token이 어떤 개체에 속하는지 분류하는 모델이다. 한 이름이 여러 Token으로 나뉠 수 있으므로, Token의 Label과 원문의 위치를 모아 하나의 이름 범위를 만든다.

BIO에서 B는 개체의 시작, I는 같은 개체의 내부, O는 개체 바깥을 뜻한다. 어떤 모델은 `B-PER`·`I-PER`, 다른 모델은 `PER-B`·`PER-I`처럼 표시하므로 모델의 실제 설정을 읽어 변환해야 한다. Label의 표기 차이와 탐지 정확도는 별개다.

```text
원문: 김철수
Token: 김 / 철수
Label: PER-B / PER-I
범위: 시작 0, 끝 3, PERSON
```

모델을 평가할 때는 변환 규칙도 고정한다. 앞선 B가 없는 I나 종류가 다른 I를 거부하는 보수적인 Decoder라면 그 거부 건수도 전체 결과에 남긴다. 유효한 빈 탐지와 혼동하거나, 실패한 Case를 빼서 전체 정확도가 오른 것처럼 계산하지 않는다.

### 누락과 과도한 마스킹은 다른 문제다

이름을 아예 놓치면 개인정보가 남는다. 반대로 `김철수 님` 전체를 가렸다면 이름은 제거됐어도 정답으로 정한 이름 범위보다 더 많이 바꾼 것이다. 정확한 위치를 비교하는 평가에서는 둘 다 불일치가 나올 수 있지만, 개인정보 노출과 최소 변경이라는 관점에서 원인을 나누어 읽어야 한다.

`제 이름` 같은 일반 문구를 PERSON으로 가리는 것도 오탐이다. 영향 인원·마감·복구 사실의 몇 가지 보존 검사만 통과했다고 다른 모든 표현까지 그대로 남았다고 보장하지 않는다. 위치 일치, 민감 문자열 제거, 업무 사실 보존, 인물 관계 유지를 따로 점검한다.

비교 실험의 종료 코드 0은 실험 보고서를 정상적으로 만들었다는 뜻일 수 있다. 반면 운영 Scanner의 0은 실행을 마친 뒤 응답 계약 검증으로 넘어갈 조건이다. 둘 다 모델 품질 합격을 뜻하지 않으므로, 프로그램의 계약과 결과 안의 평가 항목을 함께 읽는다.

## 로컬 검사 Process의 실행과 회수

호출 Thread가 기다리기를 그만두는 것과 검사 프로그램이 종료되는 것은 다르다. Java가 로컬 검사기를 별도 Process로 실행했다면, Timeout 예외를 던진 뒤에도 그 Process가 CPU·메모리를 사용할 수 있다. 실행을 중단하고 자원을 회수했는지는 별도로 확인해야 한다.

`ProcessAiPrivacyScanner`는 `AiPrivacyScanner` Port 뒤에서 단일 전경 Process를 실행하는 Transport다. 전경 실행은 결과를 반환한 뒤 그 실행이 끝나는 방식이며, 뒤에서 별도 작업을 계속하는 Daemon이나 자식 Process 실행은 이 Transport의 계약에 포함하지 않는다. 실제 탐지 모델을 선택하거나 Spring Bean을 자동 등록하는 클래스는 아니다.

### 원문과 결과를 전달하는 통로

| 통로 | 역할 |
|---|---|
| 표준 입력 `stdin` | 제목·본문을 UTF-8 JSON의 `title`·`body`로 전달 |
| 표준 출력 `stdout` | 검사 결과 JSON만 반환 |
| 표준 오류 `stderr` | 별도 크기 제한을 두고 버림. 앱 Log나 응답 JSON에 합치지 않음 |

실행 파일과 인자 목록은 관리자가 고정한다. Shell을 추가하거나 문의 본문으로 명령을 만들지 않고, 원문은 명령행 인자·임시 파일·Log에 넣지 않는다. App의 API Key·DB 암호 같은 환경 변수도 자식에게 복사하지 않는다. 이 구성 자체가 검사 프로그램의 Network·파일 접근을 막는 Sandbox는 아니므로, 신뢰할 실행 파일과 Container 제한을 함께 사용해야 한다.

Pipe는 두 Process 사이에서 데이터를 전달하는 통로이며 저장 공간이 무한하지 않다. 부모가 결과를 읽지 않으면 자식의 출력이 막힐 수 있고, 자식이 입력을 읽지 않으면 부모의 쓰기가 막힐 수 있다. 입력 쓰기·결과 읽기·오류 읽기·종료 대기를 별도 보조 Thread에서 진행하고 주 호출부는 하나의 제한 시간을 관리한다. [Java Process의 입출력 주의사항](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Process.html)

### JSON 출력과 정상 완료를 구분한다

유효해 보이는 JSON이 출력됐더라도 그것만으로 결과를 사용하지 않는다. 응답을 끝까지 읽고, Process가 Exit Code 0으로 종료했으며, 시간 조건을 지켜야 Transport가 결과 문자열을 반환한다. 이후 전처리기가 JSON 필드·완료 여부·위치와 종류를 검사하고 마스킹한다.

예를 들어 JSON을 출력한 뒤 멈춘 실행은 Timeout이다. JSON 뒤에 계속 데이터를 내보내 응답 상한을 넘으면 결과를 거부한다. Test Fixture는 정상 JSON 뒤에 `System.exit(7)`로 실패를 보고한다. 이 `7`은 Test가 선택한 값이며 공통 오류 번호가 아니다. 현재 계약은 `0`만 실행 성공으로 인정하므로 이 JSON은 사용하지 않는다. [Exit Code의 기본 개념](process-health-and-ci.md#exit-code를-읽는-방법)

종료 코드 0과 JSON 검증 통과도 탐지 정확성을 보장하지는 않는다. 모델이 이름을 놓쳤다면 실행 제어를 통과했어도 탐지 품질을 개선해야 한다.

### 종료를 요청한 뒤 실제 종료를 확인한다

Timeout·입출력 실패·호출 Thread 중단에서는 이번 호출이 직접 만든 `Process`만 종료한다. `python`이나 `java`라는 이름으로 다른 Process를 찾아 일괄 종료하지 않는다.

`destroyForcibly()`를 호출한 직후에는 짧은 시간 동안 Process가 살아 있을 수도 있다. 종료 요청 뒤 실제 종료를 기다리고 Pipe와 보조 Thread까지 정리한다. [Java의 강제 종료 설명](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Process.html#destroyForcibly())

검사 제한 시간과 종료 확인 예산은 구분한다. 검사 시간이 끝나면 결과를 더 기다리거나 외부 AI로 전송하지 않고, 별도의 짧은 예산으로 회수를 확인한다. 확인하지 못했다면 고정 내부 오류로 거부하며 자원 회수 성공이나 빈 정상 결과로 취급하지 않는다. 호출 Thread의 Interrupt 표시도 보존한다.

정상 종료와 자원 회수, 탐지 정확도, DB의 실패 저장은 각각 다른 검증이다. 실행 Test에서는 중단 뒤 Process와 보조 Thread가 남지 않는지 확인한다. Pipeline Test에서는 그 실패 뒤 원문·예약이 유지되고 제안이나 외부 요청이 생기지 않는지 확인한다. 실제 모델 평가는 이름 누락·오탐·관계 보존을 따로 확인한다.

## 전송 직전과 원문 보존을 함께 확인한다

마스킹 함수의 반환값이 올바르더라도 요청 생성 코드가 DB 원문을 다시 넣으면 개인정보가 전송될 수 있다. 검사는 실제 HTTP 요청 Body를 대상으로 하고, 검사한 Body를 그대로 전송해야 한다. 이 확인도 사용하는 탐지 규칙과 모델의 범위 안에서 해석한다.

Test에서는 가려야 할 부분이 제거됐는지와 함께, 로그인 성공·영향 범위·긴급성·문의 목적 같은 나머지 내용이 유지됐는지 확인한다. DB의 접수 원문이 변경되지 않았는지도 별도로 확인한다. 잘못된 탐지 결과나 검사 실패를 만들었을 때는 외부 HTTP 요청이 없었는지 확인한다. 원문·민감 값·전체 요청 Body는 Log나 Assertion 실패 메시지에 출력하지 않는다.

범위 기반 Test에는 동일 항목 중복·종류 충돌·부분 겹침·포함 관계·인접 범위와 서로 다른 필드를 각각 넣는다. 충돌이 있는 요청의 전송 0회와 정상 복사본의 치환 결과를 구분해 확인한다. 이 Test는 탐지 결과를 검증하고 적용하는 처리의 근거이며, 실제 모델이 개인정보를 정확하게 찾는지는 별도의 합성 입력으로 평가한다.

Job 처리 Test에서는 두 실패 코드와 `FAILED`의 실제 저장, 원문 보존, 새 Suggestion 없음과 외부 HTTP 전송 0회를 확인한다. 이후 Worker Polling과 담당자 조회를 반복해 재검사·추가 Provider 호출이 생기지 않는지도 별도로 확인한다. 범위 치환 함수의 예외 발생만으로 이 DB·Worker 동작까지 확인했다고 해석하지 않는다.

## 핵심 질문

1. 알려진 문자열을 치환하는 것과 개인정보를 탐지하는 것은 어떻게 다른가?
2. 검사기가 본문 전체를 다시 쓰는 대신 위치와 종류를 반환하도록 하는 이유는 무엇인가?
3. 본문 길이를 벗어난 위치를 임의로 고쳐 마스킹하면 어떤 정보가 가려지는가?
4. 위치 검사를 통과한 결과가 개인정보를 정확히 찾았다는 뜻은 아닌 이유는 무엇인가?
5. Unicode Code Point 위치를 Java `substring()`에 바로 넣으면 왜 잘못된 부분을 자를 수 있는가?
6. 빈 탐지 목록과 검사 Timeout을 같은 결과로 취급하면 어떤 문제가 생기는가?
7. 함수 반환값뿐 아니라 HTTP 전송 직전의 Body와 DB 원문도 확인하는 이유는 무엇인가?
8. 완전히 같은 탐지 결과의 중복과, 겹치는 범위·서로 다른 종류의 충돌은 왜 다르게 처리하는가?
9. 범위 치환 Test의 통과와 탐지 모델의 정확도 평가는 각각 무엇을 확인하는가?
10. 로컬 검사기의 Timeout과 외부 Provider 응답의 Timeout을 구분해야 하는 이유는 무엇인가?
11. 검사 실패 뒤의 Worker Polling과 읽기 전용 조회가 재검사나 AI 호출을 시작하면 어떤 계약을 위반하는가?
12. Attempt의 자동 복구 차단과 Job의 최종 실패를 같은 Transaction으로 저장하는 이유는 무엇인가? 이 기록이 Rollback되면 이미 접수한 문의도 사라지는가?
13. 외부 전송 전에 검사 실패가 났는데 생성 요청 예약이 1건 남아 있을 수 있는가? 예약과 실제 Provider 호출은 무엇이 다른가?
14. `completed: true, spans: []`와 `completed: false, spans: []`는 왜 같은 빈 목록으로 처리할 수 없는가?
15. `completed: false`만 보고 Timeout으로 기록해도 되는가? JSON 검증 예외와 실패 기록의 Commit은 어떤 점에서 다른가?
16. 검사를 성공했더라도 실행권·Lease·남은 처리 시간을 전송 직전에 다시 확인하는 이유는 무엇인가?
17. 검사기 Port의 구현이 없어서 Worker 조립에 실패한 것과, 실행 중 검사가 실패해 Job이 `FAILED`로 저장된 것은 어떻게 다른가?
18. NER가 날짜·수량·기관을 찾아냈다면 전부 개인정보로 보고 가려도 되는가? 마감·영향 범위의 보존과 어떻게 구분하는가?
19. 모델 파일 크기만으로 JVM과 같은 Task에서 실행할 수 있다고 판단할 수 없는 이유는 무엇인가?
20. `PERSON` 종류를 추가하는 것과 실제 모델이 이름을 탐지하는 것은 어떻게 다른가? 통제된 위치의 Test가 통과했는데 실제 모델이 이름을 놓칠 수 있는가?
21. 업무 마감·영향 인원을 보존하면서 이름을 가려야 하는 이유는 무엇인가? 탐지 누락을 숨기려고 문장 전체를 지우면 어떤 정보가 사라지는가?
22. 두 사람의 이름을 같은 표시로 바꾸면 어떤 사건의 의미가 사라질 수 있는가? 같은 이름만으로 동일인을 확정할 수 있는가?
23. 이름인지 일반명사인지 모호한 표현을 일반명사로 해석하는 것과, 검사 Timeout을 무시하는 것은 왜 다른가?
24. 유효한 JSON을 출력한 Process가 종료하지 않거나 비정상 종료했다면 왜 결과를 채택하지 않는가?
25. Timeout 예외 발생·강제 종료 요청·실제 Process 종료·보조 Thread 종료는 각각 어떤 사실을 뜻하는가?
26. 검사 Process를 종료할 때 이름 대신 직접 만든 Process를 대상으로 삼아야 하는 이유는 무엇인가?
27. `[PERSON_1]`·`[PERSON_2]`처럼 표시가 다르더라도 관계가 UNDETERMINED이면 왜 다른 사람으로 단정할 수 없는가?
28. 원문에 서버 표시와 같은 문자열이 있거나, 후속 Guard가 생성 표시만 바꾼다면 본문과 관계표를 어떻게 잘못 읽을 수 있는가?
29. 같은 문자열로 범위 검증·치환을 한 것과 실제 Scanner 입력·응답의 대응을 지킨 것은 어떤 점에서 다른가?
