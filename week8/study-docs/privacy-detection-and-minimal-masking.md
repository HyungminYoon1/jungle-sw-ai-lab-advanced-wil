# 개인정보 탐지와 원문을 보존하는 마스킹

AI에 보낼 문의에서 개인정보를 가리는 일은 두 작업으로 나뉜다. 먼저 어떤 부분이 개인정보인지 찾고, 그 부분을 정해진 표시로 바꾼다. 검사기에게 문의 전체를 다시 쓰게 하는 대신 Java가 확인한 범위만 치환하면, 연락처와 무관한 로그인 복구 사실이나 문의 목적을 유지할 수 있다.

처리 대상은 전송용 복사본이다. 이미 접수한 Message의 DB 원문을 덮어쓰는 작업과 구분한다. 원문의 열람 권한과 보관 정책은 [AI 제안의 신뢰 경계](../../week7/study-docs/ai-suggestion-trust-boundaries.md#원문-보관과-ai-전송은-다른-정책이다)를 함께 참고한다.

## 탐지와 치환의 역할

탐지기는 이메일·전화번호 같은 개인정보의 위치와 종류를 찾는다. 규칙 기반 탐지기는 일정한 형식을 이용하고, NER 같은 모델은 문맥에서 이름·주소 등의 항목을 찾는다. NER는 문장 속 항목의 종류와 범위를 식별하는 작업이며, 자유롭게 문장을 다시 작성하는 작업과 다르다.

치환기는 탐지 결과에 따라 원문의 해당 부분을 표시로 바꾼다. 이메일이면 `[EMAIL_REDACTED]`처럼 확인한 종류를 남기고 실제 값은 제거할 수 있다. 종류가 불확실한 값을 임의로 전화번호라고 바꾸지 않는다. 탐지와 치환을 분리하는 구조는 [Presidio의 Analyzer와 Anonymizer](https://presidio.dataprivacystack.org/text_anonymization/)에서도 사용한다.

미리 지정한 문자열을 찾아 바꾸는 것은 임의의 개인정보 탐지와 다르다. `first@example.invalid`만 등록한 치환기는 `second@example.invalid`를 찾아내지 못할 수 있다. 알려진 문자열 검사 통과는 그 문자열이 남아 있지 않다는 근거이지, 모든 개인정보가 없다는 근거가 아니다.

## 위치와 종류를 반환하는 예

다음은 위치를 0부터 세고, 시작 위치는 포함하되 끝 위치는 포함하지 않는 예다. 실제 개인정보가 아닌 합성 이메일을 사용한다.

```text
원문: 메일 a@b.invalid, 로그인 성공
탐지 범위: body의 start=3, end=14, type=EMAIL
치환 결과: 메일 [EMAIL_REDACTED], 로그인 성공
```

`start=3`은 이메일의 첫 글자인 `a`의 위치다. `end=14`는 이메일 뒤 쉼표의 위치이며, 쉼표는 치환 대상에 포함하지 않는다. 탐지 결과는 다음처럼 표현할 수 있다.

```json
{
  "field": "body",
  "start": 3,
  "end": 14,
  "type": "EMAIL"
}
```

Java는 수정된 본문을 검사기에게서 받는 대신, 서버가 보관한 입력과 이 범위를 이용해 복사본을 만든다. 탐지 결과가 적용되는 제목·본문은 검사기에 전달했던 것과 정확히 같아야 한다. 검사 전후에 원문을 자르거나 공백을 없애면 위치가 다른 문자열을 가리킬 수 있다.

## 탐지 결과를 적용하기 전에 검사한다

모델이나 별도 검사기가 반환한 결과도 검증 대상이다. 최소한 다음 조건을 확인한다.

- `field`가 허용된 입력 필드인가?
- `start`와 `end`가 약속한 단위의 정수인가?
- `0 <= start < end <= 원문 길이`인가?
- `type`이 서버가 처리할 수 있는 허용값인가?
- 필요한 필드가 빠지거나, 예상하지 않은 필드가 추가되지 않았는가?
- 여러 범위가 중복되거나 겹칠 때 적용할 정책이 있는가?

본문 길이가 20인데 `start=15`, `end=40`이라면 존재하지 않는 위치를 반환한 것이다. 끝을 임의로 20에 맞추면 실제로 어떤 부분을 가리려 했는지 확인하지 않고 다른 결과로 바꾸게 된다. 이런 결과는 정상적인 검사 완료로 취급하지 않고 외부 전송을 중단한다. 잘못된 항목만 버린 뒤 나머지를 적용해 전송하지 않는다.

위치가 유효해도 개인정보 판단이 맞다는 뜻은 아니다. 로그인 성공 문장 전체를 이메일이라고 표시했다면 범위 검사는 통과할 수 있어도 문의의 의미가 사라진다. 개인정보를 놓치는 경우와 일반 문장을 잘못 가리는 경우를 각각 평가해야 한다.

## 중복과 겹침을 처리한다

탐지 위치 목록의 초기 처리 규칙은 다음과 같다. 먼저 각 항목의 형식과 범위를 검증하고, 같은 입력 필드 안에서 원문 기준 위치와 종류를 비교한다.

| 탐지 결과의 관계 | 처리 |
|---|---|
| 같은 필드·같은 시작과 끝·같은 종류 | 중복을 제거하고 한 번만 치환 |
| 같은 필드·같은 시작과 끝·서로 다른 종류 | 종류 충돌로 외부 전송 중단 |
| 같은 필드에서 서로 다른 두 범위가 부분적으로 겹침 | 외부 전송 중단 |
| 같은 필드에서 한 범위가 다른 범위를 포함함 | 외부 전송 중단 |
| 같은 필드에서 한 범위의 끝과 다음 범위의 시작이 같음 | 겹침이 아니므로 다른 검증을 통과하면 각각 치환 |

범위가 `[3, 14)`와 `[14, 18)`이면 첫 범위는 14를 포함하지 않으므로 두 범위는 겹치지 않는다. 제목과 본문은 별도 문자열이므로 위치 숫자가 같다는 이유만으로 중복이나 겹침으로 판단하지 않는다.

겹친 범위를 무조건 합치면 개인정보와 무관한 문의 내용까지 가릴 수 있다. 종류가 충돌했을 때 임의로 하나를 선택하면 연락 수단을 잘못 표현할 수도 있다. 처리 규칙이 없는 충돌은 전송을 멈추며, 접수한 Ticket·Message는 유지한다. 동일 항목의 중복 제거와 충돌 항목의 임의 보정은 다른 처리다.

## 위치의 단위를 맞춘다

Byte, Unicode Code Point, Java의 UTF-16 Code Unit은 같은 단위가 아니다. Java `String`의 일반 인덱스와 `length()`는 UTF-16 Code Unit 기준이며, 일부 이모지는 두 자리를 차지한다. [Java String의 문자 표현](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html)

예를 들어 위치 계약을 Unicode Code Point로 정했다면, 그 숫자를 그대로 `substring()`에 넣어서는 안 된다. 원문에서 `offsetByCodePoints()`로 Java 인덱스를 계산한 뒤 사용한다. 아래는 범위 검증을 마쳤다는 전제의 변환 예다.

```java
int startIndex = body.offsetByCodePoints(0, startCodePoint);
int endIndex = body.offsetByCodePoints(0, endCodePoint);
String selected = body.substring(startIndex, endIndex);
```

`"A😀B"`에서 `B`의 Code Point 위치는 2지만 Java 인덱스는 3이다. 이때 Code Point 범위 `[2, 3)`의 시작과 끝을 각각 변환하면 Java 범위 `[3, 4)`가 된다. 시작 위치만 변환하거나, 치환한 문자열에서 위치를 다시 계산하지 않는다.

서로 다른 언어나 라이브러리로 검사기와 치환기를 만들 때도 단위를 명시하고 변환해야 한다. 이모지 앞뒤의 이메일을 가리는 Test를 두면 ASCII 입력만으로 발견하기 어려운 위치 오류를 확인할 수 있다.

여러 범위를 치환할 때는 원문 좌표를 유지해야 한다. 앞부분을 긴 자리표시자로 바꾸면 뒤쪽 위치가 달라진다. 검증과 중복 제거를 마치고 충돌이 없는 범위만 사용해 원문의 구간을 순서대로 이어 붙이거나, 원문 좌표를 Java 인덱스로 변환한 뒤 뒤쪽부터 치환하는 방법을 사용할 수 있다.

## Java 범위 치환기의 처리 순서

Lab의 `AiInputSpanMasker`는 제목·본문과 `DetectedSpan` 목록을 받아 전송용 `MaskedInput`을 만든다. `DetectedSpan`에는 입력 필드, 원문 기준 Code Point 시작·끝, 개인정보 종류가 들어간다. 개인정보를 찾아내는 일과 감지된 위치를 치환하는 일은 분리한다.

처리는 다음 순서로 진행된다.

1. 제목·본문이 비어 있지 않은지 확인하고, 각 항목의 필드·종류·범위를 검증한다. 범위 상한은 해당 필드의 Code Point 수다.
2. 필드·시작·끝·종류가 모두 같은 항목만 중복 제거한다. 제목과 본문의 같은 위치는 서로 다른 항목이다.
3. 원문의 `offsetByCodePoints()`로 시작과 끝을 Java 인덱스로 바꾼다.
4. 필드별 범위를 정렬하고 겹침·종류 충돌을 검사한다. 제목과 본문 모두 검증을 마친 뒤 문자열을 만든다.
5. 원문의 앞부분, 종류별 자리표시자, 다음 원문 구간을 차례로 이어 붙인다. 이미 치환한 문자열에서 다음 위치를 계산하지 않는다.

예를 들어 다음 호출은 `B`만 가린다.

```java
var masked = new AiInputSpanMasker().mask("문의", "A😀B", List.of(
        new DetectedSpan(InputField.BODY, 2, 3, SensitiveType.CONTACT)));
// masked.body(): "A😀[CONTACT_REDACTED]"
```

위치는 0부터 시작하고 끝은 포함하지 않는다. `B`의 원문 범위 `[2, 3)`을 Java 인덱스 `[3, 4)`로 변환하므로 이모지와 그 앞의 `A`는 그대로 남는다.

잘못된 범위나 충돌은 내용과 원인을 포함하지 않는 고정 오류 `PRIVACY_SCAN_INVALID_RESULT`로 거부한다. 일부 항목만 적용한 결과는 반환하지 않는다. `MaskedInput.toString()`도 내용을 출력하지 않는다. 마스킹에서 놓친 정보가 있을 수 있기 때문이다.

이 API는 Java의 Enum과 `int`로 표현한 위치 목록을 받는다. 외부 검사기의 JSON을 연결할 때는 필수 필드·추가 필드·정수 여부·허용된 필드명과 종류도 별도로 검증해야 한다. 범위 치환기 자체는 검사 완료 여부나 탐지 정확도를 판단하지 않으며, 예외를 Job의 DB 상태로 저장하지도 않는다.

## 검사 완료와 탐지 성공을 구분한다

검사기가 정상적으로 끝내고 빈 목록을 반환한 것과, Timeout으로 검사를 끝내지 못한 것은 다르다. 검사 실패를 빈 목록으로 바꾸면 개인정보가 발견되지 않은 것처럼 보인다. 검사 실패를 원문 그대로 전송하는 경로로 연결하면 검사 장애가 보호 생략으로 이어진다.

이미 접수한 Ticket·Message은 유지하면서 AI 전송을 멈추는 처리와, 문의 접수를 취소하는 처리는 구분한다. 로컬 검사기의 실패와 외부 AI Provider의 실패도 같은 사건이 아니다.

탐지 목록이 비어 있어도 검사기가 모든 개인정보를 찾았다고 보장하지는 않는다. 한국어 문의에 사용할 모델과 규칙은 합성 입력으로 탐지 누락·잘못된 탐지·CPU 처리시간을 확인해야 한다. Presidio의 기본 구성은 영어이며, 추가 언어에는 NLP 모델과 인식기의 설정이 필요하다. [Presidio의 언어별 구성](https://github.com/data-privacy-stack/presidio/blob/main/docs/analyzer/languages.md)

## 검사 실패를 Job에 기록한다

로컬 검사기의 실패를 외부 Provider의 실패로 기록하면 어느 단계에서 문제가 생겼는지 구분할 수 없다. 초기 실패 처리 계약에서는 다음 두 코드를 사용한다.

- `PRIVACY_SCAN_TIMEOUT`: 로컬 검사기가 정해진 시간 안에 검사를 끝내지 못했다.
- `PRIVACY_SCAN_INVALID_RESULT`: 검사 결과의 필드·위치·종류가 계약을 위반하거나, 같은 필드의 범위가 겹치거나 종류가 충돌했다.

두 경우 모두 외부 AI 전송을 중단하고 이미 저장한 Ticket·Message는 유지한다. 현재 실행권·상태·처리 기한이 유효한 Job을 `FAILED`로 마감하며 해당 실패 코드를 남긴다. 검사 실패를 `ABSTAINED`나 빈 탐지 목록으로 바꾸지 않는다. 실패 코드와 상태를 DB에 기록하지 못했다면 실패 처리의 Commit까지 완료됐다고 단정하지 않는다.

초기 계약에서는 이 두 실패의 자동 재시도를 하지 않는다. 반복 Polling이나 담당자의 읽기 전용 조회가 재검사·새 Provider 호출을 시작해서는 안 된다. 검사 재시도가 필요해지면 대상 단계·횟수·대기·처리 기한과 현재 실행권을 별도 정책으로 정한다. 외부 AI의 Rate Limit 대기나 출력 보완 정책을 로컬 검사 실패에 그대로 적용하지 않는다.

구현에서는 실패 코드의 Java 허용값·PostgreSQL 제약·조회 응답과 UI 허용값을 함께 맞춘다. 이전 Attempt의 늦은 실패가 새 실행이나 완료된 결과를 덮어쓰지 않도록 기존 현재 실행권 검사도 유지한다. 일반 오류 전체를 두 코드 중 하나로 묶지 않으며, 원문·검사 결과 전체·외부 오류 메시지 대신 고정 코드로 실패 단계를 기록한다.

## 전송 직전과 원문 보존을 함께 확인한다

마스킹 함수의 반환값이 올바르더라도 요청 생성 코드가 DB 원문을 다시 넣으면 개인정보가 전송될 수 있다. 검사는 실제 HTTP 요청 Body를 대상으로 하고, 검사한 Body를 그대로 전송해야 한다. 이 확인도 사용하는 탐지 규칙과 모델의 범위 안에서 해석한다.

Test에서는 가려야 할 부분이 제거됐는지와 함께, 로그인 성공·영향 범위·긴급성·문의 목적 같은 나머지 내용이 유지됐는지 확인한다. DB의 접수 원문이 변경되지 않았는지도 별도로 확인한다. 잘못된 탐지 결과나 검사 실패를 만들었을 때는 외부 HTTP 요청이 없었는지 확인한다. 원문·민감 값·전체 요청 Body는 Log나 Assertion 실패 메시지에 출력하지 않는다.

범위 기반 Test에는 동일 항목 중복·종류 충돌·부분 겹침·포함 관계·인접 범위와 서로 다른 필드를 각각 넣는다. 충돌이 있는 요청의 전송 0회와 정상 복사본의 치환 결과를 구분해 확인한다. 이 Test는 탐지 결과를 검증하고 적용하는 처리의 근거이며, 실제 모델이 개인정보를 정확하게 찾는지는 별도의 합성 입력으로 평가한다.

Job 처리 Test에서는 두 실패 코드와 `FAILED`의 실제 저장, 원문 보존, 새 Suggestion 없음과 외부 HTTP 전송 0회를 확인한다. 이후 Worker Polling과 담당자 조회를 반복해 재검사·추가 Provider 호출이 생기지 않는지도 별도로 확인한다. 범위 치환 함수의 예외 발생만으로 이 DB·Worker 동작까지 확인했다고 해석하지 않는다.

## 핵심 질문

1. 알려진 문자열을 치환하는 것과 개인정보를 탐지하는 것은 어떻게 다른가?
2. 검사기가 본문 전체를 다시 쓰는 대신 위치와 종류를 반환하도록 하는 이유는 무엇인가?
3. 본문 길이를 벗어난 위치를 임의로 고쳐 마스킹하면 어떤 정보가 가려지는가?
4. 위치 검사를 통과한 결과가 개인정보를 정확히 찾았다는 뜻은 아닌 이유는 무엇인가?
5. Unicode Code Point 위치를 Java `substring()`에 바로 넣으면 왜 잘못된 부분을 자를 수 있는가?
6. 빈 탐지 목록과 검사 Timeout을 같은 결과로 취급하면 어떤 문제가 생기는가?
7. 함수 반환값뿐 아니라 HTTP 전송 직전의 Body와 DB 원문도 확인하는 이유는 무엇인가?
8. 완전히 같은 탐지 결과의 중복과, 겹치는 범위·서로 다른 종류의 충돌은 왜 다르게 처리하는가?
9. 범위 치환 Test의 통과와 탐지 모델의 정확도 평가는 각각 무엇을 확인하는가?
10. 로컬 검사기의 Timeout과 외부 Provider 응답의 Timeout을 구분해야 하는 이유는 무엇인가?
11. 검사 실패 뒤의 Worker Polling과 읽기 전용 조회가 재검사나 AI 호출을 시작하면 어떤 계약을 위반하는가?
